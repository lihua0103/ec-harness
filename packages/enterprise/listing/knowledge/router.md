## 自动沉淀闭环 v2（自进化协议；对标业界 agent memory 实践，2026-09-12）

业界共识（Agent Workflow Memory/ICML25、AgentFly、Anthropic Agent Skills、eval-driven
development）：**生产级 Agent 的自进化=经验蒸馏进记忆（模板/技能/口径），不碰权重**；
金标准=golden 基准回归门 + 人工评审门。本库即 dsh 的"程序性记忆"，本协议是其写入
纪律：

```
【写码前】新项目 → router 路由 → 场景库过 Gate → U-Gate 需求理解自审（矩阵+红队，
          见下节）→ 声明门禁 → 读 L5 同型项目档案
          （一遍过率/差异收敛史/体积比——上次踩的坑这次先避开）
【写码中】按 L3 人写风格表达 + 守卫红线（行数守恒/零命中告警）+ [REPLACE] 标记
【交付前 G-Gate】项目存在 golden 基准（golden_gt/golden2=已交付代码同数据产物，
          三个已交付项目目录即常备 QC 基准，2026-09-19 用户定案）→ 交付汇报必须附
          双跑逐文件 QC 结论（0 差异=交付；有残差先 harness 主导自修，修不动如实
          列残差清单，禁止未对账即宣称交付）。**未达双零不得宣告交付、不得结束回合**；
          确需停手必须在汇报里写明残差清单、已排除假设与阻塞点。残差是"值层/结构层
          双查"（NA 敏感 xor 口径 + names/class/label），"celldiff=0 但 FAIL"=结构残差。
          长会话退化对策（实测有效，2026-09-19）：同一会话多轮后开始"宣告完成+给
          残差找语义豁免"时，换**新鲜收尾会话**接手——只带 GT 路径+残差模式清单+
          逐列镜像指令，一次一列组外科对齐，不重跑全量推导。
【交付前 D-Gate】"可交付"四查（逐条在汇报里给结论，不许默认）：
          ① **根路径**：程序 root 默认值=交付运行时的项目根（会话项目目录即运行目录）；
             若产物要搬去另一台机器/路径，须改默认值或显式声明用 DSH_R_PROJECT_ROOT 覆盖；
          ② **单文件自包含**：无 source()/无会话临时脚本（.dsh/work、探针 .R）依赖；
             依赖仅 harness 契约允许的基础包（readxl/dplyr/tidyr/stringr/openxlsx/haven，
             按车道）；服务器无 python、无网络安装前提；
          ③ **[REPLACE]/待确认清单**：逐条给出"已实证取值"或"需用户确认"的当前状态；
          ④ **产物与运行摘要**：文件名/落盘目录/行数·flag 计数与 spec 契约一致，
             QC 报告与残差清单（如有）随交付。
【收尾学习协议】（触发：项目收官/人工参考代码投递/新错误新口径；AI 执行，人工评审）
  1 GT 基准：人工代码原样跑同数据（仅补环境依赖与输入形态字面量，业务逻辑零改动），
    产物入项目 golden_gt/
  2 双跑逐文件 QC：AI 产物 vs GT——列序/class/label/逐单元格/文件形态（sheet 名/
    文件名/精度口径），0 差异=值层通过（datasetQC 按列名比会掩盖结构差异，勿单用）
  3 风格三维分析：值层（diff 数）/结构层（列序·sheet·命名）/表达层（体积比·注释比·
    管道形态·[REPLACE] 标记）
  4 蒸馏入库：差异→Gate 强化/口径终案/postmortem；核查写码纪律（注释 ≤15%、体积
    ≤人工 2 倍、论证进库不进程序）
  5 eval 刷新：golden 切 GT 基准 → dsh-standard-verify ALL PASS
  6 项目档案：场景库 L5 记一行（一遍过？差异点？KPI 数字）
  7 人工评审门：AI 只写 kb-capture 提案/档案草稿，人评审后合入（生产共识，勿跳）
```

KPI（每项目收尾记录，驱动"一遍 QC 通过"）：first-pass QC 通过率、值层 diff 数、
体积比（AI/人工）、注释占比、结构差异数。

铁律（与个人 skill 架构章程一致）：
1. 没有回填 Gate 的修复不算完成；2. 没跑 eval 的知识库改动不算完成；
3. 正文沉淀方法论不沉淀字段值（项目特定值只留项目程序/模板行段/golden 沙箱）。

## 写码前需求理解自审（U-Gate，全场景强制；2026-09-19 定案）

"100% 理解需求"不是口号，是两个可判定产物——**理解矩阵 + 红队复查**。读完全部
需求文档（U-Gate 在 read_document 之后、DSH-BUSINESS-ZONE 生成之前执行）：

1. **需求理解矩阵**（随交付汇报留存，可被审计）：spec 需求逐行/逐变量四元组
   `需求原文要点 → 口径判定 → 数据源证据（表单/列/值域实证）→ 置信级`。
   置信级：**E**=对实际数据实证 / **I**=需求文档+临床惯例推断 / **U**=未知。
2. **红队复查**（三类必查，全部来自真实事故）：
   ① **号体系**——筛选号/随机号/LIMS 形态/掩码，桥接两侧键形态逐侧实证（GP2 型）；
   ② **时间戳来源**——录入戳 vs 业务时刻，"字段自带时间"必须全行恒定差值+时刻
   分布双重实证才可采用（GP1 型）；
   ③ **边界与 off-by-one**——时点/访视/窗口/队列的每个枚举值域逐项与数据对表
   （2026-09-19 实案：PC 表 SD2/3/4 时点标签 48/72/96 与 EDC 采样记录错位一格，
   理解矩阵级值域实证当场抓出并修正）。
   另：spec 注释列/干跑值**不可信**（须独立重算，见 RBQM 教训）；旧项目惯例跨项目
   套用前先实证（GP8 同源纪律）。
3. **100% 判据**：矩阵中不存在未处理的 U 级——每项要么实证升级为 E，要么列入
   **待确认清单**给用户出路（禁止自挑相近字段代理实现后当 PASS）；I 级必须在
   汇报中显式声明推断依据。矩阵条目与生成区证据注释一一对应。
4. 通过 U-Gate 才渲染/编辑程序；生成区未生成运行 fail-fast 的出路里含本节指引。

## 分层（每场景库统一结构）

- **L0 路由**：本表（签名→场景→门禁摘要）
- **L1 门禁 Gate**：写码前必须通过（坑的预防形态，未过不得渲染/编辑程序）
- **L2 口径终案**：用户/DM 拍板记录（勿走回头路）
- **L3 方法论**：按 Gate 必读拉起（人写风格/精简度纪律）
- **L4 postmortem**：信号→预防 Gate→修法（兜底，推优先于拉）
- **L5 项目档案**：同型项目收官记录（一遍过？差异收敛史？KPI）——新项目先读，
  上个项目的终点是下个项目的起点
