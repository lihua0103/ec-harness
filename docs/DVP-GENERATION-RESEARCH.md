# 方案（Protocol）→ 数据核查计划（DVP）生成方法研究

更新：2026-11-10。目的：为 DSH 的 DM DVP 插件开发积累经验底稿。本文只记录**已核验**的方法、原文与代码现状对照，不声称任何插件实现。原始文本本地索引见 §9。实操视角配套文档：[DVP-DM-PRACTICE.md](DVP-DM-PRACTICE.md)（DM 全项目周期工作流、标准规则模式、取舍判断与常见坑）。

---

## 1. 结论摘要

1. **DVP 的正源定义（CDE 2021 词汇表）**：数据核查计划（Data Validation Plan, DVP）"也称逻辑核查计划，是由数据管理员为检查数据的逻辑性，**依据临床试验方案以及系统功能**而撰写的系统设置文件"。定义本身就说明：方案只是两大输入之一，**系统功能（CRF/ALS/数据库设计）是另一必需输入**。
2. 行业共识流程是一个**证据链**，不是一次性文案生成：
   方案 + aCRF/ALS/数据库设计 + 系统能力 → 结构化核查规格（每条规则固定字段、可溯源）→ UAT（正确/错误/**边界**数据组合全覆盖并留档）→ 版本化变更控制 → 上线后按需修订。
3. 方案只能直接确定**需求层**内容（目的、关键/次要终点、入选排除、访视窗口、安全性关注点）；**字段级逻辑**必须落到 aCRF/ALS/数据库设计；**质疑文案与实施方式**（前端/后端、系统内外）依赖系统与申办方约定；**医学裁定**（如实验室异常是否报 AE）依赖人工。
4. 对插件的定位启示：插件应生成**候选核查规则 + 方案条款溯源 + 正/反/边界测试用例建议**，交 DM/医学/统计审核确认——生成的是"CANDIDATE 草稿"，不是最终 DVP。这和平台 KnowledgeService 的 `CANDIDATE→ACTIVE` 生命周期天然同构。

## 2. 术语与文件关系

| 术语 | 含义 | 备注 |
|---|---|---|
| DVP 数据核查计划 | 依据方案与系统功能撰写的逻辑核查系统设置文件 | CDE 2021 词汇表用 **Data Validation Plan**；2016 年 EDA 指导原则（114号）转载文本用 Data Verification Plan。正式引用需按所引原文；行业两种展开并存 |
| DVS 数据验证规格 | EDCTP 语境下逐条检查规则的详细规格文档 | 可作为 DVP 的附件/明细层；系统核查与人工核查可分册 |
| Edit Check / 逻辑核查 | 数据输入系统后对有效性的检查，经程序逻辑、子程序、数学方程实现 | 评价输入数据与预期数值逻辑、范围、属性的偏离 |
| UAT 用户接受测试 | 用户全面检测所有正确和错误数据组合并记录 | CDE 要求文档含验证方案、测试细则记录、测试总结报告、验证总结报告 |

文件关系：DVP 通常作为 DMP 的附件或独立文件；逐条规则明细 = DVS；输入侧依赖方案（Protocol）、aCRF、数据库设计说明；产出侧驱动 EDC 逻辑核查配置、质疑（query）发出与外部数据一致性核查程序。DVP 及"逻辑检验及衍生数据变更控制列表、数据质疑表"均列入 CDE 归档清单。

## 4. 监管与指南锚点

**ICH E6(R3)**（表述均为"应该 should"级期望，非"必须"硬性条款）：

- **§4.2.1(c)**：在数据采集点，"应基于风险考虑采用自动化数据验证检查以发出数据质疑，且其**实施应受控并有文档记录**"。
- **§4.2.3**：数据与元数据（含稽查轨迹）的审阅"应是**有计划的活动**，范围与性质应基于风险、适配具体试验，并在试验过程中根据经验调整"——核查规则不是一次定稿。
- **§4.2.4**：数据更正应归因到人或系统、有依据、及时。
- **§4.2.6**：分析前数据定稿"按预先规定的程序确认并记录"，含数据核对、错误整改、医学编码、方案偏离影响处理。
- **§4.3.4(e)**：标准功能**和方案特定配置**（含自动数据录入检查与计算）都应验证；**(h)** 随机化、给药、终点数据采集等关键功能为重点。

**CDE 2021（数据管理计划部分）**：

- "在进行数据核查之前，应制定详细的数据核查计划，以明确**数据核查内容、方式与核查要求**。数据核查通常需要数据管理人员、监查员、医学人员及统计师等**共同完成**，因此应在数据核查计划中明确不同人员的职责分工。"
- 数据库设计"应与注释病例报告表和/或数据库设计说明保持一致，并**依据数据核查计划建立逻辑核查**，经用户接受测试合格后方可上线使用"。
- 外部数据管理要求制订传输协议并质控（传输测试、一致性核查）。
- 归档清单含数据核查计划、逻辑检验及衍生数据变更控制列表、数据质疑表。

## 5. 方法：从方案到核查规则（SCDM 2023 + EDCTP §2.7 综合流程）

### 5.1 输入材料（SCDM "Sources of information"）

1. **研究方案**：试验目的、入选/排除标准、安全性参数、主要与其他终点。
2. **DMP**：研究级数据约定，指明需要设计核查的变量。
3. **aCRF 与数据库设计文档**：核对核查与答案选项、数据库结构对齐（对应中文语境即 aCRF/ALS）。
4. **标准核查宏/规则库**：跨研究复用常用检查。
5. **生物统计师**：指出哪些领域做核查有利于统计交付。
6. **研究方/中心人员**：指出既往易错、易超范围的字段。

### 5.2 前置条件（SCDM Minimum Standards 首条）

**方案定稿 + 初步数据库规格完成之后**才设计核查。插件意义：输入材料不齐（缺方案版本或缺 ALS）时只能产出"需求层候选"，不应伪称字段级规则可用。

### 5.3 覆盖优先级（层级视图）

SCDM 给出的层级（重要性递减、效率视角）：

1. **Endpoint checks**：主/次终点变量缺失、错误、超范围——统计成败所系。
2. **Safety checks**：安全性参数偏离（如"有 AE 但无 AE 表"）。
3. **Protocol compliance checks**：入选排除核对、方案规定参数（如随访访视窗口）。
4. **Programmed checks**（系统内自动）→ **Manual checks**（自由文本等无法程序化的）→ **Listing checks**（跨字段列表人工审阅）→ **External checks**（外部数据一致性）。

与 ICH E6(R3) 风险/关键性导向一致：终点与安全数据优先，非终点非安全字段需评估"建核查的收益 vs 处理其产生质疑的成本"。

### 5.4 检查类型分类（8 类 + 前/后端）

Missing values（只对关键变量）、Missing CRF pages（可全表）、Range checks、Duplicates、单表内逻辑矛盾、跨表/跨模块矛盾、外部数据核查、方案违背类（多为范围/窗口类）。
Front-end（录入时触发，限单字段/单页）vs Back-end（多表聚合，复杂、难写）。SCDM Table 2 给出各类型的前/后端归属矩阵。

### 5.5 每条规则的最小字段集（EDCTP §2.7.1 DVS 字段 + SCDM 样例表合并）

| 字段 | 说明 | 来源可溯性 |
|---|---|---|
| Check ID | 唯一编号（如 DM001） | 系统 |
| Version | 逐条版本跟踪 | 变更控制 |
| Form/Module | 适用 CRF/数据集 | aCRF/ALS |
| Field/Variable | 涉及字段 | aCRF/ALS |
| System/Manual | 系统内实现 or 外部列表 | 申办方约定 |
| Check Type | query / derivation / email alert… | 系统能力 |
| Description | 意图或场景（如"随机化日期不得早于知情同意日期"） | **方案条款** |
| Logic | 触发逻辑。EDCTP 示例（提取文本可能丢一词，语义按 SQL 惯例补全）：`(DM.RANDAT is not null AND ICF.CONSDAT is not null) AND (DaysBetween(DM.RANDAT, ICF.CONSDAT) < 0)` | 方案 + ALS |
| Query Text | 标准质疑文案 | 申办方文案规范 |
| Listing Output | 人工列表的列/表头/排序 | 申办方约定 |
| Additional Instructions | 特殊场景对 DM/程序员的补充指引（如"已划线页面不质疑"） | 方案/约定 |
| （建议增补）protocolSource | 方案章节/页码/条款号 + 方案版本 | 溯源矩阵的键 |

### 5.6 撰写一致性约定（SCDM）

用通用词（"Subject"而非"Patient"）；字段名**与 CRF 完全一致**（"Date of Birth"而非"Birth Date"）；完整句子、统一句式（"Visit Date must be present"、"If Not Done is marked, Result must be blank"）；统一格式约定（字段名大写、仅在句子不清时加括号）；标注例外与特别说明。

### 5.7 质疑文案规则（SCDM Message Wording）

必须明确传达：研究/中心/受试者标识（遵守隐私规范）；触发字段名与值；**支持值**（如 BMI 超范围须同时给出身高体重）；**不得诱导**——不得在文案中透露期望范围（血压核查只说"超出预期范围，请确认或更正"，不写"应在 80–200 mmHg"）。人工补发的质疑同样遵循此规范。

### 5.8 测试与验证（SCDM + CDE UAT）

- 测试数据须含**应触发**的超范围/不一致值与**不应触发**的正常值，覆盖全部场景；边界必须显式测试（SCDM 原例：范围 80–200，须验证 <80、>200 触发，且**恰为 80、200 不触发**）。
- 反馈闭环：CDM 与编程人员按测试计划互查，未按预期触发/误触发都要记录；未测场景须明确说明。
- 文档：pass/fail 表（测试人签名日期）、数据库触发/未触发证据、QC 覆盖核查设计、编程与全部文档。
- 研究中新增/修订核查走同样的验证步骤。

### 5.9 版本与变更控制（SCDM）

首个批准版 V1.0；微小行政修订 +0.1（V1.1）；CRF 变更等实质修订 +1（V2.0）；所有变更记录修改人、日期、原因（邮件批准须记日期与发件人）；核查文档是**活文档**，研究中期可因 CRF 变更、逻辑/文案纠错、新发现偏差增删；研究结束归档终版。

### 5.10 平衡与效率（SCDM Balance & Efficiency）

- 不为"能做"而做：核查收益须对比**质疑处理与关闭的成本**。
- 自由文本字段：程序化核查不如 DM 人工列表审阅高效可靠。
- 系统性数据趋势可能更适合统计师在分析准备阶段发现；CRA/医学监查/编码员也可能经列表发现核查覆盖不了的问题——核查设计应咨询统计师。

## 7. 对 DSH 插件的启示

### 7.1 可复用（已核验代码现状）

- **工作簿读取**：`plugins/dm-listing/src/workbook.ts` / `workflow.ts` 的 overviewProject/readWorkflowSheet（坐标、隐藏行列、合并、公式表达式、限额与告警）可直接读 ALS 与**已有 DVP 工作簿**——`project.ts:7-10` 现已把文件名含 `dvp`/`需求`/`spec` 的 Excel 列为候选线索。
- **KnowledgeService**（`packages/platform-knowledge/src/schema.ts`）：`CANDIDATE/ACTIVE/SUPERSEDED/REVOKED` 生命周期 ≙ 核查规则"草稿/UAT通过批准/被新版本替代/撤回"；`scope=project` 存项目裁定、`shared/plugin` 存可复用规则模式；ValidationSuite 的正/反/边界用例结构（`MethodCase: group=positive|negative|boundary`）与 SCDM 测试要求同构。
- **需求 IR 模式**：listing 插件 `dm_listing_save_requirements` 的 itemsJson（id/meaning/condition/columns/mapping/validation/unresolved）与 DVP 规则 IR 高度同构，可作协议抽取 IR 的骨架（换成 clauseId/requirement/condition/variables/checkType/queryText/protocolSource/unresolved）。
- **接入模式**：Cordis patch + tools/skills/userQuestions + UI slot（`plugins/dm-listing/src/index.ts`、`cordis.patch.yml`）；歧义交可信 UI 询问的模式已存在。

### 7.2 需新建（不可假设已有）

1. **方案文档解析**：代码库**没有** PDF/DOCX 正文、表格、扫描件解析器（`readProjectArtifact` 对非文本只回 base64）。这是最大缺口。
2. **DVP 规则域模型与产物生成**：§5.5 字段模型、溯源矩阵（方案条款→规则ID→字段→用例）、**xlsx 写出**（现只有读）。
3. **测试用例建议器**：按 §5.8 为每条规则生成正/反/边界用例清单（恰等于边界值）。
4. **EDC 方言适配**：Logic 表达式按目标 EDC（Rave Architect/太美/自研）的配置方言生成——EDCTP 示例仅是伪 SQL。
5. **方案版本感知**：方案修订 → 受影响规则重审（对应 SCDM 的 living document + ICH §4.2.3"根据经验调整"）。

### 7.3 生命周期映射建议

知识库种子存"可复用核查模式"（如"随机化≥知情同意"、"AE 有无药对应合并用药"类通用规则，EDC 无关）；项目实例（具体字段绑定、阈值、文案）存 `project` scope 的候选记录；审核确认动作 = 激活（须通过用例验证）；方案修订 = SUPERSEDED 旧版 + 新候选。检索现状是 Unicode 子串非 FTS（`service.ts`），规则量上去后需升级。

### 7.4 明确不可做

- 不替代医学/统计判断（§6 最后一列）；生成物一律标待审核。
- 不把历史项目阈值/OID/文案自动推广为新项目默认（与 docs/README.md"三项目历史方法不包含对新项目的默认阈值"一致）。
- 不伪称 UAT 已通过——只有真实测试证据才能把候选转 ACTIVE（与 DEVELOPMENT.md"不伪报测试通过"原则一致）。
- 误报成本要呈现给审核者：每条候选附触发预期与关闭成本提示（§5.10）。
