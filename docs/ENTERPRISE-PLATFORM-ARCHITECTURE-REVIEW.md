## 结论

**方向正确，抽象层级需要调整。** 保留 DeepSeek Harness 底座、业务插件、知识驱动、受控数据执行与自主 Agent。当前文档适合作为 Listing 插件设计草案，但不足以直接作为企业平台总架构。

主要偏差：平台公共能力被包装进 Clinical Host/Runner/Console，企业身份与项目权限被放到末期，插件扩展合同与跨插件安全边界尚未定义。建议采用“企业平台内核 + Harness 适配层 + 能力服务 + 业务插件”，首期模块化单体，只有安全边界要求的执行器/本地连接器独立进程，不先做微服务或插件市场。

## 1. 评审发现（按优先级）

### P1：公共平台能力归属临床，第二个插件将被迫依赖 Listing

依据：原设计第 3–4 节，clinical-host 同时拥有工作区、来源、执行授权和输出合同；工程目录公共协议也命名为 clinical-contracts。

场景：新增非临床文档工具时，也需要工作区、运行记录、制品与审批，但只能依赖临床组件或复制一套；R 环境可能成为所有插件的启动依赖。

修正：公共 Workspace、Run、Artifact、Approval、Policy、Knowledge 服务归平台。Listing 提供领域 schema、工具、知识模板与 QC 规则；R 是执行能力的一种，不是平台唯一执行方式。领域适配器必须由平台审核和授权，不能自己扩权。

### P1：企业身份与项目访问隔离安排太晚

依据：原设计第 1 节及第 11 节，将 SSO/RBAC、项目隔离放到后期。

场景：多人试用时若 run/session/knowledge/artifact 没有稳定用户及项目归属，后补登录无法补回历史访问边界和审核主体，也容易交叉检索项目知识。

修正：首期建立 userId、projectId、workspaceId、runId、pluginId/version、权限检查与审计。可暂时用本地身份或测试账号适配，正式多人使用前接企业认证和项目授权。完整 SSO 管理界面可后置，身份与授权模型不可后置。内部单企业平台不必先做 SaaS 多租户计费或复杂组织树。

### P1：插件注册不等于权限隔离，Listing 规则不能被其他插件绕过

依据：原设计第 9 节提到工具 guard 与受控 profile，但尚无平台级插件权限生命周期和多插件访问合同。

场景：Listing 禁止读 Cover，但同一 session 加载的通用 Excel/文件/浏览器插件可能读到原文件；插件被禁用后，残留 worker、tool、cache 或旧会话仍可能访问。

修正：所有访问按用户、项目、资源、插件和运行身份计算有效权限。规则生效于已登记资源及其派生物，不只作用于 Listing 工具名。通用读取能力不能绕过受保护工作簿投影；可读普通资源保持正常能力。停用插件撤销未来调用和授权，取消/隔离其任务，清理注册，并保留审计。另一个插件请求扩大权限必须显式审批。

同进程插件默认是经过审核的可信代码；不能用 Cordis 生命周期或 JS 类型声称隔离不可信插件。不可信可执行扩展不进入同一特权进程，首期可直接不支持。

### P1：知识与安全策略的权威边界需要显式分开

依据：原设计第 5 节将 blockedSheets 与场景知识模板相邻定义。

场景：自动学习或项目覆盖修改了模板，从而把 Cover 从禁读变成可读；模型以知识中“已授权”为由读取辅助原始 data。

修正：知识提供名称、别名、布局及处理方法；平台策略执行不可被知识修改的拒绝规则。Listing 安装时提交规则建议，经管理员批准为项目策略。项目策略优先于知识匹配、用户任务文字和插件配置；普通单次选择不改变平台强制策略。

Manual Review 与 DM Status Report Specification 属于 Listing 场景知识；Cover 禁读属于当前 spec 资源上的强制策略。不能把 Cover 这个名字硬编码成所有企业 Excel 文件全局禁读。

### P2：通用运行状态与 Listing 业务阶段需要分层

依据：原设计第 8 节的唯一状态链包含 UNDERSTANDING/DEVELOPING/VALIDATING。

场景：引入无需写代码的插件后仍被迫使用编程阶段；若平台重建 Agent 循环，又与 Harness 会话、取消和恢复重复。

修正：平台管理 CREATED/RUNNING/WAITING_FOR_USER/SUCCEEDED/FAILED/CANCELLED 等通用生命周期；Listing 在运行记录中维护 sheet 选择、需求理解、R 生成、QC 等业务阶段。Harness 负责模型/工具迭代，平台调度器负责持久任务、幂等和授权；业务步骤可迭代，不强制单向串行。

### P2：插件合同与上游适配边界不足

依据：原设计第 9 节有 bundle/profile 的方向，但缺企业应用注册合同。

场景：每个插件自行注册全局工具和页面、访问凭据或独立绑定 provider；插件升级可能使旧任务无法恢复，Harness 升级影响所有业务实现。

修正：定义企业插件 manifest/SDK，包含 ID/版本、兼容范围、工具命名空间、输入输出 schema、能力申请、知识包、UI 入口、生命周期和迁移规则。平台统一凭据、模型配置及调用审计；业务插件默认不持有模型密钥。薄 Harness adapter 只封装企业实际使用的扩展点，不重建 Harness 全部能力。

### P2：本地工作目录与平台控制面的部署关系尚不明确

依据：原设计第 3–4 节假定本地 Host，但企业多人控制面如何连接各人工作区未定义。

场景：未来平台部署到服务器，浏览器选中的本机路径对服务器不可访问；误以为“选目录”可直接上传同步，会突破临床数据边界。

修正：逻辑上区分平台控制面和工作区执行节点。单机首版可同机部署；企业共享控制面通过已鉴权本地连接器下发任务，本地原始 data 不自动上传。中央保存安全运行元数据和允许材料，受保护内容留在绑定节点。节点身份、离线/重连、凭据保管、工作区归属需纳入合同，首期无需实现复杂分布式调度。

## 2. 推荐分层

```text
企业工作台
  ├─ 应用/插件入口、项目选择、会话、任务、制品、审批
  │
  ├─ 平台服务
  │    Identity/Project/Workspace/Run/Artifact
  │    Policy/Audit/Knowledge/Model Configuration
  │
  ├─ Harness 适配层 ── DeepSeek Harness
  │    使用上游 Agent 循环、会话和工具机制
  │    对接企业身份、策略与运行记录，不另造一套 Agent 引擎
  │
  ├─ 业务插件
  │    ├─ DM Listing：场景知识 + 需求理解 + R 生成 + QC
  │    └─ 后续插件：依赖公共能力，不依赖 Listing
  │
  └─ 能力服务 / 工作区节点
       文件投影、Excel、知识检索、执行任务、制品
       R 执行适配器；后续按需要增加其他运行时
       受保护执行、原始数据浏览：独立权限/进程边界
```

层是职责划分，不是每层/模块必须部署一个服务。平台 UI 可统一入口，原始数据查看用独立权限与安全 origin；不为每个插件另造整套工作台和登录系统。

## 3. 平台与 Listing 的归属表

| 能力 | 平台所有 | Listing 所有 |
|---|---|---|
| 目录/项目 | 目录注册、权限、资源版本、节点映射 | spec/ALS/rawdata 等业务角色 |
| Excel | 列 sheet、受控区域读取、资源策略检查 | Manual/Report 名称、别名、布局 |
| 知识 | 访问范围、版本、检索、候选/激活/撤回 | DM 方法、场景经验、合成反例 |
| 模型 | 配置、凭据、预算、调用审计 | 业务指令、推理任务、上下文选择 |
| 执行 | 任务、身份、隔离、限额、取消、授权 | R 程序及所需运行时声明 |
| 质量 | 通用证据、报告与审核记录 | Listing 业务 QC 与交付标准 |
| 数据边界 | 不可旁路的执行机制、来源及输出合同 | 受保护来源定义与领域处理适配 |
| 工作流 | 等待用户、恢复、幂等、状态、超时 | 需求发现→理解→生成→验证的业务阶段 |
| UI | 项目/会话/任务/审查基础组件 | Listing 专属需求及 QC 展示 |

共享 Excel/SAS/诊断适配器只有经过审核后才成为可信能力；不能让普通插件随意注册一个“安全投影器”并直接发布原始值。

## 4. 最小企业插件合同（设计建议，不是上游已验证 API）

- 标识：pluginId、version、platformApiRange、harnessCompatibility。
- 注册：入口、工具命名空间、可选 UI、输入/输出 schema、知识包。
- 权限：申请 filesystem/execution/model/knowledge 等能力及资源范围；声明不等于授权。
- 生命周期：install/enable/disable/upgrade；撤销能力、在途任务处理与版本兼容。
- 运行：统一 RunContext 和事件流，业务状态嵌入而不污染平台枚举。
- 版本：运行绑定插件、知识、工具 schema 与运行时；旧任务选择兼容旧版或显式迁移，不静默使用最新版。
- 信任：首期仅安装企业审核的插件，发布包摘要与审批记录可追溯；插件不能自行加载任意远端代码。

建议先实现明确业务所需的最小接口，不先开发完整公开插件市场、通用低代码引擎或复杂多 Agent 调度平台。

## 5. Listing 应当保持小，但不能只是提示词

Listing 本身只包含：

1. 场景知识：Manual Review、DM Status Report Specification、已确认别名和需求布局。
2. 需求处理：先读名称，不确定则询问；未确认不读取候选内容试探。
3. ALS/字段映射与需求 IR。
4. R 生成、合成测试和业务 QC。
5. 交付格式及 Listing UI。
6. 能力依赖与领域策略声明。

不拥有登录系统、独立模型客户端、全局任务数据库、通用审计、独立文件权限体系或自己的完整 Agent 引擎。

其中知识包可作为插件内容发布，但知识包、可执行插件、平台策略是不同概念。知识帮助模型正确理解业务；工具执行真实操作；平台强制边界。三者不能互相冒充。

## 6. 平台首期必需与可后置

首期必需：稳定身份/项目/run 归属、资源授权、插件注册与启停、模型配置、知识作用域、基本持久任务与恢复、制品权限、审计、执行边界、版本绑定。

可后置：完整 SSO 管理界面（但多人正式上线前必须认证）、复杂组织树、分布式调度、计费、大规模向量检索、插件市场、服务器自动同步和多区域高可用。

建议用 Listing 贯通第一条真实业务链，同时用一个只处理普通合成文档的测试插件验证平台无临床依赖：不开发第二个正式产品，仅做架构验收夹具。

## 7. 架构验收条件

- 停用 Listing 后平台仍启动、普通会话/项目/任务可用；未授权的历史受保护资源仍不可读。
- 第二个测试插件无须导入 Listing 或修改平台核心的业务条件分支。
- 同一受保护工作簿经通用 Excel、shell、附件、历史和浏览器入口访问仍执行资源策略。
- 知识升级或用户选择不能撤销 Cover 禁读与原始 data 红线。
- 用户 A 的项目、制品、知识、审批不能被用户 B 或其他项目句柄越权访问。
- R 缺失时只使 Listing 的相关执行能力不可用，不阻塞整个平台。
- 任务绑定版本；插件升级、撤销权限、取消、重启和恢复都具有明确且可测试的语义。
- 上游升级只需先验证 adapter/插件兼容矩阵，不在业务插件散布私有 API 依赖。
