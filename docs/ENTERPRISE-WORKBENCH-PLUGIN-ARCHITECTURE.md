# 企业 DSH 多插件工作台：架构设计方案

状态：**实施方案 v1.0**。以已评审的 v0.3（`821850ec`）为架构基线，按 §5 施工、按 §6 验收。本文交付的是开发、迁移和切换方案，不是功能已上线的证明。除锁定上游契约冲突、可复现失败或明确的产品边界变更外，不重开选型。本文细化[多插件总架构](ENTERPRISE-MULTI-PLUGIN-ARCHITECTURE.md)在工作台上的落地，沿用[应用发布合同](PLATFORM-APPLICATION-RELEASE-CONTRACT.md)、[运行合同](PLATFORM-RUN-LIFECYCLE-CONTRACT.md)与[开发规范](DSH-PLUGIN-DEVELOPMENT-STANDARD.md)。[社区调研](DSH-COMMUNITY-WORKBENCH-RESEARCH-2026-11-19.md)仅作为参考；本方案优先于该调研里的实施建议，不取代现行合同。

## 1. 选型：一个原生工作台，应用按发布注册，能力由业务插件提供

**不为每个业务插件再建页面壳。** 保留 `platform-workbench` 作为唯一员工工作台 DSH 插件；把新增业务入口做成发布数据，而不是前端新增路由或注册 React 组件。平台拥有渲染器和入口；业务插件拥有专业工具、资料语义和验证器；控制面拥有业务记录、运行和发布事实。应用与插件不是一对一：一项应用可以组合多种能力，公共能力默认不占用员工导航。无需因插件数量拆成微服务。

借鉴 philomelcc 的薄壳与版本化边界、better-sidebar 的扩展点一致性、ityyq777 的公共服务，以及 worktable 对“运行结束”的诚实投影。**不照搬**第三方运行时服务、任意组件注册、分栏引擎、会话镜像库或模型生成组件。独立应用不是运行入口。

| 层 | 所有者 | 职责及边界 |
|---|---|---|
| DSH 原生会话 | 锁定 DSH 宿主 | 会话、流式消息、输入框、队列、停止、原生问答与工具呈现；工作台不复制事件日志，不实现第二个 Chat |
| 工作台壳与渲染 | `platform-workbench` | 固定导航和条目布局、通用表单、三指针、右栏投影、键盘与 i18n；只消费控制面查询与批准的声明，不执行业务计算 |
| 平台控制面 | `platform-control` | 目录和发布、Work、会话绑定、Run、交付及复核；UI 与代理的通用业务动作最终走同一服务及服务端权限，控制主进程不加载领域实现 |
| 装配与执行 | `platform-runtime` + 现有 Worker 边界 | 发布时解析确定的能力提供者与执行计划；运行端按已有合同核对计划、授权、输入和产出；不靠 UI 决定执行权限 |
| 业务与知识 | `plugins/*`、`platform-knowledge` | 业务包提供 DSH 工具、Skill、领域验证与贡献数据；知识服务管理共用机制，业务包之间不引用源码 |
| 企业身份与数据 | IT/API/执行环境 | 授权、数据与密钥、执行隔离。UI 显示可用性，不能充当授权边界；不恢复按名称拒读或普通开发额外审批，领域专属边界不变 |

## 2. 员工界面及导航规则

| 视图 | 布局与行为 |
|---|---|
| 工作台首页 / 待处理 | 按服务端给出的事实展示：待回复、待复核、需要对账等；卡片跳转到对应 Work 或原生会话。不给“会话结束”显示成功样式，不调用模型来生成系统状态 |
| 应用目录 | 固定导航项下按授权列出应用，支持搜索；应用入口由发布登记投影，不给每个应用加一个侧栏按钮。详情和创建表单按批准描述渲染 |
| 工作页 | 左侧是工作导航；**中心始终是该 Work 绑定的 DSH 原生会话**；**运行记录只在右栏**。右栏公共区域显示输入、执行、结果与复核；点选历史 Run 只换右栏上下文，不替换会话，不向模型发送消息 |
| 历史会话 | 展示原生会话目录，能恢复获准会话。未绑定的普通会话不伪装成 Work；不从聊天文本反推归属 |

首期只允许领域贡献出现在公共表单、右栏或产物预览位置。窄屏右栏可收起，不占用中心的会话生命周期。恢复坐标只保存可重新校验的 ID；切换或刷新后重新校验 Work、Run、会话关系和权限。不存在、撤权与数据加载失败明确区分，不展示上一个 Work 的残留。

**DSH 接入依据。** 现有 [Client 入口](../packages/platform-workbench/src/client/index.ts) 使用 `slots` / `layout` 和自持 Session 引用；[上游 UI Session 文档](../upstream/deepseek-harness-git/packages/client/ui-session/README.md)描述显式 Session 引用，[Conversation 文档](../upstream/deepseek-harness-git/packages/client/ui-conversation/README.md)明确 `conversation.content` 继承渲染位置的 Session。沿用锁定 `0.2.2-rc.1` 的显式作用域，不争夺宿主主会话，不增加 DOM 寻位、iframe 或私有 API。升级另做兼容验证。

## 3. 发布合同里的 UI 贡献：首期最小版本

扩展已有 `ApplicationRelease → ViewContribution` 关系，**不新建第二个注册中心**。以下为拟议字段与语义，不是当前 API：

| 内容 | 首期约定 |
|---|---|
| 身份与版本 | 以批准的 `appId + appReleaseId` 解析；`viewContractVersion` 选择解析规则，`viewDigest` 固定声明内容。用户和客户端不自行选择 digest 或提供者 |
| 创建表单 | 使用发布合同里的参数 schema、资料角色；可声明字段顺序、分组、说明和平台允许的控件提示，不另定义一份业务校验。服务端以批准 schema 重验提交 |
| 右栏与预览 | 可声明有限数量的展示块：描述/键值、工件列表或受支持的预览提示。数据源只引用平台已授权返回的运行事实、检查回执和工件摘要；不提交路径、查询、脚本、远端 URL 或任意 HTML |
| 动作 | 仅引用平台已有的动作类别，例如打开获准会话、下载工件、请求复核。动作是否显示以服务端授予的能力为准，真正执行时再授权；业务声明不可注册任意写入处理器 |
| 可选与失败 | 无贡献或不支持其版本：展示通用视图、明确说明。可选富视图不可用不影响原生 Chat；如果通用表单无法正确承载必需参数，只能只读或停用该创建入口，不假装提交成功。非法贡献不得发布 |

### R1 · 发布与视图身份（发布脚本 / `platform-control` / `platform-runtime`）

- `appReleaseId` 在本文指现有 `(appId, appVersion, releaseDigest)`，不是新上传 ID。发布装配与 `verify-applications.mjs` 使用同一份清单转换实现：业务清单 → 规范化发布描述、参数 schema、资料角色和可选视图 → 发布预检。不能由两个脚本分别挑字段。
- 应用版本、能力版本与插件包版本各自独立；共用转换显式输出三者及映射，不以包版本代填其他版本。先对规范化 `ExecutionPlan` 正文计算 `planDigest`，固定 `appId`、`appVersion`、描述符摘要、能力到确切包版本与摘要的映射、输入 schema 和资料角色合同的版本与摘要、`viewContractVersion` 与 `viewDigest`（无视图明确记为无）。计划正文不含自身摘要或含 `releaseDigest` 的完整 `appReleaseId`。再按发布合同从描述符、`planDigest` 及适用的构建来源算 `releaseDigest`；发布封套单独核对计划归属及两级摘要，批准绑定 `releaseDigest`。Worker 校验执行所用输入合同，不加载视图；控制面与客户端只消费与批准发布匹配的视图。改动 schema、角色或视图必须新发版。历史发布按原记录的格式重算摘要，不补写摘要、不冒充新合同发布。
- 预检校验字段、类型、大小、渲染器支持、动作和资源引用，不执行插件提交的代码。系统导航、原生会话座席不是业务扩展点。缺少或不支持可选贡献时给通用视图；摘要不匹配不渲染该声明并报告完整性异常。不能正确承载必需输入时禁止提交，但不把合法历史内容变为不可读。专业前端模块不纳入首期。

### R2 · 员工目录与项目授权（`platform-control` / `platform-workbench`）

- 员工目录按所选项目服务端过滤，返回**当前默认、已批准且允许在该项目创建 Work 的发布**分页摘要（身份、名称、简介、可用状态），不随首页下发完整描述符。筛选发生在分页前；选中后以项目和预期发布身份取完整声明。`ACTIVE` 只是登记状态，不是批准事实；环境或模型暂不可用须如实说明，不宣称可执行。管理目录和历史查询不借用员工准入条件。
- 所有员工可达的 Work、Run、历史视图、交互、成果和复核查询或写入，服务端按权威归属解析项目、工作及资源关系后授权；不得从浏览器参数推定归属，也不得因缺少 workspace 就跳过 Work 的项目。列表、搜索、恢复和直接请求一致；未授权不返回元数据、摘要、状态或缓存，拒绝原因不得暴露对象是否存在。工作台只消费服务端结果，不是授权边界。

### R3 · 从表单到冻结输入（`platform-workbench` / `platform-control` / Worker）

- Work 创建保存项目、工作区、应用发布和目标等业务上下文，不把运行参数隐式取自 Work 元数据。创建请求携带所见发布身份作为前置条件；服务端按当前准入选择发布并重验授权，身份不一致时返回冲突，刷新确认后再提交，不写 Work。运行表单使用该 Work 已绑定发布；提交时比对绑定与所见身份并重验执行资格，不能用目录最新值覆盖。
- 首期参数 schema 支持封闭对象、标量、枚举、必填及长度/数值限额；默认值若有，由批准 schema 明示、服务端应用。资料角色独立声明允许的角色和基数；提交用 `roleId + materialVersionRef`，由服务端授权解析到当前项目的不可变资料版本与摘要，不接受浏览器路径或自报摘要作为权威。不支持的必需 schema 阻止该发布进入员工准入。
- 发起运行或换批时，服务端验证并固化参数、已解析资料版本和运行目标，生成不可变输入修订及摘要；Run 和调度意图绑定该修订与批准的执行计划，同事务写入。派发只消费该已冻结修订，校验归属、发布和摘要，不重新读表单或解析可变的“最新批次”。失败不创建 Run 或派发。Listing 按批准枚举保留 `applicationOptions.listingType` 四类；DVP 的 schema 不声明也不接受该字段。

## 4. 主链路、状态与隔离

### R4 · 同页操作与历史读取（`platform-workbench` / `platform-control`）

- 打开活动 Work 后，详情、运行选择、成果预览和待答入口共用工作页右栏；待处理深链接打开同一工作页并定位对应 Run/请求。右栏切换、收起与恢复不改变中央 Session 引用；选择历史 Run 不发消息或重跑。已有“查看详情”不再为这些操作卸载原生 Chat。
- 原生 Chat 的问答由 DSH 处理；Worker 的 root session 属于其 Run，不替换 Work 的中心会话。Worker 问题经右栏或获准待办提交至现有 Run 交互接口；服务端按 Run、launch epoch、Session、requestId、当前授权及待答状态以 CAS 接纳答复。接纳只证明答复已记录，不证明引擎已收到；只有可核实的引擎回执才标记已接收。投递结局不明时显示未知，按运行合同对账，不自动重投。历史选择不能改变答复目标，过期、重复、终态或已撤权请求不投递。普通聊天不构成答复或受控 Run；会话结束不推断 Run 成功。
- 发布仅退出默认目录不等于安全撤权，也不使既有 Work 或在途 Run 自动只读。仍获准的在途待答可从工作页右栏或运行待办继续处理；若中心会话不可用，Worker 待办可以独立处理，不借用或创建会话，也不把执行动作混入历史只读入口。原生 Host 的会话授权和集中部署下非 owner 的原生问答能力须独立验收，不以 Worker 答复通道代证。
- 会话缺失或工作归档时，仍有权访问的历史记录可走独立的只读入口：不创建、不 retain、不恢复任何会话，不提供执行动作。以选定 Run 冻结的发布身份解析批准视图，不经当前目录或 `resolveWorkContext` 的启动准入；视图不可用则显示通用事实与获准成果。访问仍遵守 R2 和安全撤权策略。

### R5 · 复核绑定具体成果（`platform-control` / `platform-workbench`）

- 复用现有复核记录和 CAS 决策。新复核在请求时由服务端从指定成功 Run 已封存的工件构造不可变清单，固定工件修订标识及摘要，保存 `runId + manifestDigest` 与清单引用；没有可验证封存事实不得发起成果复核。清单摘要不包含复核状态，避免与现有交付包的复核快照形成循环依赖。
- 决策绑定该请求的目标摘要与预期复核修订；服务端再次核对授权、目标与待决状态。新 Run 或不同成果清单不继承通过决定；旧的仅绑定 Run 的记录照常可查，标为“未绑定具体成果版本”。交付包只为相同清单展示对应复核结论，保留封存时快照与当前决定的区别。
- “执行成功”“成果已封存”“复核通过/退回/未发起”独立显示；复核只按适用领域合同触发，不改 Run 终态，不扩大模型审批权，不新增普通读取或开发审批。

### R6 · 默认发布切换与安全撤权（发布责任人 / `platform-control` / Worker）

- 复用发布登记，为新 Work 保存可审计的默认发布指向；切换或普通回退前核对批准状态、目标制品及服务端/客户端契约兼容，用期望指向防止并发覆盖。仅改变新 Work 准入，不用现有会撤销来源版本的操作模拟普通回退。既有 Work 发起新 Run 时按原绑定重验批准、当前授权与原制品可用性；退出默认目录不是拒绝条件，也不能借此换版。已接纳 Run（含排队、执行中和待答）继续使用原锁和制品直至排空。原制品不可用则显式阻断接纳、派发或恢复，保留事实，不另起替代执行。
- 安全撤权独立执行，仍按现行合同拒绝新授权、处理在途停止并如实记录未知状态；不因回退重新启用已撤权版本。历史读取不改写发布绑定，按 R4 及当下授权处理。
- 回退演练先用新版本创建 Work、接纳 Run 并写入记录，再切默认发布。验证新 Work 路由、旧 Work 与在途 Run 的原绑定、历史读取、旧制品缺失阻断，以及安全撤权不被回退绕过。回退不降级数据库、不改写历史记录、不删除数据。

## 5. 开发、迁移与切换手册

**首个交付是可运行的纵向切片**：隔离 profile 内，一个无可选视图的合成发布从授权目录进入 → 创建 Work 并打开原生 Chat → 从右栏发起 Run → Worker 接收冻结输入 → 右栏呈现真实运行与封存成果。闭环通过后才迁 Listing、DVP。实现前以同一 checkout 固定源码、依赖与 DSH `0.2.2-rc.1 @ fcc0ad46`，记录合成夹具、制品摘要和基线失败。当前控制面、工作台、两个业务清单均有未提交变更；开工前逐包确认写入负责人和接手点，不覆盖、不清理非本任务改动。

### 5.1 施工任务与出口

| 工作包 / 依赖 | 修改落点与交付接口 | 进入下一阶段的证据 |
|---|---|---|
| W1 发布装配 / 无 | `platform-runtime/src/plan.ts` 负责版本化计划摘要；`platform-control/src/registry.ts` 校验发布封套与批准，保留历史摘要验算；`scripts/workbench-deployment.cjs` 与 `scripts/verify-applications.mjs` 共用发布描述转换。发布声明由应用提供；公共逻辑不引用业务包。 | 新旧格式夹具均可重验；三种版本不相等仍可装配；任一受控字段变化导致原批准失效（R1）。 |
| W2 员工入口与默认路由 / W1 | `platform-control/src/migration.ts`、`store.ts`、`service.ts`、`http.ts`：在既有数据库保存每应用默认发布指向及修订；增加项目范围的目录摘要与选中发布详情读接口，在员工 `/api/workbench` 不再下发完整声明。Work 创建原子比较预期发布，过期返回冲突；项目权限从服务端资源归属解析，在分页、搜索和直达前执行。管理回退与安全撤权不共用写入动作。 | 两项目双身份、无 workspace 和跨页查询测试通过；并发切换时旧表单不创建 Work；撤权版不能选为默认（R2、R6）。 |
| W3 冻结输入与执行 / W2 | `platform-control/src/service.ts`、`input-baselines.ts`、`runs.ts`：现有 Run 创建与换批入口收敛到同一服务端校验/冻结操作；事务内写输入修订、Run、outbox。`scheduler.ts`、`worker.ts`：按 Run 的 `runtimeBundleDigest` 选择已登记的确切制品，复用现有监督器，不按默认应用版本选 Worker；无匹配执行器时不启动、不换版。 | 检查实际 Worker 接收的输入及摘要，而非仅检查请求或数据库；重复提交不产生第二次派发；两个不同制品能按原锁排空，缺制品可见且未启动（R3、R6）。 |
| W4 成果复核 / W3 | `platform-control/src/store.ts`、`service.ts`、`http.ts`：现有复核请求写入服务端封存清单引用和摘要；决定调用校验同一目标、修订和当前授权；交付投影只关联匹配目标的复核。旧记录只显示既有事实。 | 对不同清单不继承通过；并发决定只生效一次；审计可从决定回查具体工件摘要（R5）。 |
| W5 工作台纵向切片 / W2–W4 | 保留 `platform-workbench/src/client/index.ts` 的显式 Session 挂载。`src/client/WorkbenchPage.tsx` 将 `WorkDetail` 的启动、问答、成果和复核移入 `WorkConsole` 的右栏；`src/api.ts` 接入获准目录与可选声明。把历史只读入口与运行待办分开，移除活动工作“查看详情”时清空 Session 的路径。 | 合成应用闭环；锁定宿主在生成中切 Run、开详情、收右栏仍持续流式；刷新恢复同 ID；Worker 问题由原 Run 通道处理（R4）。 |
| W6 迁移业务与演练 / W5 | `plugins/dm-listing/application.json`、`plugins/dm-dvp/application.json` 按 W1 交付字段与结果声明；不改领域算法。覆盖 Listing 四类与 DVP 独立字段的实际派发，再移除被替代的专用渲染分支。最后以第三个合成应用、100 项混合目录和双制品运行回退验证扩展。 | 新应用零工作台源码改动，R1–R6 证据齐全；现有工件、会话、发布审批和历史审计均未重写。 |

### 5.2 数据迁移与上线顺序

1. **先做副本演练**：用现有备份能力保存控制库与封存工件，在隔离副本验证恢复；比较 Work/Run/复核行数、发布摘要、工件摘要及会话绑定。迁移只增加必需的字段或记录，按数据库迁移事务执行。历史发布按原格式验算；不为旧复核编造成果目标。默认指向由部署责任人从明确获准且制品可用的发布初始化；无有效选择则不开放新 Work，不猜版本。
2. **先部署制品，再打开入口**：构建并锁定平台及两个业务发布，按摘要登记可执行制品；隔离环境以同一最终制品完成 W6 和 §6。通过后由发布责任人在获准目标环境部署，再切换员工默认指向。入队/在途旧运行保留原执行制品直到排空；跨版本清理在确认无引用后按现行保留策略处理，不作为切换步骤。
3. **失败时按故障层处理**：新发布或业务表现异常，停止扩大范围，将默认指向切回上一获准、可用版本；已写入的新 Work/Run 按原绑定处理，禁止改库或改版本续跑。若是新平台界面/服务自身故障，停止新入口写入，只有上一个制品已验证能读取迁移后库才允许回退平台制品，否则保留只读或停机修复；绝不以恢复旧备份覆盖切换后已产生的记录。安全撤权仍走独立流程。

### 5.3 验收运行与证据交接

- 工程门禁：使用项目支持的 Node（工作台要求 `>=24.9.0`），在仓库根执行 `node scripts/check-development-standard.mjs` 和 `node scripts/verify-all.cjs`；按工作包补齐计划、登记、授权、输入、Worker、复核与 UI 回归测试。报告实际失败和跳过项，不能拿历史绿灯抵消。
- 宿主与 Worker：以 `scripts/native-workbench-deploy.cjs` 生成隔离部署描述，按锁定宿主运行；复用 `scripts/workbench-live-e2e.mjs`、`scripts/platform-worker-e2e.mjs` 的接线，补充本方案专用浏览器及双制品回退场景，不能把现有 smoke 当作 R4/R6 覆盖。使用合成或获准公开夹具，不引入生产凭据或临床正文。
- 每条 §6 记录制品/输入摘要、目标版本、用例、结果与脱敏证据路径。R3 留 Worker 实收证据；R4 留带同一 Session ID 的浏览器操作记录，证明生成未因右栏操作而中断；R6 留切换前后默认、队列、制品及停止事实。工程通过不代替业务和企业身份、撤权及部署验收；任一对应门禁未过，不切换真实员工入口。

## 6. 评审验收标准

| 用例 | 可观察结果 |
|---|---|
| R1 · 发布完整性 | 用三个不同的应用／能力／包版本验证显式映射；装配与校验对同一清单生成相同的两级摘要；封套串绑或单独改动 schema、角色、视图均不能复用原批准；旧记录按原格式核验；无可选视图时保留通用视图。 |
| R2 · 目录与权限 | 100 项混合发布中只分页返回获准项目的可创建应用摘要，不下发未选中视图；未批准发布不能创建 Work；直接访问、搜索和待处理不泄露未授权项目数据，包括无 workspace 的 Work。 |
| R3 · 输入闭环 | 提交前默认切换则旧表单创建冲突、无写入；非法参数或跨项目资料不产生 Run 或派发。断言持久化及实际派发：Listing 四类逐一匹配，DVP 无 Listing 字段，换批不改变已接纳的旧输入。 |
| R4 · 会话与右栏 | **锁定 DSH 宿主实时流式验收**：在原生 Chat 正在生成时打开详情、切换 Run、收起右栏；原生会话不卸载，流式消息及工具活动持续更新，不触发提交或重跑。刷新后重验权限并恢复同一 Session ID。默认切换后获准的在途 Worker 待答仍可处理；原生问答独立验收，答复登记不当作引擎接收，未知不自动重投，重复或过期不投递。历史入口不挂载会话，撤权不显示缓存。 |
| R5 · 成果复核 | 仅封存成果可请求复核；并发或目标不符的决定不生效；旧决定不适用于不同清单，历史记录可查；执行、封存及复核分别展示。 |
| R6 · 回退与撤权 | 用两个不同运行制品，先让新版本写入记录并产生排队、执行中或待答 Run，再切回默认：仅新 Work 路由改变；既有 Work 创建新 Run 按原绑定重验；已接纳 Run 按原锁执行或排空，历史成果不改绑定。原制品缺失时明确阻断；已撤权版本不能重新成为默认，停止未证实时不得报告已停止。 |
| 共通 · 扩展和验收 | 第三个合成应用不改工作台源码即可接入，无新全局入口。实现交付前需用锁定 DSH 隔离 profile 验证最终制品，并运行包检查与 `scripts/verify-all.cjs`；工程门禁不代替业务或企业部署验收。 |

**本期不纳入**：第三方市场安装、插件自绘 Chat、任意微前端、动态 GenUI、第二套调度与状态库、额外普通读取审批。它们不是扩展到上百业务插件的先决条件。
