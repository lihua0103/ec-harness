## 3. 直接复用的阻断点

### 3.1 认证协议不是现成 SSO

已检查的入口是 `/api/login`、`/api/refresh-token` 和当前用户接口。JWT helper 使用 HS256，登录 access payload 含 user_id/username/role_ids；在该发行/校验路径未见针对 DSH 的 audience/client/scope 约束。检索到的 client_credentials 是调用外部系统，不是本系统向桌面签发授权。

禁止把工时 JWT 密钥放入桌面或每个 DSH Worker；能够校验对称签名的一方也能签发令牌。DSH 不能只解码 JWT 就相信 role_ids。优先接入企业现有 IdP；没有 IdP 时采用成熟 OAuth/OIDC 服务并与现有用户目录集成。原工时登录可在过渡期继续服务原系统，DSH 新接入不继承其协议缺陷。

### 3.2 安全条件应先审查，不直接宣布源系统适合作为 IAM

以下是静态观察，不是已执行攻击或完整安全审计：
- `jwt_required` 与 `JWTAuthentication` 在读取的代码中没有显式拒绝 refresh 类型令牌用于资源访问；refresh/access 分离需要负向测试并修正不符合点。
- `web-font-end/src/utils/auth.ts:90-129` 的 token 写入由 JS 操作 Cookie，失败时写 localStorage；它们都不是 HttpOnly，不能防止有执行权限的页面脚本读取。源码中“防 XSS 直接读”的注释不能作为安全证据；不要照搬到桌面。
- `common/permissions.py:44-80` 的管理员判断按角色码命中；该分支未见 role.status 过滤，而普通按钮角色查询有状态过滤。管理员停用、撤销、岗位变更需跨全部入口测试；已核定的公司超级管理员映射为 DSH 全局管理员，不能接受未经校验的客户端 `ADMIN` 声明。
- refresh 使用记录目前先查询再标记；并发单次消费与存储故障行为需要专门测试，不能凭有 jti 就宣称防重放闭合。
- 权限逻辑有请求缓存、共享缓存和模块级缓存；角色/岗位/成员变更的一致失效和跨进程撤权时限尚需核验，不可承诺即时。
- `apps/system/services.py:167-199` 将登录成功与拥有角色/菜单关联。只需要 DSH 的用户不应被迫拥有工时页面；统一身份认证应与单个应用准入分离。
- `tests/test_permissions.py` 有接口测试，但部分路径允许 skip，SELF 用例主要检查本人出现，不能证明他人数据完全不可见。本轮未运行这些测试。

以上问题优先约束新增身份桥接的可信入口；不要求本轮未经授权改动整个工时系统。

### 3.3 超级管理员全局可见；普通角色保留范围

**用户已明确：公司级超级管理员能看所有。** 本方案据此设置 `dsh.super_admin`：在本企业平台内可查看所有项目、工作、会话、业务资料、成果、模型配置的非秘密信息及审计记录，不受普通项目成员范围过滤。该角色是显式支持的全局管理员，不是要求临时提权后才能查看。登录有效性、账号停用/撤销与审计仍适用。

工时平台目前将 `ADMIN`、`SUPER_ADMIN`、`pmadmin` 都视为其管理员码。接入时配置并测试 `source issuer + 受信角色码 → dsh.super_admin` 的映射；属于公司超级管理员的账号直接获得全局可见性，不再重复逐项目授权。哪些历史别名代表同一个超级管理员身份，在账号映射清单中核定，不能靠前端传入角色名称。普通部门/项目管理员不因名称含 admin 就自动提升。

对非超级管理员，“能看项目工时/预算”不等于“可读全部临床原始资料、向任意模型外发或下载全部成果”。`ALL/COMPANY/PROJECT_COMPANY` 是指定资源规则，不自动扩展其他资源；菜单通配符只通过已定义的服务端角色映射生效。`has_ai_access` 只是现有助手的角色准入，不代表 DSH 全部能力。

全局业务可见权不意味着提供密码/签名密钥/长期 token 明文，也不等于把全局权限下发给每个 Worker。超级管理员可通过平台授权的管理动作配置或轮换凭据；Agent Run 仍绑定本次实际项目/资料与操作授权，避免一次任务默认取得全公司数据。已有 DVP Cover/Approval 等插件领域合同不被本次角色设计悄然改写，平台管理员查看能力与领域插件处理规则分别实施。

组织 companyId 也不自动等于安全 tenantId；先确认单集团/多法人边界。使用 sourceSystem + immutable subject/project ID 建映射，工号、用户名、姓名、项目展示编码用于显示或辅助核对，不做唯一安全主键。用户注销/项目删除需要 tombstone，不能因 ID/名称重用继承历史授权。

## 4. 推荐架构与权威归属

```text
                     企业 IdP / 标准认证服务
                     系统浏览器登录 + PKCE
                              │
          ┌───────────────────┴────────────────────┐
          │                                        │
   原工时 Web 平台                          DSH 桌面应用（公共客户端）
   用户/组织/项目管理                       Renderer：工作画布、模型选择
          │                                 Main/本地代理：受限 IPC、凭据库
   Django 企业集成 facade                         │ TLS
   人员状态 / 成员关系 / 授权版本                   ▼
          └───────────────→ DSH 服务端控制面 / BFF
                            身份校验 + 项目/资源授权 + 模型/应用准入
                            Work/Run/成果/审计/运行授权
                                       │
                      ┌────────────────┴─────────────────┐
                      ▼                                  ▼
             中心受控 DSH Worker                 企业受管本地 Worker
             高敏感/无人值守任务                  本地 R/文件/交互任务
                      └────────────────┬─────────────────┘
                                       ▼
                     DSH profile/SDK + 公共能力 + 领域插件
                     数据 API / 受控文件授权 / 模型路由
```

| 对象 | 唯一权威来源 |
|---|---|
| 登录、凭证与认证会话 | 标准 IdP；工时系统不默认是现成 IdP |
| 人员/组织/项目成员事实 | 经业务确认后的工时平台（若上游 HR/项目系统才是权威，工时平台是其代理） |
| DSH 动作、应用/模型分配、成果共享策略 | DSH 授权模块；复用角色管理思想，但独立命名空间 |
| 数据文件/连接器读取与外发许可 | IT 数据 API 与执行环境合同；项目成员身份不是全部数据授权 |
| Work/Run、交互与成果证据 | DSH 平台控制面 |
| 原生会话、模型/工具活动 | DeepSeek Harness |
| 企业审计关联 | 各系统保留各自事件，按 correlationId 关联；不全量复制对话/临床内容 |

第一期 facade 可部署在现有 Django 单体内，无需抽微服务或迁移全部账户。DSH 服务端调用它；桌面不直接使用后台管理员 API 批量读取人员，不直连工时 SQL Server/Redis。

## 5. 三条整合路线的裁定

| 路线 | 裁定 |
|---|---|
| 复制工时认证/权限代码与数据库到 DSH/桌面 | 不推荐：双写、撤权漂移、Python/TS 耦合及共享密钥风险 |
| 桌面直接调用原登录，再把原 token/roles 用于所有 DSH 动作 | 不作为正式方案：受众、委托、撤权和权限语义不匹配 |
| 标准身份入口 + 工时事实 API + DSH 自己的资源级授权 | 推荐：复用已有人员/项目维护投入，又保留独立产品与执行边界 |

若无标准 IdP，迁移期间可设计服务端身份桥接，但必须通过一次性、绑定客户端/回调/PKCE 的授权流程及 audience-limited token exchange；不要用共享密码或服务端替用户保存工时密码冒充 SSO。认证服务选型是 S0 需要确认的前置条件，不在源码扫描后虚构现成端点。

## 6. 桌面技术与本地执行的真实边界

### 6.1 推荐演进

先保持正式 Web 工作台与平台 API 分离，增加桌面宿主。优先评估 Electron：当前 DSH 是 Node/TypeScript 运行生态，进程监督和 SDK 接入路径较直接。Tauri v2 可以作为替代，但仍需发行 Node/DSH sidecar、处理跨进程协议、安装和升级，不因壳更小就没有运行时成本。冻结选型前做 Windows POC；macOS/Linux 只有实际验收后才声明支持。

第一阶段桌面作为远程控制面的客户端，可先使用中心 Worker；本地 R/大文件确有需求时再开放受管本地 Worker。目标可支持混合执行，但每个 Run 明确绑定执行位置，禁止失败时静默把本地资料搬到服务器或换模型地区。

### 6.2 必要安全约束

- 桌面是 public client，不内置 client secret、数据库密码、JWT 签名秘密或共享模型主密钥。系统浏览器完成授权码 + PKCE；验证 state、回调匹配，OIDC 使用 nonce 等协议校验；不在嵌入网页中收集企业密码。
- Renderer 无直接 Node/命令执行能力；Electron 使用 contextIsolation、sandbox、禁 nodeIntegration、受限 preload/IPC；Tauri 使用显式 capabilities。IPC 校验调用来源、参数、对象归属，不能暴露任意 shell、任意路径读取或任意 URL 代理。
- access token 尽量仅主进程内存使用；refresh token/设备私钥进入 OS 凭据设施，不进入 localStorage、渲染器、日志或 DSH 子进程环境。OS 凭据库不等于能防同用户恶意代码或本机管理员。
- 本地代理只接受授权 IPC/受保护本地传输，loopback 不是身份认证；如使用 HTTP/WebSocket，仍需会话鉴别、Origin/Host、重放与 CSRF 等检查。
- 签名安装包、签名更新、版本兼容检查、受控升级/回退；权限扩展在新版本明确审查，不自动授予本地高权限。
- 本地 Worker 需要独立低权限执行身份/沙箱与网络文件边界；简单 child_process 继承桌面用户权限，不构成企业隔离。
- 本机管理员能修改软件、访问已落盘明文、绕过本地 UI；不能声称桌面客户端能绝对执行中央撤权。对不允许本地持有的资料，必须中心执行或 IT 提供受管数据环境。

### 6.3 模型与文件

本地 DSH 通过获准 adapter 调用企业模型网关/服务，或使用严格限定的短期模型凭据；网关承载认证、路由约束与计量，不重造 Agent loop。无可用短期凭据或经验证网关时，不把共享模型 key 发到所有桌面，采用中心 Worker。

“本地运行”只表示工具/代码运行位置，不表示没有外发：发给远程模型的 prompt、附件、工具结果仍发生网络传输。UI 应显示本次执行位置、模型路由/地区及资料使用范围。用户选本地目录不自动证明其属于企业项目数据授权；个人开发工作区与企业受控项目分开标记。

### 6.4 断网与撤权

首期默认在线企业模式。断网允许编辑明确标注的本地草稿，但不能新建需授权的企业 Run、刷新服务访问或发布成果。既有 Run 用有限有效期授权租约，恢复联网重新校验；超时执行受控停止，无法证实停止记 UNKNOWN。不要将缓存角色永久当成授权。

立即撤权与长期完全离线执行无法同时保证；若未来允许离线，只能明确限数据、动作、期限、存储和风险接受范围。删除用户角色无法收回已下载或已外发的数据，保留/删除按 IT 政策处理，不自动擦除用户文件。

## 7. 拟建集成合同（不是现有 API）

建议新增 `apps/enterprise_access/`（Django）作为独立 facade；名称在实施时可调整。接口版本化，不复用管理页返回值作为长期协议。

- `GET /integration/v1/me`：从已验证身份返回最小 subject、组织归属、账号状态、identityVersion；不接受客户端指定 actor。
- `GET /integration/v1/projects?cursor=...`：仅返回调用者可发现项目的稳定引用、名称、状态与带 projectId 的关系；过滤在分页/计数前完成。
- `POST /integration/v1/relationships/check`：经授权的 DSH 服务基于绑定用户上下文查询某项目关系；拒绝任意用户枚举和委托身份替换。
- `GET /integration/v1/changes?cursor=...`：持久增量变更，包括禁用、成员撤销、角色变更、删除 tombstone；支持签名/认证通知、游标补读和定期全量对账。

对 DSH 特有动作的最终 `authorize` 放在 DSH 控制面：动作码示例 `dsh.work.create`、`dsh.run.start`、`dsh.artifact.download`、`dsh.model.use`、`dsh.app.publish`；权限码独立于菜单路径/翻译文字。若将来企业统一权限中心成熟，再以同一合同迁出，第一期不重复建设两个权威授权服务。

对象至少包含：`ExternalIdentityBinding`、`ProjectBinding`、`ScopedRoleBinding`、`PolicyVersion`、`RunAuthorization`、`RevocationEvent`。账号绑定采用 issuer + subject 与源稳定 ID，不按同名/同邮箱自动合并。角色绑定带 scopeType/scopeId/effectiveAt/expiresAt/sourceRevision；受信的公司超级管理员角色按配置直接映射企业全局范围，其他角色按显式动作和范围映射，不要求超级管理员另行申请逐项目查看权限。

RunAuthorization 至少绑定 subject、project、run、execution node、app release、model selection、资源引用、有效期、策略版本、launch epoch 与唯一 grant ID。Worker 校验签名/受众/范围/有效期及回执重放，平台重试不用旧 grant；凭据与审批不进入 prompt。权限按执行点校验，不要求每一次正常工具调用远程询问人工。

当前 `PlatformPolicy.authorize` 是同步接口：远程事实查询必须在可信请求上下文建立时异步完成并绑定版本/期限，或系统性改为异步并更新全部调用者；不能 fire-and-forget 查询后先放行。列表需要存储层授权筛选，不能逐页后过滤而泄露总数或漏数据。Work/Run 的项目归属来自可信持久映射，旧记录无法确定归属时只读隔离并明确迁移，不自动归给当前登录人。

## 8. 详细实施工作包与出口

| 阶段 | 范围与负责人 | 交付/出口 |
|---|---|---|
| S0 权威与安全基线 | IT + 两平台负责人；只读核查认证、管理员判断、缓存与 refresh 并发 | 冻结账号/项目主键、身份源、角色映射、部署 OS、数据/模型地区和撤权 SLA；形成 ADR 与接口 schema；修复或隔离身份桥接阻断项 |
| S1 工时企业 facade | 工时后端负责人修改新增 facade、urls、变更 outbox 与专属测试；原业务 API 保持其合法行为 | me/项目/关系/增量合同；服务身份与用户委托区分；最小字段、版本、分页、限流、失败拒绝；不让 DSH 直读库 |
| S2 DSH 授权闭环 | DSH 身份/控制面负责人修改 platform-identity、policy/service/store/http 及查询测试 | 统一 Principal、项目资源范围、角色映射、列表过滤、模型/应用准入、审计、旧数据迁移；enterprise mode 无本地 fallback |
| S3 桌面在线切片 | 桌面负责人新增 apps/desktop；复用 enterprise-workbench UI 与冻结 API | 系统浏览器登录、PKCE、OS 凭据存储、最小 IPC、权限到期 UX；合成数据在中心 Worker 完成闭环，无密码/长期密钥进入 Renderer |
| S4 受管本地 Worker | Runtime + IT；独立执行节点/运行授权/进程监督 | 本地 R 与文件的真实权限隔离、模型网关/短期凭据、授权租约、签名 profile、取消与断网；无法隔离的资料仍中心执行 |
| S5 联调与可用性 | QA + 安全 + 业务 | 跨用户/项目、撤权、凭据失效、目录与事件隔离、故障恢复及多窗口测试；员工能识别执行地点、模型、共享范围与待办 |
| S6 受控试点与发布 | 发布/运维/业务 | 签名安装升级、灰度、回退、备份恢复、可观察性及适用业务批准；记录真实部署范围，不冒称所有平台/全球合规 |

S1/S2 合同冻结后可分不同仓库开发；同一 policy/service/store/worker 文件组只允许一个负责人。S3 先用冻结 API；S4 不阻塞中心执行模式试点，但本地执行功能必须单独通过门槛。没有用户请求不提交、推送、生产配置变更或迁移真实数据。

工期只能在 S0 后估算：已有组织/角色管理可节省重复建设，但标准认证、跨系统授权、桌面安全与本地隔离都是新增工作，不能按“复用登录接口，几天套壳”承诺。资源建议为工时后端、DSH 后端/runtime、桌面前端各一名负责人，IT/QA参与；按出口验收，不凭测试数量报完成率。

## 9. 验收矩阵

| ID | 必需事实 |
|---|---|
| A01 | 同一企业账号可进入工时和 DSH；DSH-only 用户不需工时菜单；没有复制密码 |
| A02 | 错 issuer/audience/过期/refresh 当 access/回调重放/PKCE 错误被拒；应用和服务令牌不可混用 |
| A03 | 公司超级管理员经受信映射后可查看所有项目/工作/会话/业务资料/成果/审计，无需逐项目成员资格；普通项目/部门管理员不能借别名提权。密码/签名密钥不明文外泄，禁用/撤销跨全部入口生效 |
| A04 | 非超级管理员在相同应用下不同项目互不可越权读写；列表计数、搜索、事件、下载、知识检索均隔离。超级管理员全局查看与普通成员隔离分别测试 |
| A05 | 工时项目可见但无资料 Grant 的用户不能读临床文件；普通已授权读取和 R 开发不新增审批 |
| A06 | 项目 PM 仅在对应项目有映射权；人员/项目改名、删除、ID重用不继承错误授权 |
| A07 | 排队期间撤权拒绝启动；在途撤权阻止新访问、收敛凭据与进程；超时/未知如实记录 |
| A08 | 变更事件丢失、重复、乱序与服务重启可按游标/版本对账；超过授权有效期不靠缓存放行 |
| A09 | 桌面 Renderer 无长期 token、共享 key 或任意 shell IPC；恶意页面不能调用本地代理 |
| A10 | 本地 Worker 无法读取兄弟项目/凭据库；退出、子进程、磁盘与网络边界在目标 OS 实测 |
| A11 | 模型主路由、子智能体及辅助调用不超出允许路由/预算；本地执行的模型外发范围可解释 |
| A12 | 断网、睡眠、重新登录、设备切换、账号切换不串草稿/缓存/运行，不自动恢复旧未知副作用 |
| A13 | 伪造/过期/重放 RunAuthorization 不启动任务；服务端不接受客户端自报成功或业务审核 |
| A14 | 安装包/更新签名、协议版本与回退实测；升级不会改变在途 Run 的冻结组合 |
| A15 | 原工时登录/角色/项目/报表回归通过；新 facade 不扩大历史数据可见性，未执行/skip 不计通过 |

测试使用隔离数据库、合成账号和项目；现有工时测试在确认配置完全不连接真实数据库前不得直接执行。跨系统集成、安全验收和业务验收分别记录。

## 10. 产品体验与管理整合

- 桌面普通用户只看到当前账号/项目、可用应用/模型、工作和成果；组织管理在原管理后台或受控管理入口，不把复杂权限表塞入工作画布。
- 服务端返回授权后的可执行动作与可公开的拒绝原因，UI只做投影；隐藏按钮不是安全措施。
- 工作“仅本人/项目共享”、结果与完整对话的区别、执行地点、离线状态、模型目录变更均明确显示。
- 元数据范围与资料读取范围分开呈现，不让“可见项目”误导用户认为全部资料可用。
- 可选工时业务插件后置：首期只读获准汇总/报告；未来填报或提交需要独立动作权限、幂等和操作回执。DSH Run 时长/token数不自动等于员工可计费工时。

## 11. 尚需确认的决策

1. 公司是否已有标准 IdP/SSO；工时用户/项目数据是否由 HR/D365 等上游权威系统同步。
2. 首期只 Windows 还是跨平台；是否有企业受管设备、低权限执行身份与软件签名设施。
3. 首期中心 Worker 可否满足需求；哪些资料必须留本地、哪些任务需本地 R/浏览器。
4. 工时项目与临床数据授权项目的对应关系，以及可见项目不等于资料全读的规则。
5. 撤权时限、允许离线范围、模型地区与费用策略、成果共享与审计保留。

这些输入不阻碍合成合同/原型研发，但会阻止对应企业功能被报告为可正式使用。
