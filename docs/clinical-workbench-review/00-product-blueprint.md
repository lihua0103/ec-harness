# 临床 AI 工作台：产品蓝图与架构决策补充

日期：2026-11-11 · 版本：0.1 · 状态：**产品建议／待业务评审；未批准开发**。

主文档：[需求规格](../CLINICAL-WORKBENCH-REQUIREMENTS.md) · [目标方案](../CLINICAL-WORKBENCH-SOLUTION.md) · [角色基线](../CLINICAL-ROLE-KNOWLEDGE-BASELINE.md) · [评审登记](../CLINICAL-WORKBENCH-REVIEW.md)。本目录由独立评审负责人维护，不另建一套相互竞争的需求权威。本文补充产品决策，获准后由主文档维护者整合，不默示覆盖现有 ADR 或开发规范。

## 1. 产品负责人应承担的定义

用户提供的页面反馈是发现问题的入口，不是全部需求。产品不能等待非产品专业用户穷举所有流程，也不能把技术人员能填写的表单当作临床员工能持续工作的系统。

**产品定位建议：面向临床项目团队、以持续工作和可追溯交付为中心的专业 AI 协作工作台。** DSH 是自主执行底座，临床插件提供专业能力，平台承载项目、资源版本、责任交接、运行事实和交付证据。

产品不替代 EDC、CTMS、eTMF、PV 或正式统计系统；它连接授权的事实和成果，帮助人员理解、开发、检查和协作。AI 助手生成的建议与原系统正式记录必须区别。初期不默认写回这些系统。

### 产品是否成立的判定

不是“能对话、能选模型、能跑一次”，而是员工能够：

- 找到自己的项目和已有工作，不从零描述重复背景。
- 确认当前资料、规则、代码、环境和执行地点。
- 让 AI 自主完成授权工作，必要时回答真正的业务问题。
- 分清执行完成、质量检查、业务复核、正式交付和接收。
- 在资料/需求改变、人员交接、设备掉线、应用升级之后继续工作，不覆盖历史、不继承错误结论。

**首个产品闭环以“同一项目同一工作跨两个数据批次完成两次交付”定义，而不是以首页完成定义。** DVP 方案修订和非 Listing 类合成应用检验共性；不把未开发部门场景包装成已有功能。

## 2. 全生命周期地图：平台支持工作，不代替公司流程

下列为访谈与验收的候选业务地图，不是公司已确认 SOP，也不是法规要求的统一流程。不同试验/外包范围可跳过不适用阶段；不能用地图强制 Agent 工具顺序。

| 业务阶段 | 团队要解决的工作 | 平台需要保留的关系 | 常见失败反例 |
|---|---|---|---|
| 项目入场与规划 | 项目归属、人员分工、范围/时点、方案和数据计划 | 企业项目引用、职责范围、目标和里程碑、版本化资料 | 相同项目名串资料；项目成员被当成全部资料授权 |
| 建库与准备 | 方案解释、采集结构、规则设计、DVP、测试与上线准备 | 方案→结构/规则→用例→测试结果；问题与决定 | 规则生成成功就标 UAT 完成；模板升级覆盖旧依据 |
| 执行与持续清理 | 新批数据、Listing、外部数据核对、问题处理、医学审阅 | 批次→程序→输出→稳定问题→责任人/反馈 | 每批新聊天；旧 issue 重复生成；少了记录就判已解决 |
| 变更管理 | 方案修订、ALS/结构漂移、程序修复、规则变更 | 变化事件→影响候选→人工裁定→受影响工作/成果 | 自动更新所有活动工作；只重跑程序却沿用旧审核 |
| 锁库准备与分析 | 未决项清单、数据切点、SAP/分析集、程序及独立检查 | 外部锁库事实引用、数据版本、分析目的/盲态、QC | 某 Run 绿色被解释为数据库锁定或分析批准 |
| 交付与归档 | 成果包、客户回评、修订、接收和保留 | 不可变交付清单、复核范围、接收回执、替代/撤回 | 下载成功被当接收确认；归档被当删除临床记录 |

项目状态由权威业务系统或获授权人员决定；平台只能汇总工作事实。自动汇总不得倒写“项目完成”“锁库完成”。

## 3. 三种工作模式，不把所有工作塞进聊天

| 模式 | 主要用户体验 | AI 的适当位置 |
|---|---|---|
| 探索与开发 | 描述目标、资料导航、代码/规则编辑、试运行、检查 | 自主理解、规划、编程、诊断和修复；允许有缺项的草稿 |
| 已有程序换批复跑 | 选择已有程序/规则基线与新批次；显示变化和本批检查 | 辅助解释变化、发现不兼容；不强迫重新生成程序 |
| 审阅与交付 | 并排版本、表格/证据定位、问题裁定、复核与交付包 | 帮助摘要、定位、影响分析；不能代签人员复核或编造接收 |

这些是应用贡献的工作方式，而非三套平台。复跑若声明“使用 C1 原程序”，实际执行就必须绑定 C1 摘要；AI 想改动时形成 C2 候选并展示，不把改后内容仍称 C1。是否需用户再次确认按已有任务意图与适用业务政策决定，不要求每次正常编码新增审批。

纯程序执行能力通过批准的应用执行合同及 DSH 能力复用；是否完全不发生模型请求需以执行路径证明，不能只靠 prompt 要求“别调用模型”。具体接口在锁定 DSH 契约核查后设计，不另外造通用 Agent loop。

## 4. 业务对象的最小完整集合

沿用主方案 Work/Run/Session 等对象，补充以下产品语义；名称不是已经上线的 API。

| 需要回答的问题 | 权威对象/关系 | 不应如何实现 |
|---|---|---|
| 谁需要什么、什么时候完成 | Work 目标、负责人、协作者、交接、可选里程碑引用 | 以最后发消息的人自动成为负责人 |
| 本次依据什么 | WorkBaselineRevision → 各资料/代码/规则版本 | 一个可变文件夹加一条 prompt |
| 谁在何处执行 | Run → 节点/工作区/发布/模型快照；LaunchAttempt | 单一“正在处理”状态隐藏执行位置 |
| AI 做过什么 | DSH 原生 Session 与事件引用 | 平台复制聊天作为第二套引擎权威 |
| 结果究竟是什么 | ArtifactRevision → 实际输入/代码/运行/检查证据 | 只保存可变临时文件链接 |
| 哪个问题仍需处理 | Issue → 多批观察、来源定位、决策、外部问题引用 | 每个批次按行号自动重建或关闭 |
| 哪条意见适用于哪版 | ReviewRecord → 精确对象/用途/范围/人员 | 一个 approved=true 跟随工作永久有效 |
| 什么真正交付了 | DeliveryPackage → 固定清单/摘要/收件对象/回执 | 把生成、封存、下载、发送、接收合成一个状态 |
| 历史经验能否用 | Knowledge 条目 → 来源、适用前提、验证、反例/撤回 | 把历史对话或临床正文默认加入公共知识 |

**Issue 与 Observation 必须分开。** 同一个跨批次问题可有多次观察；稳定匹配需要应用声明业务键、规则版本、对象范围和匹配依据。没有可靠键时只能推荐人工关联。B2 没观察到 B1 的问题，可能是数据缺失、范围改变或规则改变，不能自动关闭为已解决。

**ChangeImpact 是关联记录，不是第二套工作流引擎。** 输入版本改变时产生受影响对象候选，保留判断原因、已确认/未确认影响；实际重跑仍由 Work/Run 承担。避免提前建设任意 DAG 编排平台。

## 5. 持续工作和基线演进

推荐员工保持一项 Work，内部有不可变基线、多次 Run 和多份交付。三个指针必须分开：正在编辑的基线、最近运行结果、当前认可的交付版本。它们可能不同，不能统一称“最新”。

案例：W1 使用 B1/S1/C1 生成 A1，经适用检查与复核交付 D1。B2 到来后：

- 建 I2，引用 B2/S1 与起始代码 C1；D1 仍适用于 B1。
- R2 中若产生 C2，实际执行记录绑定 C2，不追溯修改启动时起始代码记录。
- A2 有本批新检查；C1 的历史程序复核可按明确范围引用，不自动批准 A2。
- R2 失败时 D1 仍是已认可历史交付；不能把它显示为 B2 的结果，也不能因为失败覆盖 D1。
- D2 经适用流程交付后，可成为当前认可版本；D1 保留，若发现旧逻辑缺陷则另记影响及撤回，不抹去历史。

普通运行不是永久占用 Worker。Work 可持续几个月；Run 在完成屏障后结算。后续 Run 以明确来源的上下文清单重建所需信息，不要求原引擎永不退出。聊天摘要用于导航，不能代替输入、裁定和成果的权威版本。

## 6. 数据与执行位置：推荐混合架构，分阶段验收

**推荐：中心控制面统一业务权威，受管执行节点按资料与工具条件选址。** 为本地研发/试点保留明确的单机开发模式；不是把个人电脑的 SQLite 直接称作多人企业服务。

- ProjectBinding 是企业项目；ResourceBinding/Revision 是资料来源与版本；ExecutionWorkspace 是某节点的目录；DSH home/profile 是引擎配置与会话存储。分别展示和配置。
- 浏览器选择文件不等于中心 Worker 可读员工目录；路径字符串不是文件传输，也不是授权。
- 员工从已配置的资料源和执行环境选择；专家可查真实路径。IT/管理员配置节点能力、数据接入、模型路由、凭据和保留策略。
- Run 独占写入区域，原始资料默认只读；同项目多个 Work 可以并行，但不得共享未版本化输出。首期同 Work 一个未结清 Run，UNKNOWN 未核对不能另起竞争执行。
- 内容固定采用不可变上传对象、源系统版本或受控快照；hash 只证明比对，不保证可重取和一致快照。高容量快照可用满足合同的存储能力，不强制每次复制所有数据。
- 本地运行可能向远程模型外发 prompt/工具结果。必须显示与执行节点不同的模型路由/区域事实；不伪称“本地模式数据不出电脑”。

**优先做受管节点的一个完整纵向切片，而不是同时开发多个桌面壳、多个云环境。** 若首批资料必须留本机且依赖本机 R，选受管 Windows 本地节点；若中心可提供授权资料与 R，则首期优先中心 Worker，降低离线/同步复杂度。此选择仅需要 IT 给出实际约束，不需要用户自行设计技术架构。

### 6.1 项目 → 工作空间 → 持续工作：实际目录工作模式

2026-11-11 用户补充：项目支持新建/未来企业系统对接入口；选择项目后选择工作空间。Listing 等插件依赖真实服务器项目目录及预置资料，每个项目的 Listing 必须保留历史。这是业务事实输入；以下具体对象和执行映射为待评审设计，不是现有功能。

**推荐关系：Project → ProjectWorkspace → Work → Run → 成果/检查/复核/交付。** 原生 Session 关联 Run；项目和工作空间可汇总所属工作的历史，但不能把不同权限的会话自动全量共享。

- **Project**：项目身份、名称、来源、人员与业务阶段。初期允许获授权人员新建平台项目，标明来源为平台创建；预留企业目录适配接口。未来接入外部项目按稳定 ID 显式绑定并保留原身份/历史，不能按同名自动合并。企业目录权威建立后，创建动作可以转为申请或外部创建，不维持两个无规则双写权威。
- **ProjectWorkspace（持久工作空间）**：隶属项目的业务工作环境，具有稳定 workspaceId、名称、资料根/受控资源引用、执行节点或节点池、程序/输出位置、权限及配置版本。可绑定已有服务器项目目录，不要求重新上传或迁移整个历史目录。一个项目可以有多个空间，一个空间可供多个兼容应用使用，不按插件硬编码一空间。
- **ExecutionWorkspace（单次执行目录）**：Run 在已选空间下获得的实际 cwd 与写入区域，不是员工每次重新配置的空间。平台解析授权数据挂载和路径映射；插件获取真实可访问的路径和工作上下文，不要求模型猜项目目录。
- **Work**：空间中的一项持续业务工作，例如“常规数据清理 Listing”；同一空间可有多项 Listing、DVP 或其他工作。改变工作空间不得静默移动在途执行或历史归属；跨空间迁移通过显式关联/迁移记录另行设计。

**范围不是提示词限制。** 工作空间提供清楚的工作上下文和执行环境授予的数据/写入范围，AI在该范围正常发现资料、分析、编程及纠错；不按文件名/类别加拒读，不要求人为工具步骤。cwd只是默认目录，不是安全边界；越界防护由服务端授权、真实路径解析、挂载/ACL或沙箱承担。已授权的额外资源可以显式挂载，不要求资料全塞进一个物理目录。

**服务器目录的接入：** 员工选择已登记空间，或获授权地登记新空间；部署侧验证执行身份可达、读写位置及所需R环境。既有服务器资料可直接获准引用/挂载，不默认复制。运行保存资料版本或可用快照与清单；源若可变且无法固定，明确复现限制，不能只保存路径就宣称输入已冻结。

正常模式将源资料、可编辑程序区和每次运行输出分开，防止多人重跑互相覆盖。默认推荐每Run独立cwd，通过受控映射呈现项目资料及所选程序快照；若某应用确实依赖既有目录布局，提供声明并测试的布局适配或独占写租约，不能未经验证改变相对路径，也不能仅靠锁一个平台对象允许两个进程改同一目录。平台不强制所有插件采用同一物理文件夹模板。

### 6.2 项目 Listing 历史不等于文件列表

项目页可按应用、空间、负责人、批次检索历史；进入工作后查看各次运行。至少关联：

| 历史事实 | 保存方式与边界 |
|---|---|
| 业务目标、需求和明确裁定 | 平台版本化工作/输入/决定；可追溯原始依据 |
| 数据批次、ALS、需求/模板、起始程序 | 输入基线和实际可取得的版本引用；保留原目录来源 |
| AI交互、工具执行 | DSH原生Session与受权投影，不另造聊天权威 |
| 实际执行程序、结果和日志 | Run关联不可变成果/证据；起始代码与最终代码分开 |
| 检查、人员复核、交付 | 绑定确切版本和用途，不随最新目录内容漂移 |
| 线下已有旧程序/结果 | 可登记为历史导入，注明来源、操作者、导入时间和未知字段；不伪造原模型、Run、QC或批准记录 |

目录改名、挂载点变化不改变workspaceId或历史业务身份。配置更新生成新修订，新Run采用新配置，旧Run仍显示当时的节点与位置。目录无法访问时历史元数据仍可查看，但内容下载是否可用如实说明；本地/服务器文件不自动等于已封存。

例：P001 → “DM服务器工作空间” → “常规清理Listing”。第一次B1/C1/R1交付D1；第二次回到同一工作，选B2并继承C1，创建R2，保留D1及其适用范围。若新批需改代码形成C2，登记实际执行C2与新结果；无需重新建项目、空间或丢弃前次会话来源。项目中其他Listing分别为其他Work，不混成一个无限聊天。

**员工路径：** 新建/选择项目 → 选择或登记工作空间 → 选择应用并新建/继续工作 → 确认本次资料与目标 → 执行与审阅。只有一个可用空间时可预选并显著显示，不增加无意义重复点击；返回原工作默认继承其空间，不让员工每次手输服务器路径。

**新增验收事实：** 同名不同节点目录不混用；两工作并发输出不覆盖；空间配置改版不改变旧Run；已授权服务器资料可读但源数据不被误覆盖；跨项目空间不能通过伪造ID使用；历史导入不冒充系统执行；换批后代码/检查/交付关联完整。上述均待实施与实际验收。

## 7. 交互信息架构与角色工作面

稳定入口建议：**我的工作、项目、应用中心、待我处理、成果与交付**；管理与运行诊断按权限进入。不要按每个插件增加顶层导航，也不要把所有部门做成互不相通的门户。

- **我的工作**：恢复工作、当前阻塞与负责人；非统计卡片墙。
- **项目空间**：项目阶段事实、资料版本、工作、交付、成员职责；不暴露与职责无关的临床明细。
- **工作主区**：目标/基线与本次变化；对话/活动、文件/代码、差异/问题、检查/复核、交付历史按任务进入。
- **待我处理**：区分业务澄清、原生授权、环境故障、复核、交接/回评。每项有对象、责任人、时点、后果；普通问题回答不等于权限批准。
- **项目管理视图**：按真实工作事实展示责任和阻塞；项目阶段/工时/计费不得从 token、运行时长或完成百分比臆造。
- **专家视图**：实际 cwd、资料来源、程序、stdout/stderr、session 关联、模型配置来源；员工不用输入 shell 才能操作。

空态需有责任归属：“无授权项目→项目管理员”“资料源不可达→资料/IT负责人”“Worker 离线→运行运维”“模型凭据失效→模型管理员”。按钮只能做实际可完成的事：不可运行时允许保存草稿，不暗示已经开始执行。

## 8. 企业运营是产品的一部分

### 8.1 交接与协作

Work 负责人、成果作者、复核人、接收人分别记录。转交不改历史作者；离职不删除项目成果；新成员只获得实际获准内容。完整会话和交付包可有不同共享范围，权限必须覆盖搜索、通知、事件流、导出与下载，不只是页面。

### 8.2 多层状态和时效

执行成功、检查通过、业务认可、已发送、已接收独立表达。派生进度必须可解释且基于可枚举的验收项，不生成虚假百分比。等待人员与环境失败分别计时；提醒不泄露敏感正文。安全性报告等法定时限由原责任体系承担，平台提醒不冒充正式提交。

### 8.3 成本与可靠性

按 Work/Run/实际模型路由归集可取得的用量，未知费用保持未知。预算规则可限制新启动或发出提醒，不静默切模型、地区或减少必须检查。用最小充分上下文、资料索引和来源引用减少成本；跨模型摘要要保留来源和不确定性。低成本模型不得自行给高风险业务结论盖章。

运行失联先对账，确认旧进程及副作用后恢复或重试。控制面不可用、设备睡眠、磁盘满、归档失败必须有可观察的真实状态，不能让新模型猜测任务已结束。

### 8.4 备份、归档与退出

控制库、原生 Session、输入/代码、工件分开规定保留与恢复。只上传目录清单不等于 Session 已备份；归档有完整性回执且需恢复演练。企业原生记录可原格式备份，不发展第二套可写聊天数据库。设备离线时可显示中心元数据，但应提示完整会话不可取及恢复限制。删除和保留遵循适用政策/保留义务，不能自动擦除源目录。

## 9. 专业知识如何沉淀

知识分四层：公开行业参考、公司经确认 SOP/模板、项目明确裁定、一次运行事实。不得相互自动升级。

建议条目至少有：问题/方法、来源、版本、适用条件、反例、领域负责人、验证范围、有效/撤回状态、使用该知识的 Run 引用。临床资料和聊天不默认进入跨项目库。个别项目成功只证明该次实证，不证明其他项目的阈值、访视窗口、编码或输出样式正确。

专业 AI 可以研究和提出反例，但不是实际 DM/统计/医学人员。评审席位必须标 AI 预审或真实人员确认，不能用多个模型互相同意替代独立业务预期。

## 10. 产品决策与验证路线

### 已给出推荐，不把设计任务退还用户

1. 项目中心的持续 Work + 版本化基线 + 多 Run + 独立交付，不以聊天作为唯一业务对象。
2. 中心控制权威 + 受管节点执行，不另造 DSH 引擎。
3. 先闭合 Listing 两批交付，再用 DVP 修订及第三类应用检验扩展，不一次造齐所有部门插件。
4. 优先资料版本、模型/执行就绪和连续性，再做主题和视觉精修。
5. 通过明确的角色案例评审，而不是要求用户写整份需求或对架构图笼统说“通过”。

### 仍须取得的公司事实，而非让用户作技术设计

DBD/CO 全称与职责；首批资料/工具部署约束；企业项目权威接口；适用 QC/复核/交付制度；模型路由及外发区域；保留与恢复目标；管理员全局可见与试验盲态的适用冲突。

预审建议可立即用于文档修订；**实施仍须当前切片相关真实角色评审、阻断项闭合和用户授权**。普通已授权读取、R 开发和 AI 自主纠错不新增逐步审批。
