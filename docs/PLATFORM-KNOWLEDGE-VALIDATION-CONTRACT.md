# 平台跨进程知识验证合同

设计版本：0.2 · 2026-11-10。类型：架构参考。状态：目标合同，未实现或验证。覆盖架构评审 3。上层：[多插件总架构](ENTERPRISE-MULTI-PLUGIN-ARCHITECTURE.md)；执行环境沿用[应用发布合同](PLATFORM-APPLICATION-RELEASE-CONTRACT.md)。

> **2026-11-11 局部实现**：单进程 `KnowledgeService` 已加入 `claims`/`coverage` 语义：固定用例通过只写
> `TOOL_REGRESSION_ONLY` 回执；仅当候选声明的全部 claims 被已安装套件覆盖且通过才 `ACTIVE`
> （`CONTENT_CLAIMS`）。这修正了“函数测试通过即整条知识已验证”的错误结论，但仍是进程内实现；
> 下文的跨进程请求/回执、执行器身份与租约尚未实现。

## 1. 不把进程内函数当远程接口

现有 KnowledgeService.registerValidator 接收含 execute 函数的 ValidationSuite，DVP 等插件在 apply 中直接注册并调用。它是本机进程内接口，不能直接序列化成 RPC，也不能把所有验证器 import 进平台控制主进程。

保留已有知识 schema、版本、来源和候选激活规则；跨进程接入新增服务适配，不重建独立经验库。已有单机实现保持可用，未经迁移不得把当前数据存储切到新路径或开始双写。

## 2. 职责与可信来源

| 组件 | 负责 |
|---|---|
| 中心 KnowledgeService | 唯一可写知识状态、检索授权、种子版本、验证请求、回执核验、CAS 激活和审计 |
| 验证器目录 | 纯数据声明：validatorId/version、实现制品摘要、caseSetDigest、覆盖知识类型/ID、schema 和兼容运行集合 |
| ValidationExecutor | 独立受控验证执行域内运行已批准代码与固定测试集，不能由用户/模型动态提供 execute 或测试 expected |
| 普通 Agent Worker | 通过授权代理检索/提交候选/请求验证，无直接激活权限，无任意回执写入权 |

现有 registerContribution 的分类、别名、种子是数据贡献，可由发布流程幂等导入。现有 registerValidator 的可执行部分留在批准的验证执行器内，由注册目录引用；客户端不得上传函数、模块路径或任意测试用例取代发布集。

执行验证的身份与普通模型工具结果通道分离。平台调度签发与 requestId、执行摘要、epoch 和执行实例绑定的一次性回执权限；模型看到的工具结果只是投影，不能自行发布有效 receipt。具体采用内部认证、短期凭据或签名回执由部署实现，但仅凭 JSON 中的 workerId、passed 字段或哈希不是身份认证。

## 3. ValidationRequest

请求最少绑定：

- requestId / idempotencyKey；actor 和经服务端派生的 project/plugin scope。
- knowledgeId、candidateRevision、candidateDigest；批准的知识快照引用。
- validatorId、validatorVersion、validatorArtifactDigest。
- caseSetVersion、caseSetDigest；输入/结果 schemaVersion。
- executionPlanDigest、runtimeBundleDigest、执行身份与租约 epoch。

中心选择候选对应的批准验证器，不采用“目录里最新的同名验证器”。发布声明覆盖范围不匹配则返回“不支持验证”，候选保持原状态；没有覆盖用例不能用空集全通过。

验证运行使用只读候选和已发布固定测试集。允许并存不同版本验证器和运行环境；相同名称不意味着相同实现。验证器缺依赖、启动失败、超时或结果未知均不激活。

## 4. ValidationReceipt 与状态提交

回执由验证执行器经授权通道提交，包含请求绑定字段、逐项测试结果、实际用例清单、运行开始/结束与退出事实、日志引用、观测结果摘要。passed 仅是汇总提示，中心根据完整覆盖、结果 schema、测试结局和绑定一致性重新判断。

中心接收时依次验证：

1. 请求存在且仍待结算；来源执行身份、epoch、一次性回执权限与已分配执行实例相符。
2. candidate、validator artifact、case set、plan/bundle 等摘要与原请求完全一致；没有缺项、重复 case 或未知替代套件。
3. 测试集非空，按批准合同覆盖必需的正/反/边界用例；全部用例有实际执行结果且通过。运行异常或未执行项不能转成通过。
4. 事务内重新读取候选当前修订与状态；仅当前仍是匹配的技术知识 CANDIDATE 时可写验证记录并条件激活。候选已变更、撤回或替换则只留 stale 回执，不激活新版本。
5. 重复提交同一有效回执返回既有结算，不能二次转换；不同内容的同 ID 回执报冲突。

原始失败、过期和未知回执也保留，不为了维持绿色状态删除证据。project_decision 不因技术验证器通过而自动升级为跨项目方法；业务裁定范围与技术验证分别处理。

## 5. 检索与快照

浏览器、模型或插件提交的 projectId/pluginId 不是授权。中心从执行身份与任务上下文派生允许 scope，再在数据查询前过滤；shared 不等于允许任意 worker 写入。发布种子、项目裁定、技术候选各有写权限。

Run 使用的知识修订集合和摘要在输入上下文中记录。验证期间新知识激活，不静默替换当前 Run 的知识快照；需要使用时登记新输入/上下文修订。知识候选可被明确查看，但不冒充已验证的方法。

## 6. 迁移与失败处理

1. 先把客户端依赖从具体 KnowledgeService 类收敛到可替换的公开接口，保留本地适配，不改已有业务含义。
2. 建立中心服务与远程代理，验证 registerContribution 的纯数据导入与执行验证的请求/回执协议。
3. 迁移采用单一写入所有者、停写窗口、备份、摘要核对和版本映射；切换前验证新旧检索及状态一致。不同时维护两个独立可写权威库。
4. 失败回退到经过验证的原写入所有者，不直接在两个库间合并状态。若无法保证迁移结局，停止写入并对账，不假报经验已同步。

首期可以让一个中心进程拥有现有 SQLite；数据库接口与执行器分开后，再按实际部署决定是否迁移持久层。不要让独立 worker 直接挂载同一可写 SQLite 文件。

## 7. 验收

| 编号 | 场景 | 期望 |
|---|---|---|
| K01 | 应用旧/新版本并存 | 各使用请求锁定的验证器和用例，不默认最新 |
| K02 | 模型提交 passed=true / 伪造 workerId | 无验证器通道身份和请求绑定，不激活 |
| K03 | 空集、缺用例、未执行、未知退出 | 候选不激活，记录实际失败/未知 |
| K04 | 验证中候选修改/撤销 | 留 stale 回执，不激活新修订 |
| K05 | 重复回执、同 ID 不同内容 | 前者幂等，后者冲突 |
| K06 | 项目越权检索或验证 | 查询/派发前拒绝，不向 worker 泄露候选内容 |
| K07 | 验证器崩溃/阻塞 | 只影响该验证任务，中心服务可用 |
| K08 | 单机到中心迁移与回退 | 唯一写入者、无静默丢失/重复激活，可实际恢复 |

此合同没有声称现有验证集已经证明任意方法正文正确；每个验证器的覆盖范围、样本适用性与业务含义仍需独立评审。
