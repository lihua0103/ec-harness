# DM 视角的 DVP 实操经验（正常项目工作流）

更新：2026-11-10。本文是**行业通行实践的综合提炼**，与 [DVP-GENERATION-RESEARCH.md](DVP-GENERATION-RESEARCH.md)（已核验文献底稿）配套；文中比例、习惯做法属经验近似，公司 SOP 与模板冲突时以 SOP 为准。用途：作为 DSH DVP 插件要模仿的"老师傅流程"蓝本。

---

## 1. DVP 在项目时间线上的位置

| 阶段 | DM 在 DVP 上做什么 | 产出 |
|---|---|---|
| 方案定稿 | 精读方案，标注核查相关内容（终点表、入排、访视窗、安全参数、实验室分级标准） | 方案核查要点摘录（内部工作稿） |
| 数据库设计冻结初版 | 拿 aCRF/ALS，把方案要点落到具体表单/字段/变量名 | 字段映射清单 |
| DVP 初稿 | 主笔起草：标准库规则 + 方案特有规则 | DVP/DVS 草稿 v0.1 |
| 规则评审会 | DM lead、DB 编程、医学、统计、CRA 逐条过：逻辑对不对、文案会不会诱导、该不该做 | 评审记录 + v0.x 迭代 |
| EDC 配置/编程 | 程序员按 DVP 配置 check function；每条对应测试场景 | 已实现规则清单 |
| UAT | DM 出测试用例（正/反/边界），编程与 DM 双向执行，签字留档 | UAT 报告（pass/fail 签名表） |
| 首例入组（FPI）前 | 批准 v1.0 上线；给录入人员/研究者培训核查行为 | 批准版 DVP + 培训记录 |
| 运行期 | 监控触发率；方案 amendment 或 CRF 变更 → 增补规则走变更控制；运行中发现的系统性问题加新规则 | DVP v1.1/v2.0 + 变更记录 |
| 锁库（DBL）前 | 核查覆盖率确认、未关闭 query 清理、DVP 终版归档（连同变更控制列表、质疑表） | 归档包 |

经验要点：**DVP 不是一次性文件**。运行期新增的规则往往比初稿更值钱——它们来自真实数据暴露的问题。

## 2. 一条规则怎么"长"出来（贯穿示例）

以最常见的一条为例："随机化日期不得早于知情同意日期"。DM 实际的处理步骤：

1. **找方案依据**：方案 X.Y 节规定"知情同意后方可进行随机化"。记下章节/页码/方案版本——这条溯源将来写进 DVP。
2. **落到字段**：在 ALS 里确认变量名，如 `ICF.CONSDAT`、`DM.RANDDAT`；确认两个日期的类型（完整日期还是允许部分缺失）。
3. **定类型**：跨两张表 → back-end 批跑核查（不是录入时前端能做的）。
4. **写逻辑，重点是 null 处理**：任一日期缺失时不触发（另由"必填核查"管缺失）。`IF RANDDAT ≠ 缺 AND CONSDAT ≠ 缺 AND RANDDAT < CONSDAT THEN 质疑`。**null 处理没写清楚是误报第一大来源**。
5. **写质疑文案**：不透露"正确做法"，给支持值——"受试者 xxx 随机化日期（2026-03-05）早于知情同意日期（2026-03-07），请核实并更正或说明。"（不给"知情同意应在随机化之前"这种诱导句。）
6. **定触发方式**：EDC 保存后自动批跑 vs 每日夜间批跑 vs 周核查列表。跨表规则多为批跑；批跑频率影响 site 收到 query 的滞后。
7. **设计测试用例**：正常（RANDDAT > CONSDAT → 不触发）；应触发（RANDDAT < CONSDAT）；**边界（同一天 → 不触发，"不得早于"含等于）**；缺失一侧 → 不触发；两侧都缺失 → 不触发。每个用例记录期望结果，UAT 时执行签字。
8. **评审**：医学确认业务含义；统计确认随机化字段的分析用途（这条数据进不进分析集标记）；CRA 看现场负担。
9. **UAT 后转正**：草稿 → 实现验证通过 → 批准生效。
10. **上线后盯触发率**：如果这条规则在真实数据里月触发几十条且全是"确认无误"关闭，说明文案或逻辑有问题——要么改逻辑（比如日期录入习惯是当天补录），要么降级为周列表人工审阅。

**这条流程就是插件要自动化的骨架**：1→2 是"方案条款→字段映射"（需 ALS），3→7 是机械可生成的部分，8 是必须留给人审的。

## 3. 规则从哪来：标准库起步 + 方案特有

新项目 DVP 通常 60–70% 从标准模式库起步（经验值，非文献数据），30–40% 是方案特有。标准模式按类别：

**日期逻辑类**
- 先后链：知情同意 ≤ 筛选 ≤ 随机化/首次给药 ≤ 各访视 ≤ 退出 ≤ 结束
- 访视窗口：实际日期 vs 计划日期 ± N 天（N 来自方案，医学确认）
- 非法日期：2月30、未来日期（除非方案允许）、录入晚于事件日期过多

**必填/缺失类**
- 关键终点变量、安全性变量缺失
- 整页缺失（Missing CRF page）——按访视 Expected pages 逻辑

**范围/属性类**
- 生命体征、实验室值超合理范围（不是超参考范围——超出参考范围可能是真异常，只提示不强制）
- 数值属性：年龄 vs 出生日期一致性、体重身高与 BMI 计算

**交叉一致性类**
- 有 AE 无对应 CM；AE 起止与用药时间重叠
- 严重 AE：EDC SAE 表与 PV 库核对（外部一致性）
- 实验室异常（CTCAE ≥ 某级别）但无 AE 记录
- 妊娠检查阳性但性别=男 / 年龄段不符
- 随机化给药信息与实际用药记录不一致

**入排核对类**
- 排除标准阈值（如肌酐、QTcF、肝功能）与筛选期实测值比对
- 入选标准逐条勾选完整性

**状态流转类**
- 勾了"未做（NOT DONE）"但填了结果；未填结果又没勾未做原因
- 页面完成状态与数据存在性

**重复类**
- 同受试者同访视同表单重复录入；同 AE 重复报告

**方案特有**（举例）：剂量调整算法验证、随机分层因素与分层核对、特殊安全监测（QTc、Hy's law 肝袖查）、终点专属量表完整性（如某 PRO 量表条目）、local lab 与 central lab 分工场景。

## 4. 取舍判断：DM 怎么决定"这条做不做"

判断标准（按顺序过一遍）：

1. **关键性**：终点数据 > 安全数据 > 入排数据 > 一般数据。终点和安全必做，除非有明显理由。
2. **可程序化程度**：结构化字段做系统核查；自由文本（合并用药商品名备注、AE 描述）不做系统核查 → 转列表人工审阅。
3. **误报成本**：估计触发频率 × 每条 query 的处理成本（site 回答 + DM 关闭）。高频低值规则宁可不做或降级为列表。
4. **系统默认已有**：日期格式非法、字段类型、某些必填——EDC 本来就拦，不重复写进 DVP（写进去了也是冗余条目）。
5. **统计师输入**：分析集标记相关字段（如随机化、分层因素）的完整性由统计提出，优先级上调。
6. **医学裁定项**：实验室异常→AE 这类，规则只做"提示"，阈值和是否必须报 AE 由医学定，DVP 里注明例外条款。

## 5. 常见坑与对策（经验教训清单）

| 坑 | 典型后果 | 对策 |
|---|---|---|
| null 处理没写 | 一侧日期缺失时规则狂触发 | 每条逻辑显式写缺失分支 |
| 部分日期（UNK/年月） | 比较表达式报错或误判 | 逻辑里明确部分日期的处理（跳过/按年月比较） |
| 单位不统一 | 体重 kg/lb 混录范围误报 | 先做单位核查，范围核查基于标准化值 |
| 边界值没测 | "不得早于"在相等日误报 | 用例必须含"恰好等于"场景（含范围上下界） |
| 时区/闰年/月末 | 跨系统日期比较偏差 | 统一日期比较在单系统内做；跨系统传输日期用标准格式 |
| 窗口天数医学没确认 | 规则上线后医学不认 | 评审会上逐条确认数值，写进 DVP |
| 文案透露期望范围 | site 照抄范围改数（数据被"修正"而非核实） | 文案只描述不一致+给支持值，不给答案 |
| 规则互相打架 | 一条数据两条规则都触发，site 收两条 query | 评审时查规则间重叠；同一不一致合并为一条或注明触发顺序 |
| 方案 amendment 后没跟 | 新访视/新字段无核查覆盖 | amendment 流程绑定 DVP 影响评估这一步 |
| 反复触发已确认项 | site 每次保存又被 query 一次 | 例外条款："已关闭同一 query 的记录不再触发"（do not re-query） |
| 外部数据匹配键不一致 | SAE/PV 核对程序匹配不上 | DVP 明确核对键（受试者号+事件标识），传输协议里对齐 |
| 把"超参考范围"当错误 | 真实异常被反复质疑 | 参考范围超限只提示联动 AE，不作为数据错误 |

## 6. 输出物与审核链

正常项目的 DVP 相关交付物：

1. **DVP 主文档**（或 DMP 附件）：概述、职责分工（DM/监查/医学/统计）、核查方式分类、版本历史。
2. **DVS 规则明细表**：逐条 = Check ID/版本/表单/字段/系统或人工/类型/描述/逻辑/质疑文案/列表输出/补充说明/方案溯源。
3. **测试计划 + 用例 + UAT 记录**：正/反/边界用例、期望 vs 实际、执行人签名日期。
4. **变更控制记录**：每次增改的触发原因（amendment/运行发现/错误）、修改人、日期、批准。
5. **归档**：锁库时 DVP 终版 + 变更列表 + 质疑表汇总一起归档。

审核链：DM 起草 → 评审会（医学/统计/CRA/编程）→ UAT → 批准上线 → 运行期变更再走"评审→UAT→批准"。**每一步都有人名和日期，这是检查/稽查要看的东西。**

## 7. 对插件的映射提示

| DM 实操步骤 | 插件能力点 |
|---|---|
| 精读方案标注要点 | 方案解析 → 需求层候选清单（条款号+要求摘录） |
| ALS 字段映射 | 复用现有工作簿读取；候选映射歧义走 userQuestions |
| 标准库起步 | KnowledgeService `shared` scope 存通用规则模式（EDC 无关的业务逻辑层） |
| 单条规则生成（步骤 3–7） | 逻辑骨架 + null/部分日期分支默认补全 + 质疑文案模板（不透露范围）+ 测试用例自动生成（含恰边界） |
| 评审会 | 输出"待人工裁定项"清单（医学/统计/CRA 各自要确认什么），不代答 |
| UAT | 用例表可直接转 UAT 记录模板；插件不伪称测试已执行 |
| 触发率监控改进 | 运行期经验回填 KnowledgeService `project` scope；成熟后按知识库流程申请推广 |

一句话：**插件接管 2 里 1→7 的机械部分和文档格式化，把 8（评审）和 10（运行判断）显式交还给人**——这正是底稿"候选而非最终 DVP"定位的实操版。
