# 企业级 DSH 插件开发规范

版本：1.0 · 定稿日期：2026-11-11 · 文档类型：开发与发布参考规范。

适用范围：本项目 `plugins/` 下的业务插件、`packages/` 下的公共能力及其发布集成。本规范作为开发、审查和发布依据；其发布不代表现有代码已符合，也不构成临床验收或企业部署安全验收。

## 摘要

以 DeepSeek Harness 原生扩展机制为基础，平台统一公共机制，插件提供专业能力，AI 自主选择工作路径。用明确接口、工程检查、可复现证据和责任归属保证质量，不以额外流程限制替代正确实现，不因“企业级”机械拆包、复制基础设施或增加审批。

本规范规定开发与发布质量。企业身份、数据接入、执行隔离和进程监督由平台与部署合同负责，不要求每个业务插件重复建设。明确的数据边界、技术正确性要求和 DSH 原生权限继续有效。

## 1. 效力、用语与适用阶段

**必须/不得**是适用范围内的必需要求；**应**是默认做法，偏离时记录理由与等效证据；**可**是实现选择；**条件适用**仅在包具有对应能力时生效。本文的检查清单用于开发交付，不是要求 Agent 按顺序调用工具的运行流程。

### 1.1 适用阶段

| 阶段 | 必需结果 | 不作为该阶段的前置条件 |
|---|---|---|
| 开发/原型 | 职责清楚、接口可解释、变更有相关测试、错误和限制如实表达；保护已有文件与数据 | 完整企业身份/API、全平台 Worker 工程、所有未来场景验收 |
| 发布候选 | 冻结源码与依赖、相关检查通过、可安装/可消费的制品、兼容证据、来源与限制记录 | 将分发完整性等同临床批准，或要求每插件重做部署平台 |
| 企业部署 | 平台/IT/部署方按目标环境完成授权、运行与恢复等合同验收；业务方完成适用业务验收 | 仅凭插件安装、单元测试、模型文字或截图宣布生产就绪 |

本规范约束当前系统和所有后续开发，不设存量豁免，不为错误实现保留兼容层。开发前核对对应 DSH 上游契约和本文要求；实现时遵循职责及接口；交付前执行适用检查。发现不符合项须修正根因或重做对应模块，未完成不得标记符合规范或正式发布；分批实施只是变更组织方式，不降低验收要求。正确的数据保留和审计追溯不得因删除代码兼容层而丢失。

### 1.2 文件关系与规则变更

本文是跨包开发与发布规则的唯一维护正文，不再保留旧规范文件或跳转兼容入口。领域专属规则由插件文档维护；[企业多插件架构](ENTERPRISE-MULTI-PLUGIN-ARCHITECTURE.md)及其发布、运行、知识合同拥有平台设计的详细定义，本文不重复其完整协议。

用户已确认的业务/数据边界和本项目 [ADR-0001](adr/ADR-0001-DEVELOPMENT-AND-KNOWLEDGE-ARCHITECTURE.md)约束本文。DSH 运行事实以实际锁定版本的公共接口、实现和合同测试核对。发现矛盾时不得用泛化企业条款覆盖明确决策，也不得悄悄改变运行行为；先在对应规则的维护文件记录解决方式。

规范变更须同步版本、变更理由、受影响能力和验证要求；改变包边界、授权、持久化或公共协议的决策记录到 ADR。普通修错、局部实现和文案修订不强制新增 ADR。

## 3. 架构边界与职责

### 3.1 五个对象分开

PluginPackage 是技术包；Capability 是版本化能力；Application 是员工业务入口；ApplicationRelease 是不可变应用发布；RuntimeBundle 是确定的引擎、插件和配置组合。应用与插件不要求一一对应，公共能力不必展示为员工应用。

平台面向几十至上百插件设计，不以 Listing、DVP 写死通用导航、数据字段、执行逻辑或验证分支。Listing 员工类型仅 Manual、Medical、PK、Report；PK 内部方法不是新业务入口，DVP 不继承 Listing 类型。

### 3.2 责任分配

| 责任主体 | 负责 | 不负责 |
|---|---|---|
| 插件维护者 | 领域工具、方法、输入输出语义、专业诊断、领域验证和插件测试 | 复制企业身份、调度、知识数据库或 DSH Agent loop |
| 平台维护者 | 公共服务/API、DSH 适配、通用运行与成果机制、注册与兼容检查 | 在控制主服务执行领域正文解析、业务计算或任意插件代码 |
| 发布责任人 | 冻结制品与依赖、核对检查证据、记录分发决定和回退方式 | 以制品哈希代替批准身份，或以分发批准代替临床验收 |
| 业务验收责任人 | 当前项目结果语义、适用性、必要复核与业务验收 | 用人工复核代替开发基础测试 |
| IT/部署责任人 | 获准数据入口、企业身份、执行身份与环境权限、密钥和部署安全验收 | 让插件根据文件名/资料类别自行推断用户授权 |

同一人在本地开发中可以承担多个角色，但记录必须区分代码检查、业务结论和批准事实。例行检查应自动化，不强制每次人工签字。

### 3.3 包与执行边界

- 业务插件不得互相引用源码或私有实现。共享能力进入有明确维护者的公共包，以公开 API、类型与兼容合同消费；不绕过 `exports` 相对导入其他包的 `src`。现有相对源码互引必须整改，未完成前不得通过包独立性检查或正式发布。
- 需要独立替换/演进的公共能力可拆为定义、提供者和消费者；简单领域工具不机械三拆，不因预估插件数量提前引入微服务。
- 插件只拥有自己的注册和资源，不关闭共享服务。公共包不得因某个具体业务插件 ID 增加专用分支；领域差异由贡献或领域实现承载。
- 企业运行中的领域解析、计算、验证与成果发现位于相应执行域，控制服务只处理通用业务关系和经过验证的数据注册。独立进程不是安全沙箱。
- 新企业运行链路使用锁定 DSH 的 profile/SDK 等公开入口；不重造模型客户端、Agent 循环、Cordis Loader 或一套平行引擎协议。部署细则见[发布合同](PLATFORM-APPLICATION-RELEASE-CONTRACT.md)与[运行合同](PLATFORM-RUN-LIFECYCLE-CONTRACT.md)。

## 4. 包类型与交付要求

先根据真实职责判定包类型，再选择文件与检查，不要求所有包套同一目录模板。

| 类型 | 必需交付 | 条件适用 |
|---|---|---|
| 公共纯库 | manifest、明确 exports、接口/限制说明、相关测试；TS 类型检查 | 转译/打包在目标运行方式需要时执行；无独立安装/启停/图标要求 |
| Host 插件 | manifest、Host 入口、依赖/生命周期合同、相关测试和装配验证、**知识沉淀 manifest（[§7](#7-领域可靠性与知识验证)）** | 配置 schema、skill、工具、持久化按能力提供；作为 Bundle 发布时加 patch |
| Host + Client 插件 | Host 项及 Client 声明、browser 入口、两端构建检查、实际 UI 验证 | 专业视图、主题/语言/交互按实际贡献验证 |
| 配置型 Bundle | manifest 的 `dsh.bundle.patch`、patch、配置/依赖说明与组合验证 | 可没有 Host/Client 源码、编译步骤或 TS 检查；引用已有插件不复制实现 |
| 其他可安装 Bundle | 上述相关内容、完整安装制品、显示资源和安装/升级/卸载证据 | 运行兼容范围、依赖构建脚本和平台支持按实际发布声明 |

带员工入口（`application.json`）的 Host 插件必须提交 `knowledge/manifest.json`，把**每个业务工具**映射到知识主题（主题须有种子支撑）或显式声明 `noMethodKnowledge` 并给出具体理由；状态/元工具除外。此要求由 `scripts/check-development-standard.mjs` 自动执行（规则 `KNOWLEDGE_MANIFEST_MISSING` / `KNOWLEDGE_MANIFEST_PLUGIN_ID` / `KNOWLEDGE_CAPABILITY_UNMAPPED` / `KNOWLEDGE_TOPIC_UNRESOLVED` / `KNOWLEDGE_NO_METHOD_REASON`）。知识域 ID 与正文格式见 [国际化企业级知识库架构](ENTERPRISE-KNOWLEDGE-ARCHITECTURE.md) §7。

各包必须提供一条可复跑的聚合验证命令，检查与包类型匹配；可委托 workspace 根命令，无需每包复制 `verify.mjs`。发布构建/验证可由平台共享脚本承担，无需复制 `release.mjs`。小包不强制独立 DEVELOPMENT 文档；复杂包应提供开发说明或链接到公共开发指南。

## 5. DSH 插件接入契约

### 5.1 入口、配置与 Bundle

- Host 使用目标 Loader 支持的插件形式。函数插件以 `name`、所需 `inject`、`apply` 为项目惯用形式；需要配置时导出配置类型与有效 schema；提供服务可采用上游支持的 service class。不得混合导出形式导致 Loader 选择错误。
- `inject` 声明必需服务，未就绪时允许保持 PENDING；可选服务使用目标版本支持的可选查询/注入并定义降级。区分等待依赖、被禁用、加载失败和能力降级，不人为将正常等待写成异常。
- 部署可调参数集中在配置契约中解析；秘密使用凭据/环境 secretRef。环境变量回退和固定默认值须说明来源，不将常用运行时路径散落在代码中。
- `dsh.bundle.patch` 指向随包 patch；新增 row ID 唯一，覆盖已有 row 必须明确目标。Loader `config` 整段替换，不是 deep merge；不得无意抹掉其他必要配置。
- `exports` 仅暴露公开入口/类型/资源；`files` 包含制品需要的文件。不是每个分发文件都要成为 exports 子路径。必须验证真实安装文件清单，不能只验证开发目录。

### 5.2 生命周期与状态

- 使用所属 Context 注册能力。上游已 effect-owned 的 `tools.register`、`skills.register` 等不重复注册清理；自建服务的普通 disposer、数据库、原生计时器和连接须显式纳入 `ctx.effect`。
- 注册到 `agent.ctx` 等另一上下文时，也由插件保留清理能力，使插件卸载或 agent dispose 任一方均可结束注册；不能留下过期 callback。
- 自有清理幂等。多个异步 disposer 不保证串行完成；顺序依赖的停止、等待、封存、清理在同一异步 disposer 中按序结算。消费者不得提前关闭服务提供者。
- DSH 会话记录是会话行为的事实来源；业务任务/工件/知识库拥有自己的权威对象，二者通过可追溯引用关联。不向 Session 追加未支持的事件类型，不把内存状态当作已持久化事实。
- hook 使用影响最小的公开扩展机制；不拥有决策时保留 `next()`/原 decision 字段。全局 prompt/policy 修改属于平台扩展，不由普通领域插件暗中承担。

### 5.3 Client 与安装配置

- Client 按 `dsh.client` 和公开 slot 契约接入，按锁定版本构建 module/factory；不加载重复 React、外部 CDN 或依赖未支持的 Harness 内部组件。私有 UI 导入即使当前可运行，也不能视为稳定 API。
- 界面文字走 locale，布局/控件遵循宿主主题、可访问性与交互；资源随 context/unmount 清理。不替换应用根节点，不读取别的插件 DOM/私有状态，不挂第二套应用。
- Host service 单份实现应用数据操作，UI 与 Agent 工具共享业务逻辑。授权批准和人类答复走可信专属通道，不提供模型自我批准工具。
- 可安装 Bundle 提供有意义的本地化名称/描述及可分发图标，校验字节、路径和文件大小。明确的测试夹具/无元数据例外须记录原因；不强制纯库承担界面资源。
- 常规 profile 安装/启停使用上游 Plugin Manager 或官方管理命令。业务插件不得重写用户整个 profile/patch；修改自身配置使用公开配置编辑机制，保留用户覆盖。企业部署服务可生成受控发布组合，责任归部署而非业务插件。
- 安装记录的 saved/enabled 与实际 activation/restart/error 分开；安装成功后测试实际能力。依赖 build script 授权、兼容豁免和业务执行权限不能互相代替。

## 6. 工具、Skill 与自主工作

### 6.1 工具合同

- 使用 `defineTool` 或目标版本等效公开 API；名称不冲突，描述准确，参数和 canonical output 有明确 schema，`execute` 返回声明的 lossless JSON 值。参数类型检查之外，工具仍负责必要的跨字段/业务不变量。
- 返回值可为对象、数组、字符串、数字、布尔或 null。结构化业务结果直接返回有类型字段；纯文本可返回字符串，不将所有业务对象统一 `JSON.stringify` 为无字段契约字符串。`render` 和展示 metadata 是纯投影，不执行 I/O、取时钟或产生副作用。
- 基础设施异常通过 pipeline 成为工具失败；已完成执行但存在待处理领域问题可用明确结构化状态表达。不得捕获全部异常后统一返回成功类型的 `{ok:false}` 字符串。错误码、分页、部分结果及未确定状态须可解释。
- 分别审计 canonical value、模型 content 和持久 metadata；只替换展示内容不能阻止程序调用方获取 canonical value。不扣留用于正常开发修复的已授权输入和真实诊断。

### 6.2 取消、超时、并发与副作用

- 前台异步工作必须检查/传递 `exec.signal`，包括调用前已取消、初始化中取消和执行中取消。Promise 仅在本次拥有的工作及必要清理结算后完成。
- 优先使用合作取消/优雅关闭，必要时升级终止并等待受控进程树退出；不是每次取消都强杀。不能确认退出/外部副作用结局时报告未知，不假报取消完成；不按复用 PID 盲目终止进程。
- `timeoutMs` 是声明，registry 本身不执行 deadline；须装配对应 timeout policy 或有经过测试的等效超时实现。`Promise.race` 返回不证明后台停止，同进程死循环也不能靠 AbortSignal 强行中断。
- 已按 DSH Jobs 等公开机制发布的后台任务采用任务自有 signal/owner/结束合同，不无差别绑定外层工具调用寿命。不要自造无所有者的后台 Promise 或孤儿进程。
- 只有确认对父级状态及共享数据安全的工具调用才声明 `isConcurrencySafe`。允许并行时验证 CAS、幂等或明确竞争失败；没有证据就保持默认互斥。
- 重试不得自动重复未确定的副作用。写文件默认防覆盖；显式覆盖表达意图，不要求对每个正常写操作新增人工审批。写入失败不得交付半成品为成功；重要输出采用适合介质的原子提交/恢复机制。

### 6.3 Skill 与提示词

Skill 使用 kebab-case 名称、准确路由描述和 `modelInvocable`/`userInvocable` 策略；Skill 是参考指导，不是授权机制。

**本项目要求：写目标、可用能力、数据/业务边界和验收标准，不编排 AI 的工具调用步骤。** 不用“必须先调用某工具”“只能走某路径”“资料未齐禁止草稿”等人为枷锁替代 Agent 判断。合理操作示例可作非强制参考；真实技术前置条件应由代码检查并返回诊断。

领域插件不得全局限制 Harness 工具、重写模型 provider 或接管 Agent 循环。平台已有身份/运行权限仍有效，不因 AI 自主而扩大授权。当前明确业务要求与项目裁定优先于历史知识；真正歧义才询问，不把常规工作交还给员工逐步驱动。

## 7. 领域可靠性与知识验证

- 保留原文/原值与归一化值的关系、单位及文件/页/表/行列来源；摘要绑定对应输入或产物版本。不得静默丢行、丢页、丢列、改变条件或用旧项目常量填补当前未知值。
- 对声明支持的格式测试实际结构边界：隐藏/合并/公式、压缩对象/关系、编码、损坏和大输入等。不能理解时保留可用资料并诊断，不猜测丢失内容；资源限额、窗口与分页须明确完整性，分页拼接无重复/遗漏。
- Listing 规则与 DVP 边界分属领域。DVP 的 Cover/Approval、受试者号/评审信息处理和候选/UAT 纪律见 [DVP 模板合同](DVP-TEMPLATE-SCHEMA.md)及插件文档；不将它们套用到 Listing 或所有未来插件。
- 生成、解析、工具回归、知识断言验证、项目业务检查、UAT、人工复核和生产批准是不同事实。未执行就写未执行；草稿/候选不因格式校验通过成为业务批准。
- 知识库保存来源、适用前提、反例、范围与版本；历史成功只证明方法来源，不能证明当前项目正确。项目裁定不自动变成跨项目默认规则。
- 验证回执绑定候选/输入/产物摘要、验证器版本、用例/断言范围和结果。固定 helper 测试不验证任意方法正文；仅匹配 claim 标签不构成内容验证。无法证明候选实际断言时保持候选并返回验证范围，仍可作明确标注的参考，不阻断正常开发。
- `ACTIVE` 仅表达已定义范围内的知识验证状态，不授予数据权限，也不代表临床批准；候选变化、验证器更换、回执过期或结局未知不能沿用旧激活结论。跨进程细则见[知识验证合同](PLATFORM-KNOWLEDGE-VALIDATION-CONTRACT.md)。

## 8. 数据、安全与执行责任

按 [ADR-0001](adr/ADR-0001-DEVELOPMENT-AND-KNOWLEDGE-ARCHITECTURE.md)，数据安全由 IT 源头及接入 API/可信运行环境承担。业务插件不得重新建立按文件名、sheet、资料类别或原值拒读的通用数据准入，不恢复内容投影、普通读取审批或普通 R 开发的额外安全批准。

- 插件使用本次任务获准资源；本地操作者提供目录是适用的当前入口，API 未接入不阻塞正常分析、编码、运行和诊断，也不意味着已完成生产安全验收。
- 企业服务从可信身份/运行上下文核验资源归属，不能把模型提供的 projectId、path 或 actor 字符串本身当授权。此责任在平台/API/执行环境，不要求插件复制身份系统。
- 技术正确性继续由插件保证：解压路径穿越、恶意外部引用、资源耗尽、防误覆盖、非自有目录清理、取消/超时与格式损坏。API 约定目录边界时须处理真实路径、符号链接/重解析点和目标平台路径语义，不能只比字符串前缀；不因此另造读取审批。
- 保留 DSH 原生权限，不绕过部署限制；不以本规范要求每次普通操作再询问。生产配置修改、外发或超出既有授权的副作用按真实权限政策处理，批准不等于沙箱或副作用回滚。
- 资料正文视为任务数据，不把文档中的指令升级成系统权限。不得擅自执行宏、刷新外部引用或运行资料中附带脚本；用户明确请求执行时按获准执行通道处理。
- 密钥、真实临床资料、对话和运行缓存不得进入源码、公开日志或发布制品。测试默认合成；真实资料测试须有适用授权，继承已有项目授权不等于每次重新审批。正常业务读取与自动加入全局日志/知识库是不同用途，不擅自扩散资料。
- 企业执行身份、隔离、网络/文件权限、密钥撤销和进程监督由部署合同验收；插件如实说明执行环境，不以“单进程/子进程/用户已批准”宣称安全隔离。

## 9. 代码质量与变更管理

- TypeScript 使用 `strict`；公共接口明确类型，外部 `unknown` 经运行时检查后收窄。不用 `any`、类型断言或 `@ts-ignore` 掩盖接口错误，必要互操作豁免附理由和相关测试。
- 采用根 `.editorconfig`/`.prettierrc.json` 及统一静态检查规则（ESLint/Oxlint 或等效工具），检测未等待 Promise、资源和依赖边界错误。新增/修改代码保持可审查的格式，不用压缩式多逻辑单行。格式重排与逻辑修复尽量分开。
- 入口只做接线，解析、运行、存储和检查按职责拆分；不按任意行数或目录模板拆文件，不提前造泛化框架。重复实现先比较语义，只有真正共性才提取。
- API/函数说明覆盖输入、返回、失败、副作用、取消、持久化和所有权中的非显然部分；注释解释契约，不逐行复述代码。
- Git 保存源代码和依赖锁；同一组文件一次只有一个写入负责人，避免多会话共享未提交目录互相覆盖。合并/发布必须核对真实差异与源码基线，不自动提交或初始化仓库。
- 公共工具/schema/协议/持久化变化评估全部消费者。兼容新增不强制升 schema 主版本；破坏兼容变更必须新版本及明确迁移/拒绝/只读降级，不能悄悄按新格式解释旧产物。
- 迁移保留数据与摘要，按风险提供备份、恢复和回退验证；失败不静默删除用户记录。取消、重试和恢复分别记录，不能以重试掩盖前次未知副作用。

## 10. 测试、检查与验收

检查按能力与风险选择，不强迫每个插件重复运行全部平台验收。所有检查必须写明对象/版本、输入类别、命令或方式、实际结果及未覆盖项；失败/跳过/被阻止不伪报通过。

| 检查类别 | 主责 | 适用条件与证据 |
|---|---|---|
| 静态与格式 | 插件/公共包维护者 | TS 类型、目标语言语法/静态检查、依赖边界、格式；纯配置检查 schema/patch，不强加编译 |
| 单元与格式完整性 | 能力维护者 | 纯逻辑、正/反/边界、损坏/大输入、分页和写出保真；按声明支持的格式选择 |
| 服务/工具集成 | 插件维护者 | 经真实入口检查参数→服务→canonical result/失败；有状态能力测隔离、CAS、恢复；异步能力测取消与停止 |
| DSH 装配 | 插件维护者与平台维护者 | 在锁定宿主加载、发现、调用、卸载/重新挂载；新增依赖/共享服务变更检验相关消费者 |
| Client 验证 | UI 维护者 | 实际宿主内容、交互、错误/重放、必要主题/语言与可访问性；mock 不证明 DSH UI 正常 |
| 包验证 | 发布责任人 | 干净消费环境中的包入口、资源、依赖、兼容与独立安装/消费，不能仅在源码 link 环境通过 |
| 当前业务验收 | 业务验收责任人 | 当前输入/产物、领域期望与必要独立检查；批准绑定明确产物，不拿合成回归替代 |
| 企业运行验收 | 平台、IT/部署责任人 | 身份/资源授权、执行隔离、启动/取消竞争、恢复、工件登记和运营；详见对应平台合同 |

不设统一“覆盖率达到某数字即合格”的替代标准。新增功能和缺陷修复必须有相关正向/反向证据，重要错误路径不能只用成功桩。真实模型测试仅在需要验证模型/宿主整合时使用，记录模型与范围，不以模型自评代替确定性检查。

CI 应对受影响包及共享包消费者执行相关检查；失败非零退出，无理由跳过不得记绿色。未接入 CI 前保留同一源码基线的本地检查报告，不声称 CI 已通过；建立 Git/CI 是平台工程缺口，不是让每个插件复制 pipeline。聚合检查发现包清单，不写死仅 Listing/DVP。

## 11. 依赖、构建与发布

### 11.1 依赖与产物

- 开发与 peer 声明可以使用经过验证的兼容范围；发布/部署解析为确切版本、依赖锁和摘要，无隐式 latest、运行时临时选 provider 或网络回退。兼容声明与部署锁定是两件事。
- 与宿主共享实例的 DSH/Cordis 包按上游教程声明 peer 与开发依赖；第三方及独立无状态 utility 按实际运行需求声明。不得因本机 link/祖先目录碰巧可解析而遗漏依赖，不重复打包必须共享身份的宿主 service/class。
- 采用随包捆绑或明确安装依赖二者之一，完整记录实际分发闭包；不得无差别要求所有库都 bundle。捆绑本地公共源码时也纳入摘要、许可与消费者回归。
- 构建可在记录的干净环境重做，精确绑定源码、lock、Node、包管理器、DSH 和构建参数。产物后修改源文件/配置/依赖须重新检查并构建；不得拿旧 bundle 证明新源码。
- 依赖/许可证清单是发布必需项；机器可读 SBOM 按企业部署/供应链要求提供。逐字节可复现为推荐目标；若对外声明可复现或依赖其完整性验证，则必须实际比较摘要并解释时间戳/平台差异。

### 11.2 可安装与可追溯发布

- DSH 安装物采用宿主实际支持的包目录、registry 包或打包产物；离线交付至少验证等效 `pnpm pack` 的安装文件闭包。自定义 ZIP 证据包不自动等于 DSH 可安装包，不得只验证 ZIP 内哈希就声称独立安装通过。
- 发布记录至少包括：包 ID/版本、源码修订或完整摘要、依赖锁摘要、DSH/Node 兼容组合、制品摘要、相关验证证据、限制及发布决定；捆绑第三方代码附对应许可证。
- 依赖 prepare/build script 是安装期代码执行，按宿主政策批准；优先分发已构建产物，git 安装须锁定提交且构建不依赖发布包外的兄弟源码目录。
- Candidate 完整性、允许分发、企业部署和业务批准分别表达。批准来源来自当前可信操作者/发布系统及对应制品；不得硬编码历史授权文字冒充本次批准，也不要求新增无业务意义的逐步人工签字。
- 应用发布在平台绑定确切能力提供者、schema/protocol、配置和 runtime 摘要；普通升级影响新 Run，不静默改在途组合。紧急封禁/撤权按[发布合同](PLATFORM-APPLICATION-RELEASE-CONTRACT.md)处理，不由插件各自实现。

## 12. 文档、诊断与可维护性

包 README 必须描述用途/非目标、配置与依赖、输入输出、失败/限制、验证入口及真实能力状态；工具/skill/package metadata 与其一致。详细 API 和状态只维护一处，其余链接引用；历史实证、规划与当前承诺分开，不把文档中的计划视为已有接口。

已授权的真实错误和 stdout/stderr 应足以驱动修复；截断标注范围，不把错误静默变为空结果。不返回秘密或与诊断无关的资料；合法绝对路径、源定位和必要数据不是一律禁止返回的内容。未知异常保留受控日志关联和实际原因，避免仅返回无法定位的“操作失败”。

日志按需要关联 run/session/attempt、插件版本、输入/产物摘要和结果；不重复存储 DSH 全量会话，不凭日志自称不可篡改审计。资源保留、备份和清理由其维护者负责，只删除明确属于本次工作或保留政策允许清理的内容。
