# 企业级 DSH 平台与两插件整改实施方案

日期：2026-11-11。修订：1.2（补充 WP8 模型选择/工作台落地状态指针，不代表全部完成）。状态：整改方案；实施进度与逐项证据以[整改记录中的剩余工作矩阵](REMEDIATION-2026-11-11.md#补充方案剩余工作矩阵2026-11-11按实际证据)为准，本文件不宣称任何未执行验收已通过。

本次产品要求：平台定位为面向国际用户、可扩展大量智能体应用的企业 AI 智能体平台；Listing/DVP 是首批专业应用，不是平台产品边界。用户可自行选择平台统一接入的可用模型，模型选择属于核心工作体验，不是仅供管理员使用的配置。当前工作台需要重新设计交互与信息架构，而非在旧界面补一个下拉框。国际化目标不等于已经具备全球部署、跨境数据合规或全部模型支持。

## 1. 目标与决策摘要

整改目标不是再做一套 Agent 引擎，也不是补更多审批按钮，而是让员工从统一工作台发起业务工作，平台可靠执行、恢复和交付，插件提供准确的专业能力，发布与验收都有可复核证据。

建议采用：**模块化控制服务 + 独立企业工作台 + 锁定 DSH SDK/profile 的受控 Worker + 公共能力包 + 独立领域插件**。复用已有代码和合同，不为百插件提前拆微服务，不给 Listing/DVP 各建一套工作台。

交付分三个层次：

| 层次 | 能对外声明什么 | 必须满足什么 |
|---|---|---|
| L1 工程发布候选 | 指定版本可安装、接口正确、已通过声明范围的工程检查 | 插件缺陷、公共包消费、干净安装、构建追溯与相关回归通过 |
| L2 内部业务试点 | 指定使用者、项目与任务范围内可试用 | 工作台真实闭环、可信身份/资源入口、执行隔离与恢复、限定业务验收 |
| L3 企业正式部署 | 指定部署与用途获准运行 | 部署/运维/业务/必要合规验收，生产批准与回退记录 |

不得用 L1 代替 L2/L3；IT 对接未提供不阻碍本地研发，但阻止声称企业身份、数据授权已验收。合成资料可以贯穿研发和集成验收，不能替代当前真实项目业务验收。

### 2.2 不应继续传播的过度判断

1. **字符串结果不天然违反 DSH。** 上游允许 scalar/string。问题是本项目把结构化业务对象统一变成 JSON 字符串，并将基础设施异常包装成正常成功值，违背项目规范及可靠程序化调用要求。应按真实语义改接口，不是禁止所有字符串工具。
2. **不能把当前公开源码导入直接判为绕过 exports。** platform-workbook 已导出 `src/index.ts`，platform-knowledge 已声明 `./src/*`；本轮边界检查也通过。真正要整改的是公共 API 收敛、依赖与安装制品闭包、干净消费验证，而不是为消除误报机械改路径。
3. **本地 approve CLI 不必各自实现 SSO/签名。** 受信本地操作者显式提供 provenance 可以作为本地操作记录；但任意文本本身不是企业发布授权证明。企业批准需由平台发布流程核验身份与制品绑定，不要求每插件重建身份系统。
4. **钩子不是发布安全边界。** PostToolUse 是编辑后的反馈；已完成的修改不会被它回滚。检查器异常不得被计为通过，发布必须有独立的非零退出强制门禁。
5. **工作台已经是 v4 原型。** 已有应用贡献、第三应用接入和合成目录测试，不能继续以旧 v3 的业务硬编码状态评价当前原型；但仍未接真实服务端与 DSH。
6. **Git 已建立。** 当前缺口是远端托管、分支保护、CI 实际全量运行与发布治理，不是再次初始化仓库。

上游契约以本地锁定 DSH `0.2.2-rc.1`、commit `fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159` 为准，参考 [工具合同](../upstream/deepseek-harness-git/docs/cookbook/adding-a-tool.md)。不以最新网络文档替换锁定契约。

## 3. 不可退让的实施边界

- 保留 Harness 自主规划、工具选择、编码与纠错；不引入固定工具调用顺序或普通读取审批。
- Listing 仅 Manual、Medical、PK、Report 四类；DVP 不继承 Listing 类型。
- 数据授权由 IT/API/执行环境承担。插件负责格式完整性、真实路径、防覆盖、取消、资源限额等技术正确性。
- DVP Cover/Approval、受试者号与评审信息的领域边界继续按 [DVP 模板合同](DVP-TEMPLATE-SCHEMA.md)执行，不扩大为所有插件的通用拒读规则。
- 平台不加载领域解析或验证代码到控制主进程；插件不改全局 provider、Agent loop 或工具策略。
- 同一文件组只有一名写入负责人；并行工作必须先定文件范围和接口，未回复的协调消息不算达成一致。
- 不自动提交、推送、发布、修改生产 profile、迁移/删除用户数据或启用真实模型付费验收。
- 不给错误实现保留兼容分支；但历史数据和审计必须有明确迁移、只读或拒绝策略。

## 4. 目标结构与最小产品闭环

```text
员工浏览器：统一企业工作台
  │ 可信登录、项目上下文、版本化命令/查询/事件
平台控制服务：IdentityAdapter / Project / ResourceRevision
              AppRegistry / Work / Run / Interaction / Artifact / Audit
  │ Outbox、租约、执行授权、冻结 ExecutionPlan
Worker Supervisor：启动登记、进程树、取消、资源限制、恢复对账
  │ 锁定 DSH SDK/profile
DSH Worker：自主 Agent + 按计划加载的公共能力与领域插件
  │ 受控资源引用与候选成果
平台成果存储：不可变 ArtifactRevision + Evidence + ReviewRecord

中心 KnowledgeService ← 授权检索/候选请求 → Worker
中心 KnowledgeService ← 绑定请求的验证回执 ← 受控 ValidationExecutor
```

平台第一条纵向闭环：**选择应用/项目 → 引用获准资料 → 保存 Work/InputRevision → 创建 Run → 实际执行 → 必要澄清 → 封存成果 → 展示检查状态 → 授权下载/业务复核**。

浏览器断线、刷新、换设备不能丢工作。执行成功、技术检查、业务审核、部署批准分别显示，不能合成一个绿色“完成”。

正式前端独立于业务插件维护，以平台 API 为边界；保留原生 DSH 会话作为专家/诊断入口。**重新设计信息架构、导航与工作画布，不把 v4 原型的现有布局作为必须继承的基础**；只复用经验证且符合新体验的草稿、版本与状态纯函数。浏览器 localStorage 只保留偏好和明确标注的未提交草稿。不得把原型预设回复或示意结果接成假执行。用户选择平台内置模型是首期必需能力；模型目录与配置由平台管理，实际模型调用继续使用 DSH 已装配适配器，不重建模型客户端。

建议初期新增一个正式前端目录 `apps/enterprise-workbench/`，不要复制两份领域 UI。具体框架沿用团队受支持栈，框架选择不阻断当前接口和状态整改。

## 5. 整改工作包

### WP0：冻结基线与发布证据体系（工程负责人）

**范围：** docs/README、RELEASE-READINESS、PLATFORM-CONTROL-IMPLEMENTATION、规范、验证脚本及 CI。

- 记录源码修订、未提交差异摘要、Node/包管理器/DSH、依赖锁和配置摘要；每次验收绑定同一基线。
- 建立唯一当前状态矩阵：需求编号、实现文件、测试编号、执行记录、结论、负责人、未覆盖项。历史报告保留日期并指向当前矩阵，不把历史正文全部改成新状态。
- 统一证据状态 `PASS / FAIL / NOT_RUN / BLOCKED / NOT_APPLICABLE`；不适用需理由，失败与阻塞不可被汇总成绿色。
- 工程门禁、业务验收、部署验收分别产生记录；摘要发现变化，不证明批准身份。

**验收：** 旧证据不能用于变更后的源码/制品；缺少适用必需项不能生成 release-ready 结论；已有两处未提交改动归属被确认且不丢失。

### WP1：工具 canonical output、错误与诊断合同（两插件各自负责人）

**范围：** 两插件 `src/index.ts`、必要的领域结果类型与工具入口测试；共享抽象仅在语义确实相同后提取。

- 为每个工具定义真实输出 schema：对象、数组或诚实的纯文本，不再统一 JSON.stringify。
- `execute` 直接返回结构化值；`render` 仅作纯展示投影，不执行 I/O、时钟或状态变更。
- 基础设施错误抛出，让 DSH 形成工具失败；已完成但存在领域问题的结果保持结构化诊断，例如 NEEDS_OCR、未解析逻辑、NOT_RUN。
- 取消不能变成普通成功值；写出已经提交的操作不得假称被回滚。
- 未知异常保留可定位的实际原因与关联 ID；避免只写“查日志”而没有任何对应日志。必要授权数据保留，秘密和无关资料不进入日志。
- 核对 schema 破坏性变化的全部消费者、工具脚本和知识引用；升级版本并记录变更，不保留旧字符串 API 作为错误兼容层。

**新增验收 T01–T05：** 正常结果可直接按字段消费；基础设施异常为失败；领域诊断非伪失败；取消不成功；Native/PTC 两路结果与错误语义一致。必须通过真实 DSH registry，不仅调用 helper。

### WP2：取消、超时、文件路径与原子写入（插件/公共能力负责人）

**Listing 范围：** project/workflow/datasets/archive/runner。**DVP 范围：** protocol/parse/write。公共 OOXML 实现位于 platform-workbook，由一个负责人修改。

- 从工具入口贯穿 `exec.signal`；覆盖调用前已取消、目录遍历、读文件、解压、解析、R/7z 执行以及清理阶段。
- 短同步纯计算可以保留；大同步解析要分块让出事件循环，或移到有明确所有者的 worker thread/执行进程。仅在同步循环中读取 signal 不能保证及时收到取消。
- 统一超时语义：超时触发停止并等待自有资源结算；禁止 Promise.race 返回后后台继续写。验证实际 timeout policy，不能只填 timeoutMs。
- 子进程优雅关闭失败再升级终止；按目标 OS 核验进程树，不能仅凭直接子进程 close 声称整树停止。
- DVP PDF 目录与目标文件都解析真实路径；写出目录、父目录与既有目标覆盖路径同样核验重解析点/符号链接。不把技术边界解释成新的数据读取审批。
- DVP 默认防覆盖采用原子 no-clobber 提交，不能仅 existsSync 后普通写入；显式覆盖先同目录临时写、必要 flush，再使用目标 OS 验证过的原子替换。禁止先删旧文件再 rename。
- 中途失败保留旧成果，只清理本次创建的临时文件；路径检查有竞争窗口，企业运行还需受控挂载/目录写权限，不能宣称 realpath 单独彻底消除 TOCTOU。
- 补 PDF 解压后字节、对象数、递归深度、时间/内存及工作簿/ZIP 资源预算；限额命中明确诊断，不静默截断为完整。

**新增验收 F01–F08：** 预取消无副作用；处理中取消最终结算；初始化/停止失败保留 UNKNOWN；超时无孤儿写入；目录内链接越界被拒；并发同名写不覆盖；磁盘写失败旧字节不变；畸形/膨胀输入不拖死宿主。测试均用合成夹具与独占临时目录。

### WP3：公共包与真正可安装发布（平台/发布负责人）

**范围：** 四个公共包 manifests/exports/build/lock，两插件 build/release，安装验收脚本。

- 逐包确定纯库、Host Bundle 或 Host+Client 类型，收敛公开类型与功能 API。新消费默认使用包名和公开子路径；不把全部 src 永久暴露当作边界治理。
- 允许两种已声明分发方式：正式公共包依赖；或构建时捆绑公共纯库并记录源码摘要、版本、许可与消费者回归。不强迫所有公共代码独立部署。
- 有状态共享服务（知识服务等）由独立平台 Bundle 单实例提供，业务插件卸载不得关闭它；不能因捆绑复制宿主 class/service 身份。
- 校验 exports 每个承诺入口在实际打包文件中存在。目前 knowledge 的 src 导出与 files 清单需核对消费方式，不能把源码树可用当作发布包可用。
- 使用真实 `pack` 等效安装制品；ZIP 可以保留为证据包，但不能冒充 DSH 安装验收。
- 干净环境不链接回开发 checkout：依次安装锁定宿主、公共 Bundle、单个业务插件，真实加载/调用/卸载/重挂；再验证两个插件共存及禁用一个不影响另一个。
- 核对 Host/Client 两端、资源/图标/本地化、传递依赖与许可证；对声明支持的 OS 建矩阵，未验收的 OS 不声明支持。

**新增验收 P01–P07：** Listing 独装；DVP 独装；两插件共存；卸载/重挂无残留；有效安装文件闭包；无隐式祖先依赖；相同基线重建摘要符合可复现声明。测试缺许可、缺 peer、错误宿主版本、缺导出资源均应失败。

### WP4：运行准入、进程监督与恢复（平台运行负责人）

**范围：** platform-runtime/run、platform-control 的 service/runs/store/scheduler/worker，必要的独立 supervisor 模块。避免先造分布式框架，首期单调度写入者也必须有持久准入和恢复。

- 补 Work 与同 Work 单活动 Run 约束；UNKNOWN 不视为可安全重试的终态。
- 同事务创建 Run、初始输入与 outbox；先 CAS 领取执行权、持久 launch intent/epoch/spawn permit，再启动 Worker。
- 拆开当前 dispatch 内的“创建 Harness”和“发送业务 prompt”，保证建立可停止进程树、复核取消/授权/epoch 后才发送任务。
- 租约/fencing 单调递增并约束回执与资源写入；旧 token 拒绝，但不能拿 token 代替终止旧进程。
- 引入必要状态 WAITING_FOR_USER、FINALIZING、CANCELLING、UNKNOWN；持久结构升级采用受控迁移，保留历史事件。
- 取消先记录意图；关闭失败、退出证据不足时 UNKNOWN，不吞掉 close 异常后声明 cleanedUp=true。
- 启动恢复只做对账；确认旧进程退出后才恢复同 Run。普通 retry 使用新 Run/home/root session，不继承未知队列。
- scheduler 查询应在存储层筛选 QUEUED 并确定排序，不能只取全库前 100 条后过滤导致旧排队任务饿死；补公平性、容量、最大排队时间与退避，不重放未知副作用。
- OS 监督采用目标环境原生机制（例如 Windows Job Object 或 Linux 受控服务/容器进程组）；具体选型在部署 ADR 固定，独立进程不宣称安全沙箱。

**验收：** [运行合同](PLATFORM-RUN-LIFECYCLE-CONTRACT.md) R01–R05、R09、R12；额外覆盖双调度者、spawn 前后崩溃、close 抛错、租约失联及超过 100 条混合历史运行。所有竞争用 barrier/fault injection 确定性复现，不依赖偶然 sleep。

### WP5：输入交付、人工交互与可信完成屏障（平台/SDK 适配负责人）

- 输入区分保存、发送、入队、消费；单会话唯一派发器，不并发多个 high-level run 争同一 session。
- 修正固定读取前 100 条输入的问题，按序完整分页；每条提交有状态和来源事件关联。
- 若锁定 SDK 不能可靠证明消费，保留 UNKNOWN，不凭消息正文或模型总结推断。可以提供明确“下一 Run 生效”的补充草稿，不静默忽略当前已接受要求。
- FINALIZING 原子关闭输入窗口，记录 cutoff；晚到补充进入下一修订，旧成果来源不变。
- 业务澄清、原生工具授权、计划答复、业务审核分开。回答绑定 requestId/session/launchEpoch/修订，经服务端授权与 CAS 领取唯一提交权。
- 网络发送结局未知不自动重发，旧 epoch/撤权后的回答拒绝；浏览器断线可恢复待办，不能伪造默认回答。
- 完成屏障来自实际事实：输入结算、后代结束、交互关闭、成果封存、事件持久化和进程退出。删除 inputsSettled/descendantsDone/cleanedUp 的无依据常量赋值。

**验收：** R06–R10、R12；至少包含第 101 条输入、回执丢失、根 idle 但子会话仍活动、parked 输入、封存与补充并发、旧问题晚答。锁定 SDK 的能力不足应明确阻塞对应功能，不重造 Agent loop。

### WP6：成果与业务检查证据（平台成果负责人 + 两领域负责人）

- ArtifactRevision 保存稳定 ID、Run/epoch、输入修订/消费范围、mediaType、摘要、大小、存储引用；浏览器不直接获得 Worker 任意路径。
- 在 Worker 不能再写入后封存成果，或通过可信存储复制并验证源稳定性；对封存副本计算摘要，原子登记。封存失败不能报交付成功。
- 下载和预览重新鉴权；预览代码不执行文件附带脚本/宏；缓存与临时文件按保留政策处理。
- Evidence 绑定输入摘要、产物摘要、检查器版本、实际用例、结果、日志引用。业务 ReviewRecord 绑定确切 ArtifactRevision，不跟随“最新文件”漂移。
- UI 分别展示 Run 技术终态、领域检查状态、业务复核状态。DVP CANDIDATE/RENDER_REFERENCE_ONLY 保留；Listing 合成测试通过与目标服务器实际复跑独立。

**验收：** R11；封存后 Worker 文件被改不影响下载；校验摘要与下载字节一致；存储失败不登记成功；跨项目下载拒绝；输入更新使旧证据显式过期而非删除历史。

### WP7：企业身份、资源入口与运行隔离（IT + 平台负责人）

沿用 [身份与数据入口合同](ENTERPRISE-IDENTITY-AND-DATA-CONTRACT.md)，不是另造插件权限系统。

- IT 提供身份断言发行方/受众/签名验证及轮换、成员关系 API、获准资源位置/版本、撤权通道、secretRef 与网络策略。平台不把摘要当作签名验证。
- 所有目录/工作/运行/事件流/知识/成果/下载/审核接口按可信 Principal + project/resource/action 授权，不能只校验登录。
- Worker 采用独立运行身份与 Run 级短期授权；缺失/过期不回退到 LocalOperatorPolicy。开发模式与企业模式显式隔离，不能有生产绕行开关。
- 资料进入方式先选一条真实可交付路径：受控上传、IT API/连接器或受管本地执行节点。统一 resourceId/revision/digest，不能把浏览器 D:/ 路径当服务器文件。
- 执行身份只读安装包/profile，工作目录可写；数据范围、网络出口、CPU/内存/磁盘/时限/模型预算由部署落实。
- 人员撤权同时阻止新输入、回答、下载与新运行，并按 supervisor 处置在途执行；无法确认停止则 UNKNOWN，保留证据。

**验收：** I01–I05 + 跨项目事件订阅/下载/知识检索 + 断言伪造/过期/错误受众 + 撤权延迟与在途进程处置。记录实际网络/文件/进程权限，不以登录页面或提示词证明隔离。

### WP8：工作台由原型转为正式业务入口（前端 + 平台 API 负责人）

- 目录来自服务端 AppRegistration；支持搜索、收藏、最近、分页与按需加载。百插件不变成百个常驻导航或全量工具上下文。
- 以 Work 为员工任务载体，Run 为执行尝试；点击开始返回服务端持久 ID 和状态，不能只插入提示词。
- 页面覆盖应用中心、项目、工作详情、待办、成果和必要管理员诊断；一般员工不需要选择 profile、输入工具名或手动推进内部阶段。
- 统一命令/查询/事件 API，写操作幂等键 + expectedRevision；事件流可按持久序号重放，重连去重。传输协议可采用 HTTP + SSE，具体选择不进入领域插件。
- 区分已保存、待接收、执行中、正在停止、未知与真实终态；结果页明确候选/未验证/审核状态。
- 复用原型 v4 的应用贡献、草稿与版本语义；本地记录导入必须用户确认项目归属，原型结果不迁移成真实成果。
- 第一条垂直切片用 DVP 草稿路径，覆盖读入→生成→封存；第二条 Listing 验证有执行进程/多成果的差异。另用第三个合成 probe 应用证明无平台业务分支。
- 真实浏览器覆盖键盘导航、中文错误、主题、必要响应式、刷新/断线恢复、无障碍标签和旧数据兼容呈现。

**验收 U01–U06：** 无指导找到业务并开始；刷新/重新登录可找回；问答/取消/失败恢复真实；成果可授权下载；切换应用不污染上下文；第三应用无需改平台核心分支。建议 5 名非开发员工试点，预先确认成功标准，记录求助、误操作与耗时，不以截图替代验收。

#### WP8 产品重构增补：国际化 AI 智能体工作台

当前原型已有工作区/项目/工作记录/应用中心/成果文件/设置等导航，但界面自述不连模型，工作区描述要求与草稿为核心，尚无模型发现/比较/选择和对话协作体验。整改不是原样正式化或添加孤立下拉框，而是由产品设计和真实用户研究驱动的重新设计。以全球企业智能体平台为产品，不将视觉和术语锁定为临床垂直工具；Listing、DVP 是应用目录中的专业智能体。

**交互架构目标**

- 建立一体化「AI 工作空间」：主区承载可恢复的会话/Agent 工作，侧区承载项目/资料上下文与当前任务成果；运行状态、引用来源和待办在工作上下文内出现。应用中心是进入/发现智能体的入口，工作记录可恢复会话，不把用户强迫分流到表单导航与聊天两套不相通的产品。
- 用户可从全局模型控制器选择平台已配置、对当前用户/组织可用的模型；在开始新 Run 前可选择或沿用上次选择。显示名称、供应方、能力和限制（如多模态、上下文/输出限制）、组织可用状态及管理员说明。比较只展示可验证的信息，不伪造公开 benchmark 或“智能度评分”。
- 提供适当默认项与快速选择，也允许打开模型目录查看可用项、详情和用途说明。模型选择不应被混在高级设置；改变选择后清楚显示作用范围。设置页可保留默认模型偏好，工作区控制当前新 Run 的选择，二者区分明确。
- 已在运行的 Run 始终固定创建时模型配置；切换只影响后续 Run，界面显示当前运行模型，不静默切换 Provider 或重试到其他模型。若模型失效/限额，展示可选替代项并由用户决定重试/新建 Run；不得自动 fallback 改写运行含义。
- 新建工作时能先以普通语言描述目标，再选择 Agent/应用；可根据服务端可用能力推荐匹配的智能体和模型，但推荐不是强制路由，用户可调整。确有影响结果的歧义才提问。
- 导航面向平台任务：工作区、智能体/应用、项目与资料、工作/历史、成果；个人偏好与组织管理分层。管理员模型/供应方配置不与普通用户选模型混为同一权限面。
- 有清晰的欢迎/空状态、运行中、等待用户、失败、取消中、未知和结果检查状态；故障信息给下一步可做动作。对国际用户优先为 locale-ready：避免硬编码字符串，日期/数字/时区按 locale 显示，布局考虑长文本和 RTL 扩展；首批支持语言、翻译和区域部署由产品/业务确认。

**模型目录与配置服务（后端先决条件）**

新增平台控制面 `ModelCatalog` / `ModelAvailability` / `ModelSelection` / `ModelConfigSnapshot` 合同，准确职责如下：

- ModelCatalog 只枚举经部署配置并验证已装配的 Provider/模型；当前最小 SDK profile 只包含 DeepSeek 官方适配器的事实必须反映在目录，不宣称有所有供应方/全球所有模型。新供应方先通过适配器、兼容性和部署安全审核。
- ModelAvailability 在服务端按组织/用户/地区/工作区策略过滤，说明可选原因/禁用原因；目录 UI 的隐藏不是授权边界。
- 用户模型选择保存 `modelSelectionId` 或明确的平台 model ID 与 provider binding；不得接受任意客户端字符串直接触发 Provider 注入、动态 npm 安装、任意 base URL 或请求外网。
- ModelConfigSnapshot 在 Run 创建时固化 model/provider/adapter 版本、参数策略、能力声明、凭据 secretRef 的版本/引用、区域和策略摘要。secretRef 只给受控 Worker 授权，密钥本体不进浏览器、Work/Run 可读投影、日志、Bundle 或模型提示词。
- 由于模型会影响结果可复现性，Run/Artifact Evidence 记录实际有效模型配置与变更事件；同一 Work 后续 Run 可选新模型，但旧 Run 保持原快照。
- Provider 没有已装配 adapter、区域不允许、凭据缺失/失效、模型被管理员停用时，目录/启动准确报不可用；不能偷偷改到默认模型。健康检查使用部署侧安全通道，不让普通用户在浏览器提交密钥测试。
- 模型偏好是用户/组织配置，不覆盖业务权限、数据授权或候选/审批语义。模型能力元数据来自受控目录，可标注“由供应方声明/平台验证/未验证”。

**视觉设计方向与重构原则**

建立 Emerald 的国际企业智能体品牌，而不是通用 SaaS 卡片墙。优先采用深墨绿/石墨作为工作空间结构色、翡翠绿作为主要动作色，辅以中性高对比背景和克制的暖金/琥珀提示色；明确 light/dark token 与 WCAG 对比要求。采用清晰、现代、长文本友好的 sans 字体栈；数字与模型 ID 保持易辨读，不用单色渐变、装饰性 KPI 或密集胶囊标签冒充设计。以稳定导航、宽阔对话/工作画布、可收合上下文栏、模型选择控制器作为主识别元素。减少同质圆角卡片，将层级交给版式、标题和必要分隔线。详细色值、字体、断点、图标、组件与动效规范进入设计系统任务，需先基于品牌资产/用户研究确认，不在本计划内臆造最终 UI。

**核心流程与验收 U07–U14：**

- U07 全局模型入口：启动新工作前，在平台内查看可用模型、完成选择并读懂能力/限制；无需找管理员设置页面或复制模型 ID。
- U08 选择持久性：刷新/换页后，用户偏好按预期保留；选择组织受限模型时给明确不可用原因，不遗失草稿。
- U09 运行快照：Run A 用模型 A 启动后选择模型 B；A 的执行、恢复和历史详情仍绑定 A，后续 Run 才用 B。
- U10 故障安全：选择器指向停用模型/缺少 adapter/凭据过期时，禁止静默 fallback；给可理解状态和显式新 Run/重试选择。
- U11 权限：伪造 modelId/provider、直接调用 API 越过前端筛选时服务端拒绝并审计；无法枚举未授权模型。
- U12 推荐可控：平台可解释为何推荐 Agent/模型，但用户能看、能改；未提供数据时不伪造推荐理由。
- U13 全球可用性：已批准语言的导航、模型名、错误、日期/数字和长文本/RTL（若在范围内）视觉回归通过；键盘/屏幕阅读器可操作模型选择器。
- U14 国际体验研究：非开发用户代表至少完成“发现智能体—选模型—开始—跟踪—检查成果”任务；量化成功率、选择耗时、错误理解、求助率，基线和目标由产品负责人在测试前登记。

模型 UI/API 合同冻结、模型目录有实际多 Provider/配置差异测试前，不把静态模型选单视为可用功能。产品团队应先交互设计/原型评审，再进入正式 UI 实施；正式实现须以浏览器真实交互、响应式、键盘/无障碍和状态恢复验收。

### WP9：知识验证与领域业务验收（知识服务 + 业务负责人）

- 复用已有单机知识实现，不复制每 Worker 一份可写权威库。企业共享部署由中心拥有写入与授权，领域验证在受控执行域。
- Validator/CaseSet/Candidate 的版本和摘要绑定；验证回执来源从受信执行通道核验，模型提交 passed=true 不能激活。
- claims/coverage 标签匹配不是内容证明。检查每个验证器是否实际验证绑定候选的具体断言；无对应正文/机器可检验断言的证明时保持 TOOL_REGRESSION_ONLY/CANDIDATE。
- Run 固定知识修订快照；项目裁定不自动提升为全局方法。迁移单写入者、备份、摘要核对与回退，不直接把同一 SQLite 文件挂给多个独立 Worker 写。
- Listing 业务矩阵：Manual/Medical/PK/Report 四类；PK 至少包含 BE 与 SAD/MAD 方法用例，但不变成额外平台入口。按授权项目验证 spec/ALS/数据→自主 R→纠错→独立 QC→交付→目标服务器异目录复跑。
- Listing QC 的 expected/判定依据独立于待验程序和模型自评，包含漏行、关联放大、重复键、日期、单位、缺失、输出保真及回执过期。
- DVP 业务矩阵：中文/英文文本层、扫描件降级、损坏/加密、ObjStm、分页、规则追溯、逻辑/用例/边界值、模板往返、Cover/Approval/评审边界；不承诺未验证的任意 PDF 或全 EDC 自动部署。
- DVP 完整性须由业务方对照源方案/模板和预期规则集复核，语法有效、issues=0、零编造不等于没有漏规则。按风险抽样或完整复核的方案在验收前确定。

**验收：** K01–K08；两插件各自的业务需求→用例→输入/输出摘要→实际检查→审核记录矩阵。真实项目执行和付费模型复跑另行明确授权/预算，研发默认合成数据。

### WP10：规范执行、CI/CD 与运维（工程效率 + 发布/运维负责人）

**规范执行：**

- 规范条款映射到规则 ID、适用包类型、检查入口、责任人与证据；区分自动检出、人工代码审查、运行验收、IT/业务验收。
- 修正 verify-all 的通用假设：配置 Bundle 可无 src/build.mjs；读取 manifest 的实际 patch 与声明命令，不硬编码目录模板。
- 不再在缺 verify 时静默择一 typecheck/test/build 充当聚合验证；按包类型声明完整适用检查，缺项失败或有明确不适用理由。
- 将正式前端、规范检查器和重要发布脚本纳入验证发现机制。原型测试与正式应用测试分开，不因都绿而混为产品验收。
- 静态检查覆盖未等待 Promise、危险类型绕过与边界；格式与逻辑变更分开。边界检测逐步采用可靠语法分析/模块解析，覆盖公共包反向依赖、别名、动态字面量导入及构建脚本；非静态导入需显式审查，不伪称扫描证明全部安全。
- Hook 失败明确可见，路径/config 修改也需触发适用检查；修复错误输入/检查器崩溃被静默当成功的问题。使用锁定工具版本，独立 CI 才是交付门禁。

**CI/CD：**

- PR 自动执行静态检查、相关测试与共享包消费者回归；候选构建执行全量、干净安装、制品清单与许可检查。
- 锁定上游、Node、包管理器和 R 依赖环境；不能把每次 apt/CRAN 最新安装称为冻结构建。
- 声明支持的平台实际跑矩阵；远端托管/分支保护经用户授权建立，不能仅写 YAML 宣称 CI 已启用。
- 企业发布记录由可信 CI/发布服务核验 actor/权限、制品摘要、证据摘要、决定与时间；本地 provenance 保留为说明，不作为唯一企业授权凭证。不为此给每插件增加 SSO。
- 环境推广安装同一制品，不在每个环境重新构建；普通升级排空旧锁，紧急封禁走撤权与停止合同。

**运维：**

- 关联 Work/Run/launch/session/版本和事件水位；收集排队时间、运行时长、错误/未知、取消耗时、资源使用和模型费用，不收集无关临床正文。
- 明确备份范围、保留期、密钥轮换、配额、告警责任人、故障对账和人工恢复 runbook。
- RPO/RTO、容量和撤权时效由业务/IT 确认后写成可测指标；至少实际演练数据库+成果引用一致恢复、制品回退与旧运行排空。
- 若用途涉及受监管电子记录/签名，由 QA 判定适用要求与验证范围；不自行宣称 GxP/Part 11 合规。

## 6. 优先级、依赖与实施排期

优先级是发布阻断顺序，不代表所有问题发生了生产事故。

| 批次 | 工作包 | 出口 | 并行约束 |
|---|---|---|---|
| S0 基线与产品定义 | WP0、IT 输入清单；WP8 用户研究/信息架构/模型目录合同 | 状态证据口径、用户旅程和模型选择范围明确 | 产品/设计从首批介入，不等后端全做完 |
| S1 插件正确性与体验原型 | WP1、WP2；WP10 门禁；WP8 交互原型与设计系统 | 缺陷回归；含模型选择的核心旅程通过设计评审 | 两插件可分负责人；设计只改独立原型文件，明确非真实运行 |
| S2 引擎与模型接入 | WP4、WP5、WP3；WP8 ModelCatalog/API/快照与 DSH 适配验证 | 持久准入、完成屏障、真实包消费；选择模型与实际调用一致 | control service/store/run 同一集成负责人；先冻结公共接口 |
| S3 企业纵向切片 | WP6、WP7、WP8 正式工作台 | 选择智能体/模型→真实执行→成果的闭环 | 前端按冻结 API 接线，不 mock 冒充完成 |
| S4 第二插件与知识 | WP9、WP8 第二路径；WP10 发布/运维 | 两领域限定业务试点可验收 | 业务验收与技术实现分别记录 |
| S5 发布与演练 | 全量回归、恢复演练、业务/部署批准 | L3 上线决策 | 未完成适用必需项不放行 |

关键路径：WP0 → 运行/接口缺陷修复 → 输入/完成事实 → 成果封存/身份资源 → 工作台真实闭环 → 业务与部署验收。

**粗估，不是承诺工期：** 建议 1 名平台负责人、1 名插件/公共能力负责人、1 名前端负责人、QA 与 IT 按阶段参与。以现有功能为基础，整体约 45–75 工程人日（含相关自动测试，未含业务方等待、IT 采购/网络审批和正式合规验证）；3 名工程人员协作约 5–8 周是规划区间，不是上线日期。S0 结束后按故障注入结果、目标 OS 和 IT 接口成熟度重估。一个人顺序实施不能直接套用上述周数。

不建议把全部模块同时交给多个写入者：尤其 service/runs/store/worker 的接口与状态必须统一设计、串行集成。每个工作包交付代码差异、测试证据、限制和迁移说明，而不是只报“完成百分比”。

## 7. 各层发布门槛

### G-RC：工程发布候选

- T/F/P 对应适用用例通过；结构化结果/真实错误/取消/写入与目录边界无未修阻断项。
- 两插件独立消费与平台共享服务生命周期通过；安装文件、依赖、许可证、宿主兼容和制品摘要齐全。
- 全量门禁在冻结基线上通过，CI 证据和本地证据明确分开；公开接口破坏性变更与持久化迁移已处理。
- RC 只能声明验证过的功能和目标 OS；不因此获准真实项目或企业共享部署。

### G-PILOT：内部企业业务试点

- A01–A08、R01–R12、I01–I05 中对应试点功能的必需项通过；未实现功能明确不可用，不能把必须能力改成不适用。
- 工作台真实闭环、服务端恢复、授权下载和交互通道通过；没有预设回复代替执行。
- 使用真实项目前已有适用数据授权；业务范围、审核责任与退出条件明确。
- 至少完成两插件各自限定业务用例；未验收的格式、EDC 或部署环境不扩张承诺。

### G-PROD：企业正式部署

- 试点缺陷闭合；源码/制品/配置冻结；身份、隔离、撤权、备份/恢复、告警和回退实测通过。
- 业务责任人对指定输入/产物/用途完成验收，部署责任人批准目标环境，发布责任人批准同一制品。
- 企业共享知识启用时 K01–K08 必须通过；若暂不提供该功能，明确不开放，不能暗中使用无授权的共享库。
- 无未结清的执行未知状态被自动重试；未达适用必需门槛不得靠风险备注绕过规范。

## 9. 推荐第一批实际实施范围

先做一个可审查、可测试的“插件发布合同与文件正确性”批次：

- 两插件 canonical 输出与错误语义，连同真实 registry/PTC 入口测试。
- DVP 真实路径检查、默认无覆盖竞争和显式覆盖原子提交。
- Listing/DVP 耗时读取、解包和子进程取消传播，按实际同步/异步实现补测试。
- 对公共包公开导出与实际 pack 文件做一致性检查，保留合法捆绑方式，不以新增 src/* 掩盖私有 API。
- 同步当前状态矩阵，明确通过/未执行；本批不做企业身份、正式工作台或生产发布。

本批结束才能把“代码审计阻断”收敛为真实通过项。随后推进运行准入与完成屏障，避免先把不可靠后台包装成漂亮工作台。
