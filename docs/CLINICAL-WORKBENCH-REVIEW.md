# 临床工作台：角色评审方案、预审与决策登记

日期：2026-11-11 · v0.1 · **AI 独立预审草案，真实角色评审未召开，未批准开发**。

评审对象：[需求规格](CLINICAL-WORKBENCH-REQUIREMENTS.md)、[目标架构](CLINICAL-WORKBENCH-SOLUTION.md)、[角色知识基线](CLINICAL-ROLE-KNOWLEDGE-BASELINE.md)。这四份文档为本会话新增；既有源码/整改文档属于其他负责人，本轮不改。其他会话的独立反例审查为补充证据，不代替公司授权的批准。

## 1. 为什么不能再直接按页面开发

上次问题是从工程对象走到 UI，却没有以真实项目的长期工作、数据换版、程序复用、复核与交付检验产品闭环。技术验收和真实业务验收必须分开。先评审并关闭本切片问题，再进入实现；不能把“AI 模拟了各岗位”写成“各部门已通过”。

本轮已做：只读实现核查、行业候选整理、场景/架构草稿、反例预审及修订。未做：实际业务访谈、用户签字、生产接入、真实项目验收、代码修改、测试复跑或上线批准。外部官方正文获取受阻，规范条款证据仍待补核。

## 2. 评审参与者与责任

| 参与角色 | 需带来的事实/案例 | 需确认的内容 |
|---|---|---|
| DM + Listing 负责人 | 一个首次交付和至少一次数据更新案例，需求及独立预期 | 工作边界、批次/代码/检查/交付状态；稳定 issue 键 |
| DBD（全称待核）+ DVP 负责人 | 结构/方案/模板变更案例 | 数据库/规则职责、差异、UAT与EDC范围 |
| 统计 + 统计编程/QC | SAP/分析或程序换版例，盲态安排 | 预先指定/探索、复用证据范围、独立QC及盲态 |
| PM/项目负责人 | 阶段/里程碑/交接及客户回评例 | 项目状态、责任人、待办与交付接收事实 |
| CRC/CRA/CO | 中心任务/监查/协调及权限案例；CO全称 | 中心/项目范围、来源和关闭流程；不冒充研究者职责 |
| 医学/PV | 医学审阅与安全核对例 | 医学确认、时限和原系统责任；不与普通审核混用 |
| QA/合规 | 记录用途/SOP/受监管适用判断 | 复核/签名/保留/验证/偏差和批准边界 |
| IT/身份/数据/运维 | 身份源、数据/模型路由、部署与恢复约束 | 授权、执行位置、管理员/盲态、备份撤权与外发 |
| 平台/插件/runtime负责人 | 当前实现、锁定上游契约、测试能力 | 接口、单一权威、隔离、取消恢复及可扩展性 |

每项评审指定真实姓名/身份和职责；本稿不代填。用户批准产品方向不能自动代表 QA 批准监管用途或 IT 批准生产部署。

## 3. 评审方式与输出

### 3.1 需求走查

按需求 U01–U14 用合成或已有授权案例逐场景走查，既看成功，也看缺资料、结构漂移、权限撤销、运行未知、复核后改文件。对每个场景记录：角色、输入/版本、预期、错误后果、实际责任、系统边界、证据与未决项。

只评新页面截图不够；必须画清同一 Work 的 R1/B1/C1/D1 与 R2/B2/C2/D2 关系，并追问谁可看/谁复核/谁接收/失败怎么办。实际角色没有确认时保持 NOT_REVIEWED。

### 3.2 架构反例预审

从源文件位置、会话权威、版本变化、授权、并发及失败中反证方案。不把新增业务门禁变成普通工具调用审批，不重造 DSH loop。检查旧合同冲突和并行整改，避免重复建设。

### 3.3 交互评审

在需求与对象关系确认后，用低保真原型走完整流程：选择项目→确认资料与环境→首次工作→查看/补充→检查/复核→交付→新批次重跑→比较→再次交付。原型标明未接入状态；不以预设聊天作为真实模型证据。本轮不开发此原型。

### 3.4 评审记录字段

问题 ID、发现角色/人员、场景、文档版本、证据、后果、优先级、处理决定、责任人、目标版本、复验方式、实际复验结果、批准者与时间。结论用 NOT_REVIEWED / NEEDS_CHANGE / RESOLVED_PENDING_REVIEW / ACCEPTED；AI 只能记录预审建议，不能填实际角色 ACCEPTED。

## 6. 负向验收清单

- 同名项目、伪造 projectId、列表/计数/下载/事件越权，全部不泄露资料。
- 目录同名不同机器、扫描后被替换、映射盘离线、快照不完整，不标输入固定或运行成功。
- 模型目录可见但无凭据、route不可达、主调用与子调用路由不同，不显示已全面可用。
- Work建立后Run创建失败、POST重复/网络超时，不丢工作、不静默重复启动。
- 晚追加输入、待回答问题、客户端关闭/断流，不能凭旧结果宣布全部消费完成。
- Worker崩溃/睡眠/取消超时，无法确认进程和副作用时保持UNKNOWN，不自动重试。
- B2换数据、C1复用或生成C2，都不能覆盖D1或自动继承其结果复核。
- 复核后改文件、两个复核人并发、旧版问题迁移，不能静默覆盖或伪造认可。
- 本地session未归档，另一设备只看到元数据，不能写成完整历史已恢复。
- 应用卸载/版本升级、成果撤回或链接过期，不丢通用历史、不用新schema误读旧记录。
- 盲态信息不得通过摘要/日志/通知/模型/导出绕过已确认边界；边界尚未确认时不宣称通过。

## 7. 开发与正式使用门禁

**产品开发门禁**：针对拟开发切片，真实相关角色完成需求/交互/架构走查，阻断问题关闭，确认验收样例和版本；用户明确授权进入实现。当前为 HOLD，未满足。

**工程交付门禁**：核对目标DSH公共契约；单一写入负责人；实现相关正/反/故障测试和实际UI验证；按开发规范运行项目支持Node版本的聚合门禁。只报告实际执行的结果。

**业务与部署门禁**：真实授权案例、独立业务期望、IT授权/隔离/恢复、QA适用用途验证及必要批准分别完成；工程测试不代替这些。生产发布、配置变更、外发、提交推送仍按用户授权处理。

门禁用于需求开发和正式交付，不要求 AI 按固定工具顺序，不给普通已授权读取、R 编码和迭代加审批。

## 9. 当前结论

方向可进入实际角色评审，**不能写“评审通过”或直接开发**。最先闭环的是 Listing 首次交付→新数据重跑→代码复用/修订→本次检查与复核→新交付，再用 DVP 方案修订和第三类应用验证通用性。官方条款、公司职责与部署决策未核实部分保持公开未决。
