# 临床企业 AI 智能体工作台：需求规格（评审稿）

版本：0.1 · 日期：2026-11-11 · 状态：**待实际业务角色评审，未批准开发**。

本轮仅编写需求与方案，不改产品代码、生产配置或数据。AI 角色视角预审不等于公司各部门评审；单元测试、截图、模型自评不等于业务验收。配套：[临床角色知识基线](CLINICAL-ROLE-KNOWLEDGE-BASELINE.md)、[目标方案](CLINICAL-WORKBENCH-SOLUTION.md)、[评审与决策登记](CLINICAL-WORKBENCH-REVIEW.md)。既有开发约束仍以 [开发规范](DSH-PLUGIN-DEVELOPMENT-STANDARD.md) 为准。

## 1. 本轮纠偏

工作台不是“选择插件 + 输入提示词 + 看聊天”。它需要让临床员工在正确项目和授权资料范围内，使用可执行的模型与环境，持续开展工作、更新输入、修订程序、复核结果并交付可追溯版本。

截图明确暴露的体验问题：项目只有文本输入；本地工作目录与执行位置不可理解；模型选择和模型配置被混淆；执行器未配置却显示开始工作；历史工作、当前运行与交付状态缺少清楚关系。截图不能证明后端不存在相关能力，源码核对见方案的现状表。

产品原则：
- 项目、资料、代码、运行、会话、成果、复核分别建模，不靠一条“完成”概括。
- 一项长期工作允许多次运行；刷新、关闭客户端、换设备不丢失权威状态。
- 新数据不是失败重试；旧代码可复用，旧结果及旧审核不可自动继承。
- 应用来自发布登记，平台面向几十至上百个临床插件；不在通用壳里写 Listing/DVP 分支。
- 平台与 IT/API/执行环境执行授权；插件不增加按文件名或资料类别拒读，不给普通读取和 R 开发新增审批。
- Harness 自主规划、选择工具和纠错；业务复核门禁控制正式交付，不把专家 SOP 写成 AI 强制工具顺序。

## 2. 范围与非目标

### 2.1 本期需求对象

项目空间、临床应用目录、工作与运行、受管本地/中心执行环境、资料和程序版本、模型可用性、会话持久与恢复、检查与复核、版本化交付、角色待办、经验引用、运营诊断。

首个完整验证切片为 Listing 的首次交付与换批次重跑；第二切片为 DVP 方案/模板修订。其他部门用真实角色访谈和代表性场景验证共性，不因此承诺所有角色已有可执行插件。

### 2.2 非目标

不替代 EDC、CTMS、eTMF、统计正式生产系统或公司 SOP；不自动对受试者作医疗决定；不把 AI 草稿当正式临床裁定；不以功能清单宣布 GCP、Part 11 或电子签名合规。首期不做任意跨插件自动流水线，不重造 DSH Agent loop/provider/session 存储协议。

## 3. 角色与权限的区别

角色用于理解任务，不等于全局授权模板。DM、DBD、统计/统计编程、PM、CRC、CRA、CO、医学/PV、QA、IT/运维、项目负责人及申办方接口人参与需求验证。DBD、CO 的公司全称与职责**待确认**，不得按缩写直接分配权限。

同一人可在不同项目承担不同职责。人员与项目关系复用既有企业权威系统的事实；项目元数据可见、临床资料可读、程序可执行、成果可复核和成果可外发分别判定。公司超级管理员按既定受信角色映射支持全局业务查看，不向所有 Run 下发全公司数据权限；不得以新方案悄然推翻既有管理员决策。

## 4. 用户能回答的八个问题

1. 我是谁、现在在哪个项目，项目处于什么阶段？
2. 我在做哪项业务工作，负责人及协作者是谁？
3. 本次使用哪一版方案、需求、ALS、模板和哪一批数据？
4. 工具在哪里执行，实际 cwd 和授权数据位置是什么，R 等依赖是否可用？
5. 使用哪个模型路由，是否已配置且可用，资料会发送到哪里？
6. 当前是排队、运行、等待谁、失败还是退出未知？
7. 生成了哪版代码/结果，检查了什么，谁复核了哪个确切版本？
8. 下一次换数据，怎样保留历史、复用合适代码、比较差异并再次交付？

## 5. 端到端业务场景

### SC-01 项目入场与资料绑定

员工从可发现项目列表选择项目，看到稳定项目 ID、展示编码、阶段、本人职责和可用执行环境。从项目进入应用时继承项目上下文。无企业接口时仅能进入明确标识的本地开发项目，不用任意文本项目名冒充企业授权。

项目资料位置允许多个受控引用：方案、需求、元数据、数据批次等是资料角色，不强制每个插件具备同一张必填表。平台显示数据版本和位置；Agent 能在已获准范围发现资料，不要求员工逐文件预分类。

验收：同名项目不串数据；无授权项目不出现在搜索、计数和最近使用中；目录失效给真实诊断，不静默退回源码仓库根目录。

### SC-02 Listing 首次开发与交付

员工选择 Listing 及 Manual/Medical/PK/Report 中的适用类型，绑定当前需求/ALS/数据，说明业务目标。AI 使用现有工具和技能理解、编程、执行和纠错。输出程序、数据/Listing、检查证据和已知限制；是否需要独立程序 QC、医学复核及正式交付由实际 SOP 确认。

验收：交付能定位输入版本、程序版本、运行环境、真实检查与复核范围；未运行的目标服务器复跑不能显示已通过。PK 内部方法不是新平台入口。

### SC-03 同一 Listing 更换数据后重跑（核心）

例：工作 W-001 首次使用批次 B1、需求 S1、程序 C1，运行 R1，交付 D1。换为 B2 后，从 W-001 发起“使用新资料再次运行”，而不是覆盖 R1 或另建无关联聊天。

- 形成新输入基线 I2，展示 B1→B2 及其他实际变化；保留 I1。
- 员工可选择已交付程序 C1，AI 判断新结构是否仍适用；需要修订则形成 C2，不静默改 C1。
- 形成新运行 R2，冻结启动基线 I2 和起始代码 C1；若运行内生成 C2，另记实际执行代码与最终产物摘要，不要求启动前预知 C2。人工修改也产生代码修订，不就地改已交付代码。
- 纯数据复跑允许经应用执行能力运行已有受控程序，不强迫每次 AI 重新生成。程序不得静默改变，执行和检查事实仍经同一 DSH/平台合同登记；这不是平台另造执行引擎。
- 旧程序审核可作为有明确代码版本、用途和适用范围的历史证据引用；本次新数据/结果检查与必要复核仍要执行，不把一切历史证据一律判废，也不自动批准新结果。
- R1/D1 仍可查询；D1 标明适用 B1，不因 B2 出现变成“错误”，也不冒充 B2 当前成果。
- D2 在本次检查/复核要求完成后才能作为新交付；旧审核不自动迁移。
- 比较代码、规则、数据结构、统计行数和输出差异；新增/消失 issue 只能在具备稳定业务键时自动对齐，不能按行号猜测。

验收：一页可对照两次输入/代码/结果/证据；B2 缺文件或结构漂移不产生假成功；返回查看 D1 不触发重跑；结果更少不自动说明质量更好。

### SC-04 失败重试、继续会话与恢复

断开浏览器后重新打开是查询/重连，不启动新任务。确认仍存活的同一引擎执行可重连；崩溃后只有满足恢复合同才恢复同 Run。失败后重新执行是显式新 Run，关联前次失败。退出未知时先核对进程和外部副作用，不盲目重放。

员工在未结束 Run 补充要求，记录输入提交及是否已被引擎消费；Run 完成后新增指令通常创建下一 Run。改变项目或应用不悄悄复用旧运行。

验收：双击/网络重试不重复启动；取消请求与确认停止分别显示；流断开不标完成；设备睡眠、Worker 重启及租约竞争不重复写成果。

### SC-05 DVP 方案与模板修订

方案 P1/模板 T1 形成规则候选 V1；P2 修订后产生新输入和候选 V2，保留旧规则来源、修改原因及待澄清项。按规则标识和来源定位做影响分析，不能仅按 Excel 行号比较。没有原生 EDC 接口或未执行 UAT，明确显示参考/候选与未验证。

验收：新增/删除/修改条件及其来源可审查；历史规则不默认为当前项目正确；DVP 专属 Cover/Approval 等边界沿用该插件合同，不向所有应用扩散。

### SC-06 角色协作与交接

开发者提交一个确切成果包给复核人；复核问题绑定成果摘要与位置。修订产生新版本，旧意见保留、是否适用新版本由影响分析确认。离职、角色变更、代理复核和申办方回评按公司授权与 SOP 处理。

验收：A 项目 PM 不自动获得 B 项目权限；提交时改了文件，旧复核不能套在新内容上；聊天中的“好的”不是正式批准。审核不要求模型代替人，也不要求人逐步驱动普通开发。

### SC-07 跨应用与项目多任务

同一项目可同时有多个 Listing、DVP 和其他工作。平台按负责人、应用、批次、待办和阶段检索。把 DVP 成果作为另一工作输入时显式引用版本、项目和来源，不复制后失去血缘；跨项目引用另行核验授权及适用性。

验收：并发工作输出互不覆盖；应用下线仍能读历史通用记录；几十个插件不产生几十个顶层导航。

### SC-08 医学、统计与运营的不同语义

医学复核看 issue 证据及裁定；统计工作绑定方案/SAP/数据切点/分析集/程序/输出与盲态；PM 看里程碑和责任阻塞，不默认需要受试者明细；CRA/CRC 看所辖范围的待办和来源，不用 AI 直接改 EDC；PV 安全性事项保持原法定流程和时限。CO/DBD 的具体路径访谈后补充，不用猜测完成验收。

验收：通用平台承载证据、版本、待办，各应用提供领域语义；不把 Listing 的“通过”语义用于所有部门。

| ID | 需求 | 验收事实 |
|---|---|---|
| FR-01 | 项目选择与切换 | 服务端授权检索/分页；稳定 ID；切换不会改变在途 Run 的项目 |

| FR-15 | 成本与运行诊断 | 展示真实可取得用量/时长及失败原因；无用量不能填 0 伪造；预算规则待 IT/财务确认 |
| FR-16 | 经验引用 | 方法含来源、适用性、反例和验证范围；项目裁定不自动推广；运行绑定使用快照 |
| FR-17 | 备份、保留和恢复 | 控制记录、会话、输入、代码及成果分别有保留/恢复策略；恢复测试而非只写备份配置 |
| FR-18 | 受控正式交付 | 依适用用途/SOP执行复核；不因技术校验通过升级为正式业务批准 |

## 7. 状态语言（拟议业务语义，不是当前 API enum）

| 维度 | 示例 | 不可混同 |
|---|---|---|
| 项目 | 启动/执行/清理/锁库准备/分析/结题；实际枚举由企业系统确认 | 某个任务完成不等于项目结题 |
| Work | 草稿/开展中/暂停/关闭/归档 | 归档不删除会话或文件，也不等于完成业务审核 |
| Run | 排队/启动中/执行中/等待交互/取消中/成功/失败/取消/未知 | 成功只证明约定执行及完成屏障满足 |
| Artifact | 候选/已封存/已替代/已撤回 | 封存不是业务批准 |
| Verification | 未执行/通过/失败/部分/未知 | 没有证据不能通过 |
| Review | 未提交/待复核/需修改/已认可/已撤回 | 只对确切对象/用途/版本有效 |
| Delivery | 未交付/已交付/已替代/撤回 | 与外发授权和接收确认分别记录 |

变更不追溯改写历史事实。后续发现缺陷须建立影响关联和撤回/替代事实，而非删除原成功记录。

## 8. 非功能需求

- **授权与保密**：服务端按可信身份核验；IT 决定数据和模型外发范围、盲态及执行隔离；不把职责名称当数据许可。管理员查看、模型可见及正式解盲分别评审。
- **可追溯与复现**：版本/摘要/执行环境/输入输出关系可查询；“重新拿最新数据跑一遍”不是历史复现。算法随机性、模型变化及外部连接变化明确记录，不能承诺逐字节相同。
- **可靠性**：幂等、CAS、断流重连、取消竞争、未知副作用、故障接管、磁盘满及部分封存均覆盖。控制服务不能被领域程序死循环拖死。
- **多人和扩展**：按项目/工作隔离并发写路径；分页与查询服务端过滤；扩容依据真实并发/数据量，不按插件个数盲目拆服务。
- **可用性**：普通员工不用输入绝对路径、shell 或密钥；专家能查实际路径/日志。环境不可执行时允许保存草稿，不能用“开始工作”造成已启动错觉。
- **性能待定量**：代表性输入大小、并发、排队时延、事件刷新、恢复 RTO/RPO、审计保留、可访问性目标由试点冻结，不编造已达到的数字。
- **受监管用途**：QA 按具体记录用途和地区判定验证、电子签名、审计与保留要求；电子签名是单独能力，不能用普通确认按钮冒充。

## 10. 全生命周期补充需求（独立预审后纳入）

## 11. 项目与持久工作空间补充

已核对[独立蓝图 §6.1–6.2](clinical-workbench-review/00-product-blueprint.md)。对方会话记录的用户补充在此作为待共同评审的需求来源，不视为本会话新的开发批准。

- **FR-27 项目建立与未来企业绑定**：获授权人员可新建平台项目，记录稳定ID和来源；企业目录接入后显式绑定外部ID，保留原历史，不按同名合并、不无规则双写。
- **FR-28 持久项目工作空间**：选择项目后选择或获授权登记ProjectWorkspace，绑定真实服务器目录/资源、节点、程序/输出位置及配置版本。已有服务器数据直接登记/受控映射，不强制上传。唯一可用空间可预选，返回工作继承原空间。
- **FR-29 项目Listing历史**：按项目、空间、应用和批次查看多项Work及其Run、代码、会话来源、成果、检查和交付。线下旧程序/结果可作为历史导入，但必须标来源和未知信息，不伪造Run、模型或QC批准。

对象关系为 **Project → ProjectWorkspace → Work → Run → Session/成果/证据**；一项目多空间，一空间可有多应用多Work。持久空间不是单Run的cwd，也不是一条无限会话。目录改名不改变workspaceId；配置改版不改写旧Run位置。数据权限由可信环境落实，不按文件类别另设拒读。

验收须覆盖同名不同节点目录、未授权空间ID、相对路径兼容、并发输出防覆盖、源数据防误写、空间改版历史和线下导入真实性；全部待实施。相对路径程序的布局适配必须实测，不能假设逐Run新cwd天然兼容原服务器目录。

## 12. 冻结条件与评审出口

本稿不是让用户一次填写全部细节。各角色用合成/已授权代表性案例走查，并记录问题、责任人、处理方案和复验事实。DBD/CO 名称、复核层级、数据位置、模型路由与保留期限等未知项集中在评审登记。

开发启动要求：本次拟开发切片涉及的阻断问题全部关闭；相关实际业务角色、平台与 IT/QA 确认其职责范围；形成已批准版本、可执行验收样例、源代码范围与唯一写入负责人。尚未实施角色可以后续扩展，但不得宣称已覆盖。需求修订与本轮评审结论一起保留，不靠口头“差不多”绕过门禁。
