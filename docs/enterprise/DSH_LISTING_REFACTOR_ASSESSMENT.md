# dsh Listing 重构评估：以真实服务器目录承载 ZCode 级交付闭环

- 日期：2026-10-20。
- 性质：**现状核查、架构评估与重构建议，不是实施完成报告。**
- 范围：当前工作树中的企业插件、既有设计文件、ZCode 生成/审查指引、三个本地服务器同步副本的目录，以及用户追加授权的 Manual 与两个 PK 交付程序源码。
- 本轮操作：只读代码、枚举同步目录；执行不加载项目数据的内存合成探针。项目程序阅读屏蔽凭据相关行；不读取临床数据单元格，不执行真实项目，不启动服务，不改业务代码/安全开关/输入目录。
- 使用项目 A/B/C 中性代称；方案不依赖具体研究名称、固定 listing 数或某次数据量。
- 历史会话证据沿用上一轮已取得的用户纠正、执行记录及报告。本轮没有重新完整读取所有历史会话，也未审计 ZCode 的实际模型网络载荷。

## 1. 结论：应当改的是执行模式，而不只是增加白名单

**建议将现有“文件分类 + 若干独立车道 + 文本扫描拦截”的组合，重构为“统一项目材料清单 + AI 自主编程 + 本地计算和诊断 + 独立 DM 审查 + 统一模型出口”。**

目标是：用户提供服务器同步项目和需求，智能体能自己发现材料、解释每条需求、建立映射、编写单文件 R、本地反复验证、修复、审查后交付。用户不应继续承担“每次安全报错以后换工具/换目录/补提示词”的工作。

**按用户最新定案，目标为四场景：`manual / medical / pk-mapping / report`。RBQM彻底退出本轮目标：其独立场景、知识、规则和专属验证案例直接弃用，不迁入Manual或其他场景，也不保留rbqm→manual的兼容映射。** 此条明确取代本报告此前“并入Manual并保留经验”的版本。现有代码/旧文档仍有旧路由，实施时须清除相关有效入口和引用，不能声称本轮已删除代码或原文件。Manual/Medical共用完整识别处理核心但保留两个入口；PK按两个成功交付项目的BE和SAD/MAD经验建设；Report保持独立报表/汇总场景。

这不等于关闭安全：

- 本地 R/Python 必须能使用完整数据计算，不能因代码提到数据文件而禁止执行。
- 模型必须获得完整的获准需求、结构、足够的验证证据和可修复诊断。
- 两类保护对象是数据集行值、辅助数据业务值；换成日志、Excel、RDS或知识条目不改变保护属性。
- **按用户最新补充：默认不释放上述业务值；当具体spec需求确实需要某一列的场景值时，允许系统按需求生成该单列的最小必要视图。真实敏感内容必须先在本地脱敏并验证后，才能交给AI；不能先发给AI再让AI脱敏。** 不敏感的场景/设计词表也须确证范围，不是整表豁免。详细合同见§8.6。
- 正式交付由证据和验收结果决定，不由“模型说完成了”或“程序 exit 0”决定。

### 本轮核实后，不能再沿用的几个结论

1. **不能说“ZCode 没警告，所以一定满足了同一数据边界”。** 历史流程确实表现出更完整的取证与修错能力；但两边是否接入相同守卫、是否发送过数据值，本轮未审计。零告警是体验事实，不是同等安全认证。
2. **不能把 dsh 的所有旧误拦都说成还没修。** 路径参数原子处理、发现型工具放行、部分错误分类和额外上下文处理已改进；剩余机制问题仍存在。
3. **不能要求把需求搬到 `doc/`。** 当前服务器同步目录本来就不是这一契约。目录负责定位，材料内容与授权范围负责角色判定。
4. **不能把双编程零差异说成“百分之百理解需求”的证明。** 两份程序可能共享同一错误解释。它证明特定输入、版本和比较合同下的一致，还需要独立需求审查、反例与必要的 DM 澄清。
5. **不能把待确认项写进清单就视为可交付。** 可以继续不受影响的探索和开发，但影响结果的未决项不能获得正式通过。
6. **不能一边宣称 `Project_Data` 只读，一边默认在其中解压、写缓存并删除 SAS。** 当前 R 模板确有这些副作用，需明确迁移。

## 2. 先看真实目录：本轮实际枚举结果

以下仅来自目录与文件类型统计，没有打开文件正文。因此 `.xlsx` 的存在不等于已确认它是 spec、ALS 或医学编码表。

### 2.1 项目 A：Manual Listing 同步副本

```text
<项目A根>/
├─ [根目录有 8 个 .xlsx 候选，角色尚不能仅凭位置确定]
├─ Project_Data/
│  └─ 01_Raw_sas/Manual Listing/
│     ├─ 20260907/                 .zip、.RData、.xlsx
│     └─ 20261013/                 .zip、.RData、.xlsx
│        │                        70 个 .sas7bdat、.sas7bcat、.sas 等
│        └─ sas7bdat/              当前为空；实际 SAS 在日期目录本层
├─ SAS_Program/
│  └─ SAS_program/Manual Listing/  1 个 .R、2 个 .xlsx
└─ Output/
   └─ 04_Out/Manual listing/       .xlsx、.RDS、.json
      └─ _diag/                   .csv、.tsv、.json、.py、.R 等诊断工件
```

**本案事实：**日期子目录出现在输入侧；程序和正式输出侧未见日期子目录。此项目没有 `02_Raw_csv` 输入树，不能把 `_diag` 中 CSV 误认成原始输入。

### 2.2 项目 B/C：PK Mapping 同步副本

```text
<项目B或C根>/
├─ Project_Data/
│  ├─ 01_Raw_sas/PK Mapping/<投递批次>/
│  │                            .zip、.RData 等
│  └─ 02_Raw_csv/PK Mapping/<投递批次>/
│                               实际为 .xls / .xlsx，另有 .txt
├─ SAS_Program/
│  └─ SAS_program/PK Mapping/   .R、.xlsx 等
└─ Output/
   └─ 04_Out/PK Mapping/        .xlsx、.RDS 等
```

- 项目 B 的两条输入树均见 `20260914 / 20260916 / 20261015` 批次。
- 项目 C 的两条输入树均见 `20260910 / 20261020` 批次。
- 两者程序/正式输出层也未见日期子目录。
- **`02_Raw_csv` 是业务目录名称，不是文件格式声明。** 实际输入是 Excel，必须使用实际文件格式解析器。
- 程序目录的 `.xlsx` 还可能是比对键配置等文件，不能全部当 ALS。

### 2.3 日期目录应该怎样处理

用户已说明目录按服务器真实结构构建，日期层可以按当前批次/运行生成。系统应保留这一行为，但不能把几个不同概念压成一个 `dataDate`：

| 概念 | 来源 | 不允许的替代 |
|---|---|---|
| SAS 输入批次 | 已选投递目录及输入版本 | 不能用今天日期代替 |
| 外部 Excel/CSV 批次 | 已选外部源及关联证据 | 不能静默取另一目录“最新文件” |
| 本次执行日期 | 运行配置/本地当前日期 | 不代表数据实际采集日期 |
| 输出目录/文件后缀 | 当前场景和服务器交付约定 | 不能从某次旧输出目录反推通用规则 |
| 旧版比对基线 | 明确的旧产物版本 | 不能默认“最后修改的文件”或当前产物自己 |

**推荐行为：**自动识别已存在的日期层；在既有契约要求创建日期层的位置，创建本次对应日期目录；不要求用户重排目录，也不强行把所有场景改成相同层级。三个样本只能证明目前存在的结构，不能仅凭目录时间戳推断所有项目的生成规则。

## 3. 现有 dsh 实际设计：不是一条完整的智能体流水线

### 3.1 两条相互分离的执行链

```text
Python/工作簿链：
inspect → 需求分片/元数据 → run_code → 内存 outputs → publish

R 程序链：
project + studyKey + dataDate
  → 渲染模板 → 立即运行 R → summary 回执
  → AI 编辑业务区 → render=false 再运行

外围安全：
tool-audit 前置检查 + listing 后置扫描
+ 若干按工具名、前缀、路径的豁免
```

代码定位：

- `packages/enterprise/listing/src/index.ts:427-582`：Python 链工具。
- `packages/enterprise/listing/src/index.ts:655-703`：R 链提示词和执行约定。
- `packages/enterprise/listing/src/r-runner.ts:351-488`：模板准备、R 执行、摘要读取。

**核心断点：**需求、数据批次、程序版本、审查证据、发布版本，没有贯穿两条链的同一份身份记录。R 能跑，不等于它所使用的需求、数据和前面的 inspect 是同一批。

### 3.2 最近已有改进，应保留而不是推倒

当前工作树已有：

- 前置保护中的完整路径参数处理、部分发现型工具支持。
- 扫描故障细分为 `SCAN_*`，不再所有失败都使用同一条提示。
- `analyze` 工具及 schema/key/join/rule/compare/run_status 操作。
- Python 预编译与运行阶段拆分。
- Python 会话 `snapshotId` 与输出绑定；重新完整 inspect 会产生新快照并清旧输出。
- Python 工作簿写入有临时文件、备份及回滚机制。
- R 工具每次运行使用独立临时 summary 路径，退出码和 `status=ok` 都满足才成功。

定位：`code_runner.py:123-146`；`worker.py:727-730,994-1064,1123-1130`；`python/excel/build_workbook.py:388-445`；`r-runner.ts:422-448,486-488`。

**但上述能力不是完整的持久运行状态机。** `run_status` 仍不等于“本轮编译、执行、审查、发布全过程的准确状态”；重新运行失败后，同一快照中的旧成功 outputs 仍可能存在。

### 3.3 发现阶段已可能选错材料，问题早于写 R

当前 Python 数据发现会递归整个项目，松散文件优先于归档，以大写文件 stem 作为逻辑数据集名，首个来源占位后，后续同名来源会被跳过。它没有与 R 一样的明确输入批次选择，因此旧日、当前日和诊断 CSV 可能进入同一逻辑数据集合；首个读取失败也不能因此视为后续正确候选已加载。

定位：`python/discovery.py:224-236,372-396`。

需求读取还有两处根本性差距：

- 没有 `doc/` 时可能返回空需求清单而不报“缺少必需 spec”；根目录需求 Excel 被当成辅助表，不等于模型已经看过需求。定位：`worker.py:776-807`。
- AGENTS 的六列白名单/Cover 禁读尚未在所有 parser 路径落实；当前 Excel 文档读取存在全 sheet、全行全列序列化。定位：`discovery.py:693-709,828-842,992`。

所以应同时修“该读的读不到”和“不该读的先全读再过滤”，不能只补一个文件名关键词。

主数据内存快照与扫描索引还可能不同步：前者保持 inspect 时的内容，后者在后续 bind 时按当前磁盘刷新。缺共同版本握手时，不能说整个任务始终使用同一快照。定位：`index.ts:292-297`；`worker.py:569-607,994-1001`。

### 3.4 当前模板也不是严格意义上的“零业务”

B1/B2/B3 的业务生成区已经存在，方向正确。但模板契约区仍有特定医学编码页名、CS 判定及列裁剪行为。不能仅因存在生成区就认定模板完全中立。

定位：`r-templates/manual_listing.R.tmpl:762,781,999-1004`。

应将这些内容分别归类：

- 真正通用的文件读写、解码/关联原语、样式：留在公共层。
- EDC 特有格式绑定、记录层级、编码页规则：放有版本的适配器。
- 研究特定业务条件、列集合、访视、判重键：由 spec 生成到项目程序。

## 4. 为什么会反复触发安全告警

### 4.1 当前仍把“提到文件”与“读取受保护内容”混在一起

路径键的原子处理已改善，但通用命令字符串仍可能被按 token 检查后缀。

本轮纯函数合成探针确认：仅输出某个 `.csv` 文件名的命令文本仍可能被拒；带空格的需求路径置于命令字符串中，也可能被拆分后误判。

**问题不在于某个扩展名要不要加白名单，而在于没有区分能力：**

- 列目录、查文件是否存在；
- 读取获准的 spec 范围；
- 本地脚本使用 SAS 计算；
- 将 SAS 行值回传模型。

这四种行为的安全意义不同，不能用同一个“参数是否有 `.xlsx/.csv`”判断。

定位：`tool-audit/src/dataset-guard.ts:213-250`。

### 4.2 全局同值扫描丢失了来源

本轮使用纯合成内存数据验证，没有读取真实数据：

| 输入/结果形态 | 观察结果 |
|---|---|
| 普通诊断词与合成数据值同字 | 扫描命中 |
| 合法计数字段与合成编号同数值 | 扫描命中 |
| 无关句子只共享相邻词片段 | 扫描命中 |
| 合成值经另一种表示转换 | 可能不命中 |

这是**全局同值/片段误判**，不是证明加密哈希算法发生了碰撞。实现定位：`python/worker.py:186-270,450-505`。

结果就是：合法需求、代码、计数可能被拒，而变换后的内容又可能漏过。不断加词长、数字长度、词表例外，只会把误判转移到下个项目。

**应当先判断来源与生成操作，再做补充扫描。** 已核准的需求片段不能因为某个字也出现在数据里就被否定；原始行值也不能因扫描未命中就自动放行。

### 4.3 豁免与拦截同时存在，所以体验和安全都不稳定

当前后置链仍存在：

- shell 名单整体放行；
- 某路径字段落在 `Output/04_Out` 时整体放行；
- `enterprise_` 前缀除部分工具外整体放行；
- 未绑定当前 Agent 项目时放行。

定位：`listing/src/index.ts:834-850`。

这会造成相同材料经不同工具、不同目录得到不同待遇。**不能以警告少作为安全提升，也不能以警告多作为真正发现泄露。**

应先提供等价的安全诊断/分析能力，再统一替换这些豁免；不能先全部封死，让模型盲写。

### 4.4 目录分类与扫描失效范围不一致

实际服务器的 `Output/04_Out` 没有被 discovery 整体作为产物排除：旧工作簿可能被当辅助输入，`_diag` 中 CSV 又可能被当数据集。

但扫描指纹逻辑会忽略 `output` 目录。于是出现“参与发现/装载，却不参与相同失效规则”的不一致。

定位：`python/discovery.py:103-124`；`python/worker.py:513-536`。

此外，当前扫描算法已有修改，但缓存版本仍为 5，缓存指纹不含算法版本；旧索引继续生效是**有静态代码依据的风险，未读取真实缓存验证**。不能直接断言用户当前每次告警都来自这一项。

### 4.5 原始错误被拿走了，安全替代诊断又不够完整

Python 已将部分原始运行错误扣留，这是边界要求；但若只剩一句“执行失败”，AI 无法判断是字段名、类型、零行还是路径问题。

R 又走另一条路：summary.message/warnings/listings 仍作为回执输入，且普通 R warning 不都进入 `note()` 的摘要；会出现既有潜在出域字段，又遗漏正常故障线索的情况。

定位：`worker.py:1017-1023`；`r-runner.ts:450-483`；`manual_listing.R.tmpl:140-141,1114-1118,1155`。

**修复方向不是恢复全部 stdout，而是提供足够准确的结构化诊断。**

## 5. 与 ZCode 全流程相比，真正缺少哪些能力

| ZCode 过程中发挥作用的能力 | dsh 当前缺口 | 改造目标 |
|---|---|---|
| 围绕真实服务器同步材料持续工作 | doc/、全树发现和 R 固定子路径是不同规则 | 一份服务器布局和材料清单 |
| 逐条推敲 spec，不满足就回原材料核查 | 读过分片并不等于语义完整；无强绑定理解记录 | 逐需求理解记录、定位、版本及冲突台账 |
| 自写小探针验证字段、编号、拆行假设 | 原始结果不应出域，但现有安全替代证据不足 | 本地自由计算 + 固定范围安全证据 |
| 编写完整 R，反复运行修复 | 首次渲染即执行；摘要与实际产物验证不足 | prepare/execute/review/release 分离 |
| 独立 DM 审查、逐项复核 | 主要靠提示词或临时脚本，没有持久验收对象 | 独立审查上下文、验证工件和覆盖账本 |
| 换新会话收尾而不重做全部 | 状态主要在 Agent 映射与 Worker 内存 | 版本化任务清单和恢复状态 |
| 锁定最终代码后服务器复跑 | 本地可跑与服务器可跑未独立验收 | 同一代码版本、环境参数切换、干净环境验证 |

### 5.1 必须同步解决知识层冲突

本轮读到的生成入口与企业知识库并不完全一致：

- 用户级 `manual-listing-r/SKILL.md:71-78` 写 DM Comments 等列禁读、按原始行数计 listing；企业 `manual/listing-manual.md:12-20` 又要求按评审定案态识别删除/合并。
- 生成入口 `SKILL.md:102-104` 写每类 flag 抽 1–2 条；独立审查入口要求逐 listing 全量覆盖。
- 生成入口仍有示例值直接导出建议；本轮目标要求默认保护业务值，必要的单列场景视图须走本地敏感性判定、脱敏和释放验证，不能原样打印后再审。
- 有的历史模式说明会回退原始术语，而当前编码门禁要求未命中置空。

**这不是只换一个模型就能解决的问题。** 同时注入互相冲突的指令，会让模型选择不同工作模式。

按用户最新要求：**原dsh知识整体隔离，新重构建立独立知识代际，不在旧库上就地叠加修补。** 新库从用户确认的成功交付项目、获准spec/澄清及重新验证的证据提炼；旧文档仅用于本轮识别冲突，不能自动成为新库规则来源。个人旧技能镜像也不自动注入新profile，不删除或覆盖用户全局文件。具体隔离范围与验收见§11.6。

### 5.2 历史过程不能全部机械复制

上一轮流程说明中的以下表述不能作为本轮验收原则：

- 用一个更宽的规则得到更多 flag，不代表这些都是真阳性；没有独立真值，不能直接称某个比例为误报率。
- 数据中没有 spec 要求的字段，不授权程序自行删除条件或用相近字段替代。
- 其他需求被 DM 判 Pass，只能提供参考，不会自动批准本条的不同口径。
- 即使允许阅读判定说明，辅助文本也不能自动推翻明确编程条件。
- 历史实验室口径经历变更，不能把某一阶段的“不拆分”固化成所有项目规则。

**要复用的是取证、反证和纠错方法，不是复用历史会话里每一个临时判断。**

## 6. 推荐目标架构：统一任务身份，分离计算与模型可见内容

```text
用户：服务器同步项目 + 本次任务/需求版本
                        │
                        ▼
       Project Context / 材料与运行清单
       布局、源版本、批次、需求范围、输出规则
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
       需求/设计安全阅读       本地数据执行区
       spec、ALS、格式绑定    原始值、辅助业务值、日志
              │                   ▲
              ▼                   │
       AI 需求分析与写码 ───→ R/Python 执行器
              ▲                   │
              │          本地结果、错误、验证工件
              │                   ▼
              └──── 安全证据与诊断出口
                        │
               独立 DM 审查与修复
                        │
              交付资格/版本/环境核验
                        │
                        ▼
          单文件 R + 用户本地可读产物和审查报告
```

**一个任务上下文，不是一个万能进程。** 读数、模型代码、可信分析、模型出口应保留职责隔离。生成区可以表达任意项目逻辑，但不能自行签发“我已安全/我已验证”的可信结果。

### 6.1 不再新增四个面向模型的碎片工具

上一轮建议新增 requirements/matrix/qc/gate 四工具，会与现有安全重设计的 `analyze` 路线重叠。本轮建议收敛：

| 现有入口 | 改造职责 |
|---|---|
| `enterprise_listing_inspect` | 发现真实布局、列材料候选、绑定项目/批次/版本；返回同一个 contextRef |
| `enterprise_listing_read_document` | 按 spec/ALS 的批准 sheet/列/行范围分页；返回定位与版本 |
| `enterprise_listing_read_metadata` | 获准结构、格式绑定、关系和设计词表；不直接返回自由文本去重值 |
| `enterprise_listing_analyze` | 扩展映射验证、拆分形态、范围覆盖、独立工件比较、运行状态和spec驱动的单列脱敏视图；承载需求/审查记录的受控校验 |
| `enterprise_listing_run_r` / `run_pk` | 分 prepare 与 execute；使用同一任务清单、本地诊断、输入及程序版本 |
| `enterprise_listing_run_code` | 保留 Python 本地自由计算，不强迫它成为 R 项目的主交付程序 |
| `enterprise_listing_publish` | 扩展为运行版本和交付资格的提交；R 工件不再由 Python 重写样式 |
| `enterprise_listing_kb` | 只读取新代际基础库与学习库，不回退旧库；扩展受控捕获、校验、去重和版本写入，验证后的同EDC/场景经验自动生效 |

门禁和任务台账主要是**宿主状态**，不是让模型不断调用一个 gate 工具为自己盖章。

## 7. 第一项重构：服务器布局与材料角色彻底分离

### 7.1 发现目录，不搬目录

从用户提供的项目根开始：

1. 定位 `Project_Data / SAS_Program / Output`；保留服务器原大小写和空格。
2. 在数据侧识别 `01_Raw_sas`、`02_Raw_csv` 等已有类别及其场景/批次层。
3. 文件格式按实际容器识别，不按目录中 csv/sas 的词判断。
4. 根目录、程序目录及用户指定位置都可作为需求/设计材料候选；不要求新增 `doc/`。
5. `Output` 是交付和诊断来源，默认不回灌为新源数据；旧产物只在明确 baselineRef 时加入比对。
6. 日期目录、程序目录中的 Excel 逐个区分需求、设计、编码/外部业务、键配置，不一概放行或一概屏蔽。

当前 `discovery.py` 的目录分类与 R 模板各自找文件，应共用这个结果，而不是各自重新递归扫描。

### 7.2 材料清单最少要记录什么

以下是建议字段，不是现有实现：

```text
projectRef / layoutVersion
localRoot 与 serverRoot 映射（仅宿主本地保存）
scenario
requirements: 文件引用、内容版本、批准范围、评审版本
sourceInputs: 数据源引用、批次、环境、格式、内容版本
auxInputs: ALS/格式目录/编码/外部表/键配置的分别引用
baselineArtifactRef + version
outputLayout: 固定目录或既有日期层、日期语义、命名合同
programVersion / adapterVersion / policyVersion
```

同一 `dataDate` 可以是缺省便利参数，但必须在每条实际源映射中落实。不同来源不同批次并非自动错误，**静默串批才是错误**。

实际已交付 PK 程序还要求补两类来源信息：

- **原件→解密副本→格式转换副本的关系。** 多文件并存时记录为什么选某一份；排除 Excel 锁文件，但不能把某项目“唯一 XLS 优先”的经验当成全局格式优先级。
- **生成时依赖与运行时依赖分开。** spec/ALS 可用于生成与审查，而最终 R 可能已内嵌经验证映射，不再运行时读取 ALS。不要为重构无故增加服务器必需文件；仍需记录生成依据的版本。

### 7.3 多版 spec 不按文件名“最新”直接定案

自动列出版本候选，依据已批准的版本、任务上下文及明确评审状态选用。文件修改时间、名称含 R1 或黄色填充只能作为线索，不能独立赋予语义权威。

生成阶段默认保持现有需求列白名单与 Cover 禁读规则。用户明确要求处理 DM 反馈时，只扩展该任务必需的反馈范围，不能借“完整理解”读取所有审阅/封面内容。身份索引用文档引用、版本、sheet 和行定位；不依赖读取被禁的 ID 列。

### 7.4 输入只读与缓存分开

当前 Manual 模板以日期源目录解压/写 RData，`zip_clear` 还会清理目录树中的 SAS；PK 模板存在同类行为。定位：`manual_listing.R.tmpl:122,228-266`。

建议默认：

- 源 zip、已投递 SAS、外部 Excel 不改、不删，不要求源目录可写。
- 解压与新缓存写到约定输出根下的宿主管理工作区或已配置 scratch；不得静默换盘。
- 只清理本轮登记的解压成员，不能按 `*.sas7bdat` 扫树删除。
- 已有 RData 允许作为候选输入/旧缓存，但须与源版本关联；只有它存在而缺原始包时，明确以它作为输入，而不是声称验证了不存在的源。
- 缓存键覆盖源内容、格式目录、适配器和算法版本，不能只凭文件名存在。

### 7.5 不再跨日期“找一个能用的编码文件”

当前编码回退可递归到 `folder_path` 全部批次，而不只是选中的数据日。定位：`manual_listing.R.tmpl:588-591,697-700`。

改为：本次清单明确指定 → 同批次确定候选 → 报告缺失/冲突。跨批次复用只能依据明确版本关系，不自动回退。

## 8. 第二项重构：让模型获得足够证据，而不是让它看不到数据后只能猜

### 8.1 安全不应拦什么

- 查看目录、文件存在性、格式/结构。
- 阅读获准 spec 条目、ALS 定义、字段标签、格式绑定及设计码表。
- 阅读/编辑已登记、内容版本与来源均确证的生成代码。运行期改写或嵌入数据字面量的副本不能继承旧授权；文件扩展名是 `.R/.py` 也不自动放行。
- 在本地运行任意合理 R/Python 数据处理逻辑。
- 获得已批准范围的覆盖、关联、重复、类型、拆分与差异证据。
- 在spec确需时获得经本地范围核验及脱敏验证的单列场景视图；符合合同的正常请求应自动完成，不需要逐列反复问用户。

### 8.2 安全必须控制什么

- 原始和派生行值的 stdout/stderr、动态异常正文、输出工作簿回读。
- 把数据值变成列名、文件名、图片或 JSON key 再返回模型。
- 来自任意脚本的 `safe:true`、summary、QC=PASS 自声明。
- 经子代理、历史压缩、spill 文件、附件、最终工具上下文进入模型的内容。

### 8.3 补充证据操作，不把生成能力缩成有限规则语言

| 需求理解问题 | 建议本地验证 | 模型应获得的证据 |
|---|---|---|
| 用哪一个临床意义字段 | 核对 ALS 与列自身 format 绑定 | 已批准字段/格式引用、是否确证 |
| 访视文字能否对应数据 | 用设计词表中的候选与数据匹配 | 覆盖/未匹配/歧义统计，候选引用 |
| 编号是否一对多、会不会串受试者 | 编号/关联基数检查 | 基数冲突、空键与未匹配计数 |
| 分号多选应展开多少行 | 登记解析合同的形态分析 | 段数/可解析/异常/展开量统计 |
| 日期部分未知是否被丢弃 | 对登记日期语义做保真检查 | 保真失败计数与需求引用 |
| 编码为何全空 | 文件存在、结构、候选键覆盖检查 | 缺文件/零交集/键不匹配等分类证据 |
| 最终产物是否符合清单 | 独立读取工件比较 | 行列/顺序/类型/标签/值层差异计数、批准字段引用与结论；逐格旧值/新值只留本地 |

这些操作是**给推理提供证据**，不是代替 R 业务代码。遇到新逻辑，模型仍可写新的本地程序；该程序的输出仍须经安全投影，不自动信任它的计数或结论。

### 8.4 两个必须明确的边界

1. **列基数用于数据特性判断，不单独授予出域权限。** 一个很小的表也可能全是个人信息；原始去重值不能只因低基数就整体释放。设计码表与观测数据值必须区分。
2. **聚合数字不是自动安全。** 只释放有任务范围、指标定义和来源依据的结果，避免任意单人筛选和重复差分探测；同时不能因合法计数恰好等于某个业务值就误拦。

不能为了安全把一切有用诊断都扣掉，也不能为了可用性把任何标为 aggregate 的 JSON 都放行。具体可释放指标在插件策略中版本化，正常任务无需用户逐条批准。

### 8.5 无法消除的能力边界

先使用获准spec/ALS/结构、本地验证以及§8.6的最小必要场景视图，不因“涉及数据值”就默认要求人工。若仍只能依靠未获准的敏感自由文本判断，或不能同时满足脱敏安全与业务语义保真，则返回 `NEEDS_LOCAL_DM_REVIEW`，明确是哪项信息缺口。它是本地待确认，不是笼统的数据泄露告警，也不是 PASS。

可以继续其他条目，但不能承诺任何脱敏方式都保留全部信息。本地模型若参与判别，须有明确本地运行、无外传和授权范围；不能先把原值送给云端“判断是否敏感”，也不能把原始上下文留在后续脱敏对话里。

### 8.6 spec驱动的单列场景视图：先本地转换，后最小释放

**用户最新授权取代“所有业务值一律不得进入模型”的绝对规则。** 两类保护对象仍为①数据集行值；②辅助数据业务值。默认留本地；具体spec确需某一列的场景值时，允许系统生成该列的最小必要视图。确证非敏感的场景/设计词表可按范围释放；真实敏感内容必须先在本地脱敏/转换并验证，不能借“单列”原样外发。

单列、低基数、少量样例、换成哈希均不是安全证明。受试者编号、日期、自由文本、浓度序列即使仅一列，也可能敏感；假名化不自动等于匿名化。

#### A. harness大脑与本地执行器分工

```text
获准spec + 获准结构 + EDC/场景知识
  → AI说明：哪条需求，需要哪个字段的什么性质
  → 本地宿主核验用途、列、批次、范围和最小必要性
  → 本地敏感性判定 + 选择已验证变换 + 生成候选视图
  → 独立校验安全性与本次需求所需语义是否保留
  → 宿主批准精确视图版本后才给AI
  → AI迭代R代码 → R在本地原始数据上执行 → 独立原始数据验证
```

AI可以基于spec提出“需要理解访视词形/打包编号格式”等请求，也可提出转换策略候选；**本地可信模块负责实际判定、变换与释放**。不能让云端大脑先看原值再决定如何脱敏，也不信任任意脚本自报的“脱敏完成”。

符合合同的常规请求自动处理，不逐列询问用户。不能确证时先缩小范围、改用统计/合成视图或本地规则验证；仍无法处理才明确升级，不建议关闭安全开关。

#### B. 视图选择：保留所需语义，而不是为了发送而破坏数据

| 所需信息 | 优先给AI什么 | 留在本地的内容 |
|---|---|---|
| 访视/表单/分类枚举 | 先ALS/设计码表；必要时已确证非敏感的单列去重标签 | 每人对应值、行序、频次和额外关联列不自动提供 |
| 打包编号格式 | 本地解析的结构说明与合成例子，保留分隔符和字段结构 | 真实编号、疾病自由文本、日期 |
| 两端键的等价与连接形态 | 默认关联覆盖/基数；确需示例时限任务范围的一致令牌或合成例子 | 原编号、逆向映射、跨任务可链接身份 |
| 日期先后/时距/部分未知 | 默认本地比较结果；必要时经验证的相对/平移视图或合成模式 | 真实日期、偏移映射和可识别背景 |
| 数值单位/格式/边界 | 结构、约定单位、合成边界例、本地结果；必要时验证过的范围化视图 | 原始个体值、可反推精确值的高精度序列 |
| 辅助表术语/场景词匹配 | 先设计词表/本地匹配；必要时确证非敏感的最小术语集合 | 记录级业务行、身份及稀有可识别上下文 |
| 自由文本语义 | 本地去标识/归类并核验的最小片段；不可可靠处理则给本地分类证据 | 未脱敏叙述及可识别信息组合 |

令牌只保留等价关系，不保留真实词义；哈希可能被字典反推。日期平移不必然保持日历规则，数值分箱不保持精确计算。必须记录并验证本需求需要的性质，丢失这些性质时换方法，不能基于失真的视图继续宣称理解正确。

#### C. 扩展现有分析入口，不新增原值读取后门

建议在 `enterprise_listing_analyze` 中增加 `scenario_view` 操作：

```text
请求：contextRef / snapshotRef / requirementRef
      resourceRef / fieldRef / purpose / requiredProperties / scopeRef

本地记录：sourceVersion / transformPolicyVersion / transformerVersion
          transformationPlan / preservedProperties / lostProperties
          privacyValidationRef / utilityValidationRef / releaseVersion / queryLineage

回执：released | transformed | withheld | needs_local_review
      viewRef / approvedFieldRef / approvedPurpose
      transformationKind / preservedProperties / lostProperties
      获准的最小正文或安全诊断
```

- 请求只是申请。用途与范围绑定真实spec定位，不能自填 `nonSensitive=true` 授权，不提供任意个体筛选表达式。
- 本地读取原始列；敏感性明细、逆向映射及原始解析结果不出站、不写普通日志。
- 候选视图按闭合协议、敏感性、组合重识别和语义保真分别核验；仅正则替换姓名、仅schema合法、仅值扫未命中均不够。
- 放行绑定精确内容、源版本、需求范围和政策版本；换目录、后缀、代码注释或知识条目不扩大权限。
- 存在个人可关联的假名化内容时仍按敏感视图管理；不能假称已经匿名。

#### D. 脱敏视图不替换正式数据源

1. 供AI理解的视图与正式源分开登记，不回灌输入发现。
2. R按原字段/类型及真实业务规则编写，在本地真实数据上执行；不得把合成编号、平移日期或例子中的分类写成真实业务常量。
3. 若需引用被令牌化的场景，AI返回批准的类别/语义引用，由本地绑定层解释；映射表不发送。
4. 在本地验证变换前后需求所需的等价关系、顺序、解析结构、缺失模式或规则结果；不可保真就不能用该视图支撑定案。
5. 最终独立重算和交付回归使用原始数据。脱敏例子跑通只是理解证据，不是正式产物验收。

#### E. 防连续单列请求拼出整行与跨任务泄露

- 按受保护资源及相关任务/父子会话累计记录释放范围，覆盖恢复、fork和新任务；用途授权可以按任务隔离，但组合风险检查不能因新runId、子代理或新会话身份重置。不为此保存云端原值，记录由本地域维护。
- 非必要不提供源行号、原行序、稳定个体令牌、精确频次；确需关联的视图使用共同批准范围，不能靠连续单列读取重建整表。
- 根据当前与历史已释放内容评估组合风险；低基数或数量少不是自动放行条件。
- 脱敏校验失败只扣留未获准内容，返回明确替代动作，不无限重试、不重跑已完成业务。
- 视图授权限当前用途；长期知识库沉淀方法与合成反例，不复制原值、逆向映射或可链接的假名样本。

#### F. 两条红线的新判据

禁止的是两类受保护来源的**未经授权或未经有效脱敏的敏感内容进入AI**，而不是屏蔽所有场景词、结构、合法统计或合规转换视图。本地完整数据用于计算，模型只获得具体spec所需、范围已确认、安全性与语义均验证的最小视图。

## 9. 第三项重构：固定识别经验进入系统，项目业务仍由 spec 决定

### 9.0 Manual / Medical 共用识别与处理核心，保留两个场景入口

按用户本轮后续明确要求：**Medical 完全可以按照 Manual 的方法开发，包括 spec 识别、范围/行/列推理、数据处理、R 程序生成及独立审查。** 不应再为 Medical 另建一套必须从模板高亮起步的流程，也不能只共用读写和样式。与此同时保留 `manual`、`medical` 两个可独立使用、验证和交付的场景入口。

```text
ListingCore：项目布局、材料清单、版本、安全证据、运行、发布
├─ EDCAdapter：字段/格式/记录层级/官方词表
├─ ReviewListingCore：spec识别→范围/行/列解释→R业务生成→独立审查
│  ├─ scenario=manual：DVP核查与已交付Manual项目的方法/验证
│  └─ scenario=medical：同一完整流程；明确差异以场景配置表达

│  ├─ form=be：以已交付项目C经验验证
│  └─ form=sad-mad：以已交付项目B经验验证
└─ ReportCore：报表/汇总需求、总体/分组/分母、去重、期间及展示验证

执行语言 R/Python 是 engine，不是业务场景名称。
```

实现上，Manual/Medical 共用需求解释规则和业务生成机制；需求文件形态差异由文档适配器处理，而不是因为名称是 Medical 就选择另一套语义。相同四列/范围语义应得到相同解释。两个场景的明确差异，例如输出名称、附加审核要求或某项书面规则，通过各自配置和版本化合同表达，不复制两份容易漂移的实现。

两者仍有各自的任务、知识索引、产物及验收记录；不能把 `publish(scenario="medical")` 理解成“只换一种 Excel 样式”。选择 R 交付也不应强迫 Medical 冒充 Manual 才能使用运行器。可扩展现有 R 工具的 scenario 参数，复用同一核心和兼容入口，不新增重复业务工具。

**Manual 固定识别经验：**

| 输入要素 | 固定职责 | 对每个项目仍需确认的内容 |
|---|---|---|
| Data Source / Form Name | 确定数据来源与表单范围；多表单分别映射 | 实际数据集、记录粒度、合并方式 |
| Visits Applied To | 限定适用访视；ALL 不额外收窄 | 设计访视与实际记录如何对应，组合访视如何解释 |
| Related Fields | 限定字段相关范围 | 内部计算依赖和最终展示列的区别 |
| Condition | 行筛选或派生计算/标记规则 | 布尔关系、空值、边界、判重键、CS 条件 |
| Column Heading | 最终输出列、派生列、顺序和位置 | 每列来源、名称、格式、匹配方式 |
| 已获准的反馈/变更 | 修改本次适用需求与状态 | 哪些条目删除、合并、新增，何时生效 |

必须把以下经验写入解析合同和验收测试，而不只放在提示词里：

1. **先范围、再行逻辑、再最终列输出。** 这是语义次序，不意味着在执行时过早 select 掉 Condition、关联和派生所需的内部列。
2. `Output if` 是筛选；`flag=duplicated` 是标记规则，**不等于默认只输出重复行**。是否过滤由该条需求决定。
3. `Condition=NA + Raw data` 不授权加入自主核查或“清除噪音”；仍需遵守该行的表单/访视/字段范围。
4. Column Heading 中不在源数据里的列不能漏掉，也不能随便找近似字段。必须区分别名、跨表带出、关联、聚合、计算、编码或明确待确认。
5. `Raw data` 的业务值保真，与 ALS 官方显示名/字段序及批准的系统定位列取舍是两个层面；不能借格式化改写原始含义。
6. “一行一条”必须形成实际记录展开，不能拼成一个单元格；同时保留需求规定的原始列。CS/非 CS 的行为分别验证。
7. 业务 `flag` 与审阅系统 `FLAG(New/Modified/Old)` 分开；不注入未要求的空 Flag1，也不能把恒 New 当已完成新旧比对。
8. 需求映射按适用版本的活动条目覆盖，不固定某次项目的 77/83，也不机械要求“一行永远恰好一张表”。合并/拆分须有清晰归属。
9. 零命中先区分“错误映射”“当前批次确实为空”“读取失败”，不能把三者都当正常无数据，也不能把正常空数据一律当语义错误。

**Medical 目前可继承的特有经验：**

- 已沉淀修改轮以模板高亮/注释、新 ALS、既有程序及比较配置联合定位；只能按本轮明确范围修改，不能重做历史 Modified 标记。
- 移动字段不等于再追加一次；根据需求说明、ALS Ordinal 和字段集合验证列数/顺序守恒。
- 新增 listing 时程序节、Content 顺序和比较配置同步更新；比较键必须存在于保留列中。
- 既有服务器路径字面量不能擅自更名；文件后缀不能取代真实容器识别。
- 单位等“数据里有、ALS 没有”的列不能按启发式自动丢弃。

旧库相应记录位于：`knowledge/manual/baiaozhi-scenario-kb.md:8-19,53-72`；`knowledge/manual/dvp-patterns.md:17-48`；`knowledge/medical/listing-medical.md:3-27,29-50,68-76`。这些引用只用于说明历史记录及冲突，**不代表新运行时继续加载旧库**。新规则须从用户确认的交付经验/获准需求证据重新提炼验证，并进入独立新代际，不能整库复制或直接固化历史项目裁定。

**Report保留独立场景，RBQM整体弃用：**

- `report` 保留报表/汇总场景；分母、去重、期间边界必须锚定需求，未说明就列待确认，不能靠“惯例”补。当前report知识库标为骨架/待首项目沉淀，是成熟度现状，不是删除或合并理由。

### 9.1 每条需求保留一份可审计解释记录

```text
需求定位/版本
适用表单、访视、字段范围
Condition 的筛选与计算语义
Column Heading 的列清单、来源、次序

```

这不是强制所有业务进入 DSL；它是程序和验收之间的索引与证据记录。E/I/U 可以保留，但字段已存在、数据有命中，不等于语义被 DM 批准。

### 9.2 独立审查须有两层独立性

**第一层：解释独立。** 审查者先读原始获准需求与澄清，不直接照抄生成者矩阵作为真值。

**第二层：实现独立。** 审查者从原输入重新计算，不调用生产程序的业务 helper。可复用文件解析器，但解析/格式适配本身也需要独立夹具验证。

宿主独立比较两边工件。模型自己写的“QC=0”文件不能成为验收依据。

### 9.3 有无 golden 都能工作

- 有已批准且版本匹配的 golden：做严格回归，用于验证兼容性和退化。
- 没有 golden 的新项目：依靠独立解释、合成反例/边界、原始数据重算、行集与结构约束以及必要的 DM 裁定。
- 不能拿生产程序自己的输出当自己的 golden。
- 不能把历史业务区注入模板的校准回归，当作 AI 从零理解新 spec 的证据。
- 比较器不可只看共同键；缺失键、重复键、缺行/多行、列顺序与标签必须单独记账。零行或跳过比较不能自动 PASS。

当前 `compare_artifacts` 是**最近一次成功 run_code 的 outputs 里两张命名表之间的比较**，不是两个独立运行文件的完整 QC，且缺失键可能被排除、列序/label 未覆盖。定位：`controlled_analysis.py:206-259`。

### 9.4 未决需求不让整个智能体停摆

- 文件发现、结构分析、合成测试和无关需求可以继续。
- 已明确条目的程序可运行与验证。
- 与未决条件相关的正式 listing 不得标通过；如果用户明确批准部分交付，按范围单独出状态。
- 安全基础设施故障、执行错误、数据事实、业务歧义必须四类分开，不能都显示“红线触发”。

## 10. 第四项重构：R 准备、执行、审查、发布拆开

### 10.1 prepare 不应该执行空模板

当前 `run_r` 首次调用是渲染后立即启动 R；Manual 模板在到达未填写生成区的 stop 以前，已加载输入、创建缓存，甚至可能删除解压 SAS。

定位：`r-runner.ts:411-444`；`manual_listing.R.tmpl:228-266,776`。

改为：

```text
prepare：登记输入/依赖、渲染公共层、报告待填区域；不执行业务读写
edit：AI 填写/修正项目业务区
parse：对固定程序版本做静态解析
execute：本地运行，产生本轮工件
review：独立验证和需求审查
release：核对证据版本后提交正式交付
```

不需要新增一排工具；可在现有执行工具中增加清晰 phase，并由宿主维护状态。

### 10.2 运行记录至少分开三个状态

- `executionState`：是否真正执行、成功、失败、未知。
- `deliveryState`：结果能否向模型释放/是否仍保留本地。
- `validationState`：业务是否已验证、失败或未完成。

程序成功但输出被扣留，不应再跑一次业务。扫描失败只重试扫描/投影。超时/断连先查 runId 与工件，不能盲目重跑。

### 10.3 诊断必须能支持自主修错

建议保留：阶段、固定错误类别、程序版本、静态行列、经源码/结构确证的符号引用、固定恢复动作；原始日志本地可供用户看。

重点测试真实可恢复故障：缺字段、类型不一致、零行塌型、编码不支持、输出被占用、依赖包缺失。只给 `RUNTIME_ERROR` 而没有可操作证据不算完成改造。

R 工具已有每次独立临时摘要，不应倒退成固定路径；独立运行程序的 `.summary_<date>.json` 另需防旧回执。普通 warning 应被分类处理，尤其写盘失败不能被 `done` 掩盖。

### 10.4 暂存和正式发布分离

工作区与暂存区位于约定输出根内部，由宿主管理；不是要求用户另造输入目录。

- 本轮运行不直接覆盖上次正式交付。
- 产物独立核验成功后，提交包含程序、输入、需求与验证版本的发布清单。
- 多文件发布不能把逐个覆盖称为原子提交；以版本目录和批准清单/指针为准，按兼容合同导出旧文件名。
- 失败保留已批准版本，不能拿旧成功 outputs 冒充本次结果。

Python 已有 workbook 局部暂存/备份，不需要重写它，但需提升到**整次运行及多工件发布**的版本约束。

### 10.5 要求 R 交付的任务仍交付单文件 R

本轮三个成功项目及用户要求的同类R任务保持单文件交付；Report或其他任务如有不同程序/工件合同，按其合同验收，不强制改成Manual样式或R语言。

- 业务代码在一份 R 文件中，自包含公共函数与业务区。
- 本地与服务器只切换显式环境配置，不能 Windows 分支偷偷读取另一套数据。
- 程序目录与输出路径从实际清单生成，服务器无 dsh/Python/网络也能运行。
- 包依赖和版本范围明确，运行前检查；不把缺包误判为业务错误。
- 不凭日期取第一匹配目录，不凭文件 mtime 选 spec/编码/旧产物。
- 新旧比较单独验收：键既要唯一，也须在比较环境间稳定；追加行序号不自动解决跨批配对。

当前模板有 `oldDate` 参数不等于比较已实现：Manual 模板仍有比较注释占位和恒 New 标记。定位：`manual_listing.R.tmpl:118,930-968,1093-1097`。最终应按交付合同确定“主 listing 是否含真实比较”，不能把参数存在当成功。

### 10.7 PK 按两个项目经验落为 BE / SAD-MAD 两种可验证形态

按用户本轮要求，现有 PK 直接以这两个成功项目经验作为建设基础，不另起一套不相干生成方式。

**两者共用的固定方法：**

1. 读 spec 的变量、类型、标签、来源、计算和盲态说明，逐变量建映射。
2. 确认外部传输件实际格式/表头/类型，不能把目录 raw_csv 当作CSV格式。
3. 对齐编号体系，检验桥接覆盖、唯一性和空值，不凭字段同名连接。
4. 分别确认名义时点、实际采样时刻和给药参照；日期与时间合并规则由实际字段证据和spec决定。
5. 构建目标列、顺序、label、类型、精度和BQL/缺失语义。
6. 验证关联基数、行数守恒、未匹配、重复、时间异常和最终工件保真。
7. 每种交付工件单独核对盲态、行集、列集、命名及验证状态。

**BE 形态的经验保留**：周期/访视匹配、随机号桥接、采样与给药时点连接、计划外情况、组别/序列/处理变量以及编盲输出。C实际实现中的给药选择和首条记录规则只是该交付样本的行为，不能推广为所有BE默认口径。

**SAD/MAD 形态的经验保留**：队列、名义日/小时、多阶段给药参照、多基质/CSF、时点映射、浓度有效数字和输出隐藏规则。B实际程序不在运行时读取spec或ALS，不能强行给服务器增加这两个文件的运行依赖。

模型应按新spec生成这两种形态的业务区，而不是把成功项目的剂量、时点码、访视名、字段名或固定23列写成永久规则。两份成功程序的合法共同行为可形成原语和验收配方；不同业务合同必须分别冻结。

### 10.8 每个工件有自己的合同，不能把“文件都出来了”当交付成功

实际 B 程序将装配全集写 RDS，再按 keep_flag 过滤 Excel；两个行数不同可能完全正确。C程序也会先写未编盲工件，再尝试编盲工件。`blind_mode` 参数/摘要本身并不证明完整工件可外发。

每个工件应登记：

```text
artifactRef / version / kind
rowPopulation（全集、筛选集或经批准子集）
schema / order / class / label
blindState / intendedAudience / allowedRelease
inputRefs / programVersion
validationState（passed / failed / skipped / incomplete）
```

- 编盲表缺失、编盲映射未覆盖、比较包缺失、没有基线、比较有差异，应分别记录。
- B的编盲输出对未匹配号存在保留原号的实现；C的完整本地产物与编盲产物并存。不能只因历史交付成功就把这些行为当成普适安全策略，正式外发需验证指定盲态合同。
- datasetQC调用完成、PDF存在，不等于差异为0；缺包跳过也不等于审查通过。

- C的输入发现允许CSV后缀却统一read_excel，不能据后缀清单声称真正CSV已支持；新读数层须实际按格式分派并测试。
- A/B/C中的源目录写缓存和删除行为不照搬；应在回归保持业务产物的前提下迁移到受控工作区。

实施前需在隔离环境用真实宿主管线和假 transport 验证：首轮、子代理、resume/fork、压缩、spill、工具异常、附件上传能否完整关联来源。公开扩展点覆盖不到的路径须明确列为阻塞/不支持，不能靠提示词保证或私改上游补洞。

具体技术预检包括：

- `tools.guard` 是同步、单调拒绝接口，不能在其中异步构建材料清单或偷偷替换执行工具。
- 同层工具重名、官方保留工具名受到限制；shell 受控适配须验证注册/禁用与 scope，不能假设同名覆盖即可生效。
- post 只改文本可能保留 canonical value；安全结果必须尽量在 execute 内形成，错误、额外上下文和 finalize 路径也要测试。
- 任意 R/Python 的隐藏 IO 不能被声明式 manifest 自动穷尽；未确证依赖的作业不能承诺自动幂等重试。
- 独立 R 工件接入比较前，先验证类型、label、列序、NA/空串的跨语言保真。
- 单文件 R 脱离 dsh 后仍可计算和做内置检查，但不会自动带走宿主安全/发布门禁；交付前认证与服务器运行状态必须分别表述。

定位：`upstream/deepseek-harness/packages/core/tools/src/index.ts:1031-1114,1732-1779`。

威胁模型也要诚实：同用户任意代码仍可有文件、进程和网络能力；只做结果 DTO 不等于防御主动恶意代码的 OS 沙箱。若要求此强度，需要独立的进程/文件/网络隔离设计，而不是把它冒充本轮既成能力。

### 11.1 成功项目经验必须进入企业知识库，不停在本报告里

用户要求的“犯过的错不能再犯、同EDC同场景直接用”，应成为重构交付的一部分。用户进一步明确：**真实运行时由智能体自行判定哪些经验值得沉淀，验证后直接写入对应EDC系统/场景知识库，后续任务自动复用；不以人工逐条批准作为默认落库前提。**

**本轮完成证据提炼和落库设计；尚未修改运行时知识库或发布新的规则。** 后续实施不可把“报告写了经验”当作“dsh已学会”。

**企业知识库为master，检索维度为：**

```text
场景（manual / medical / pk-mapping / report）
  × EDC系统/导出形态
  × spec需求模式
  × 输入/输出合同版本
```

- EDC按结构识别，不按某个项目名绑定。
- Manual/Medical共享语句识别和处理方法；保留两个场景索引及各自适用合同，不能复制两份不断漂移的知识。
- PK在同一场景下保留BE与SAD/MAD经验，先识别形态再加载相应参照/时点/交付方法。
- RBQM专属知识、规则、验证案例直接弃用，禁止自动沉淀到Manual或其他场景；Report继续独立。
- 同组合命中即自动加载已验证方法与检查，不再从零猜或重复问用户已经由合同确定的问题；只对新冲突/新未知升级确认。

### 11.2 每条经验的最小结构


### 11.4 知识、代码、测试三层同时交付

仅写“下次注意”不够。**每个已修错误必须有可重复的验证案例。** 知识层记录适用条件，可机械判定的部分进入执行层；不能自动判定的语义错误也须保留反例与明确审查判据。三层职责如下：

1. **知识层**：触发条件、处理方法、证据与边界，供模型同场景直接复用。
2. **执行层**：可机器判断的条件变为工具/适配器校验，例如键重复、列丢失、错误日期批次、未填生成区、产物没写成功。
3. **验证层**：最小复现/反例测试。以后改公共层、场景库或模型指引，都必须能检测旧错回归。

落点建议（是实施目标，不是已新增模块）：

- `knowledge-v2/router.md`（拟建独立新根）：仅保留四场景路由，不加载旧router，也没有RBQM入口/别名。
- `knowledge-v2/manual/`：从获准成功Manual证据重新提炼固定spec语义与处理经验；项目历史裁定增加版本/适用范围，不当全局规则，不引入RBQM知识。
- `knowledge-v2/medical/`：引用新代际共享Manual识别处理核心，明确场景差异；修改轮经验重新核证后落库，不导入整份旧知识。
- `knowledge-v2/pk-mapping/`：BE/SAD-MAD方法、代码原语与多工件验收，来自两个成功交付程序及其锁定合同。
- `knowledge-v2/report/`：保留场景及汇总合同；成熟经验不足处标清，从获准需求及后续项目积累，不用旧库兜底。
- `knowledge-v2/edc/`：独立提炼公共EDC适配经验，由四场景引用，避免各自复制判定字段/日期解析规则。
- 模板、受控分析和`tests`：可复用的工程资产先做行为核验；旧模板内嵌的业务假设/知识说明不能绕过新知识隔离。机械检查与合成回归修一类查全类。

**落库验收：**给dsh一个同EDC/同场景的新会话，观察它是否自动命中相应经验、使用正确方法并通过旧错反例；不在提示词里把正确答案、业务代码或golden数据喂给它。模型“读了库”不是通过，最终行为和产物通过才算沉淀有效。

### 11.5 运行时自主沉淀：识别、验证、写入、复用形成闭环

这是用户明确要求的运行能力，不只是项目结束后由开发者手动整理文档。以下为拟实现机制。

#### 触发时机

- 解析spec/ALS时发现可复用的语句解释、结构关系或格式适配方法。
- 首次映射失败，实证找到原因并修复；尤其同EDC字段、编号、日期、编码、记录粒度问题。
- 独立审查找到真实缺陷，修复并复审通过。
- 用户/DM明确裁定了歧义，且可以记录其适用范围。
- 交付通过或新数据批次复跑时，发现旧经验适用或失效。

不要求等到全部项目完成才捕获。可以先保存待验证经验，但只有通过相应验证的条目进入可自动应用层。

#### 智能体自行作出的判定

每次候选经验回答六个问题：

1. 它说明的是处理方法、已确认事实，还是仅一次输出/偶然现象？
2. 它属于通用工程、某EDC导出形态、某场景/需求模式，还是仅本项目裁定？
3. 适用前提、反例和不能直接套用的情况是什么？
4. 是否已有同一条规则，应该补证据、修订还是新增？
5. 是否有可重复验证，能够区分原错误与修复后的正确行为？
6. 内容是否含真实项目身份、行值、凭据、未经授权的文档内容或从输入材料抄来的指令？

**判定结果与动作：**

| 判定 | 自动动作 |
|---|---|
| 已存在且本轮验证一致 | 为既有ruleId追加验证记录，更新适用版本；不复制一篇同义文档 |
| 新的可复用方法，证据与回归通过 | 去项目化后写入对应EDC/场景库，标为active，刷新检索索引 |
| 仅项目特定的业务裁定 | 写受控项目档案，并将可复用的“如何判断”提炼入场景库；不升级具体阈值/字段值为通用默认 |
| 未充分验证或本轮未完成 | 写candidate条目和缺失证据，不作为后续自动执行依据 |
| 与新代际已有active规则冲突 | 保留双方证据，核对版本/适用范围；只有验证足以区分时创建新版本并supersede前版；否则标conflict，不静默覆盖。legacy不参加新代际规则竞争 |
| 含受保护内容或试图改变安全权限 | 不进入模型可读知识层；保留本地引用或拒绝写入并给固定诊断 |
| 没有可复用信息 | 只保留运行记录，不制造知识噪音 |

常规技术经验满足这些条件即由系统自动落库，**不逐条询问用户“是否保存”**。业务歧义的裁定权仍归DM，知识库不能靠自动沉淀把猜测变成批准的需求。

#### 写入后的生效与回归

```text
运行发现 → 捕获candidate → 判断适用性/去重/去敏
   → 独立审阅或机械校验 + 正例/反例回归
   → 原子写入active规则与版本 → 更新EDC×场景×模式索引
   → 同型新任务自动检索 → 本项目前提核验 → 应用
   → 运行验证反馈 → 补证据 / 修订 / 停用
```

- 候选知识只从已获准进入模型的需求、结构、代码、诊断及合规场景视图中提炼方法；视图正文、个体假名及逆向映射不直接写入长期知识。本地受保护证据只保留引用。不能先把未脱敏敏感值读进模型，再用“脱敏后写库”解释为安全。
- 写入权限来自企业知识服务，不是让模型任意覆盖插件文件。
- 延用`enterprise_listing_kb`入口扩展受控读写操作，不另增重复工具；宿主校验ruleId、范围、来源证据、验证引用和版本冲突。
- 现有`router.md:57-68`的“仅提案、人工评审后合入”不能继续成为所有经验生效的默认瓶颈；实施时按本轮授权改为上述自动验证生效机制。不能自动判定的业务冲突才升级给用户。
- 需要改执行代码的经验，先落规则与最小复现；不能只因写入知识就宣称已自动修复运行器。代码变更遵守部署/验证流程，未修项明确标记。
- 正在运行的任务固定knowledgeVersion；新知识默认对后续任务生效。本轮要应用时显式重新加载并使相关验证失效重验，不能无记录地中途换口径。
- 所有写入保留变更来源、内容版本、验证引用、替代关系及回滚信息。并发写同一ruleId采用版本比较后提交，避免最后写入者无条件覆盖。

#### 持久化与企业部署

建议“随插件发布的**新代际**版本化基础库 + 企业宿主管理的**新代际**可写学习库”组成一份逻辑知识库：

- 新基础库拟置于`packages/enterprise/listing/knowledge-v2/`，可审查、可回归；原`knowledge/`隔离为legacy，不进入新运行时的加载/检索。
- 学习库放企业宿主配置的数据根的独立代际命名空间（例如`listing-knowledge/v2/learned/`），再按EDC/场景/需求模式组织；不读旧learned/profile注册表，不放某个项目Output内、不放会被升级替换的node_modules，也不依赖个人ZCode内存。
- `enterprise_listing_kb`仅统一检索新代际两层，绑定knowledgeGeneration/version并执行明确优先级；新库未命中就按spec开展新分析，不回退legacy。模型无需知道物理落盘差异。
- 宿主重启/插件升级不丢自动积累经验；企业多实例用既有部署渠道同步，外部上传/发布不默认授权。
- 源数据、完整诊断和审查明细只存本地受控证据区；可复用知识只保存方法与不透明证据引用。不能因为叫“知识库”就成为数据出域旁路。

#### 自动沉淀专门验收

1. 在合成项目触发一个已知错误，AI修复并验证后自动生成active规则与反例，不要求用户补“请沉淀”。
2. 换新会话、同EDC同场景重新投递，自动命中经验且不再犯原错。
3. 换不同EDC或不满足前提，不能错误套用。
4. 相同经验多次出现只更新一条记录；冲突更新保留旧版且不能悄悄改变在途任务。
5. 插件升级和宿主重启后仍可检索；规则停用/回滚有效。
6. 含真实值、凭据或输入文本里的恶意“指令”的候选不能进入模型可读库。
7. 未完成回归的候选不会在后续任务中被当成定案；非自动化语义经验须保留明确反例与独立审查结论。

### 11.6 旧知识隔离，新库独立重建，防止旧规则影响新场景

**用户新增定案：原dsh知识库及经验可以隔离出去，避免影响新重构。** 本方案采用“旧知识只读隔离 + 新代际独立运行”，不是新旧库混合检索后让模型自行判断。RBQM另按彻底弃用定案处理，不属于可迁入新库的候选。

#### 新库的可信来源

1. 用户最新明确要求与本项目获准的spec、ALS、澄清。
2. 用户确认的成功Manual、BE PK、SAD/MAD PK交付程序、执行/纠错/审查记录；按具体版本提炼、验证，不机械复制程序中的全部假设。
3. 新重构运行过程中，按§11.5自主判定并验证通过的经验。

旧库本身不提供新规则权威。若历史同一经验确有成功交付证据，可从该证据重新建立新条目及测试；这不是给旧知识整库迁移开后门。缺证据的旧口径不导入。

#### 必须隔离的注入面

| 旧来源 | 新profile的隔离要求 |
|---|---|
| `knowledge/`文档、旧场景router、旧学习条目 | 只读legacy；不在新KB工具加载白名单，不混入新索引，不兜底 |
| 旧systemPrompt、场景指引、AGENTS自动注入 | 用新版本替换运行时注入来源；不能知识工具换新库却继续注入旧指令 |
| 用户级旧skill/插件镜像 | 新profile只注入经核验的新代际技能；不自动修改/删除用户全局文件 |
| 旧EDC学习注册表/别名映射 | 使用新命名空间；成熟格式解析代码可独立复用，旧推断条目不自动继承 |
| 旧检索索引、文档缓存、工具结果缓存 | cache key包含knowledgeGeneration；新任务不命中旧缓存；不靠改文件夹名假装失效 |
| 旧会话、子代理继承、摘要/长期记忆 | 新任务从新知识上下文启动；恢复旧任务只能携带获准需求/代码/工件事实与版本，不能整段继承旧知识摘要 |
| 旧模板说明/代码注释 | 检查内嵌业务假设与知识引用；已交付程序作为证据而不是高优先级指令，不能绕开新合同 |
| 搜索、文件读取和归档目录 | 新任务的KB检索、代码搜索及文档回读都不能偶然把legacy正文注入模型；历史审计须显式范围，不作为正常任务兜底 |

只做物理搬目录不够；必须检查最终实际装配的提示词、工具上下文、历史和检索结果。反过来，隔离知识不等于丢掉已验证的通用读写代码；工程资产是否复用依据其行为测试与新合同，不依据它来自旧目录。

#### 版本与切换

- 所有新任务固定`knowledgeGeneration=v2`及具体版本，工件验证记录也带同一代际。
- legacy不参与新active条目的优先级比较，旧规则冲突不导致新任务卡住；只有新代际内的适用规则冲突才走§11.5。
- 旧知识可保留供本地审计/追溯，不通过普通模型工具暴露；保留副本不是保留其生效资格。
- 新库能力缺口按spec重新分析/验证/积累，不自动打开旧库作为恢复动作。
- 回滚代码不能悄悄恢复legacy注入或旧宽安全豁免；没有兼容版本时明确暂停受影响能力。
- 本轮仅设计，未移动或删除旧知识目录、索引或会话，也未覆盖个人skill。实施时先列清单、核对来源，再做可回滚的隔离配置。

#### 隔离验收

1. 使用合成legacy独有标记，经KB查询、搜索、read、子代理、恢复和压缩测试，确认新任务模型上下文及最终请求不含该标记。
2. 新库故意移除某个主题，确认结果为知识缺口/开展分析，而不是回退旧库。
3. 重启和升级后只加载新基础库/新学习库；旧注册表和缓存不能自动复活。
4. 成功项目经验在新库仍能命中并通过回归，证明隔离旧库没有丢掉用户要求保留的交付方法。
5. 检查四场景路由及RBQM退役，无旧入口/别名或专属规则借Manual重入。

## 12. 迁移顺序：先补足能力，再收紧旧通道

### 阶段一：锁定真实材料和行为合同

- 以本轮实测布局作为代表夹具，不要求 doc/。
- 先建立新知识代际并隔离旧库、提示词/skill镜像、EDC学习注册表、索引/缓存和旧会话注入；禁止legacy兜底。
- 从用户确认的成功交付证据重建新库方法与回归，不整库迁移旧经验。
- 建立文件角色、输入批次、spec 版本、输出日期规则。
- 锁定三项目的交付程序/配置/验收产物版本，分别登记公共层与业务层，不能按mtime选终版。
- 按§11.1–11.4提炼同EDC同场景经验，建立最小反例测试，再更新知识与模板。
- 收口四场景：Manual/Medical共享完整方法，PK保留BE/SAD-MAD形态，Report独立；RBQM及其专属知识、规则和验证案例整体弃用，清除残留引用，不迁入任何场景。
- 修正知识层冲突与旧文档误述。
- 核对运行时实际加载的企业包构建版本，不能只因 src 已改就声称运行实例已更新。

**验收：**无 doc 的三类结构可发现；raw_csv 中 Excel 可识别；输出诊断不回灌；日期/基线不串用。

### 阶段二：补足诊断和安全证据闭环

- 已有 P0 修复保留。
- 统一需求阅读、元数据和分析回执的来源与版本。
- 补安全错误定位、mapping/parse-shape/compare/run_status。
- 实现§8.6的spec驱动单列scenario_view：本地判定、最小转换、安全/语义保真双验及多次请求关联控制。
- 为源码、需求、计数和获准场景视图提供基于来源的放行路径，消除全局同值误拒。

**验收：**合成编程错误能在安全开关开启下自主修复；合法需求及已批准场景视图不因全局同值误拒；未经脱敏的敏感值不能经动态错误、视图、附件或知识库出站；转换不改变正式R的原始数据输入。

### 阶段三：统一 R/Python 任务与出站机制

- R prepare 与 execute 分离，输入源只读、缓存版本化。
- 持久运行状态、独立验证、多工件发布。
- 子代理和会话恢复共享同一保护上下文。
- 替代能力通过后成组删除 shell/enterprise/Output 宽豁免。

**验收：**错误发生后不重跑已成功的业务；旧 outputs 不冒充新结果；R/Python 结果按相同规则处理。

### 阶段四：验证能达到交付水准

- 新会话从 spec/ALS/原始输入启动，不能注入旧业务代码。
- 独立 DM 审查与本地重算全部覆盖。
- 要求R交付的任务，将单文件 R 放入干净服务器等价环境复跑。
- 实现§11.5运行时自动经验判定、验证、去重、落库与新会话复用，不以手工写总结代替。
- 发布、回滚和输入/知识版本变更失效全部验证。

**验收：**达到下节质量、安全和运行稳定性指标，而非仅“没有告警”。

## 13. 如何证明达到 ZCode 产出水准

### 13.1 固定对照条件

尽量固定模型真实标识、推理预算、可用知识版本、spec/ALS/数据版本和交付合同。无法固定的差异需记录，不把宿主差异和模型差异混为一谈。

### 13.2 质量验收

- 所有活动需求均可定位到解释、程序和验证；删除/合并/新增均可追溯。
- 行集合与数量、列集合与顺序、类型/label、关联及拆行、缺失/部分日期语义、输出格式分别通过。
- 编码未命中有归因，不能靠空表/空列掩盖未实现逻辑。
- 新旧比对验证唯一性和稳定性，不能仅把所有行标 New。
- P1 清零；影响正确性的 P2 有明确裁定；P3 不冒充修复或失败。
- 无基准也能完成独立验证；无法证明的项目明确 incomplete。

### 13.3 安全验收

- 在**声明测试面**中，合成受保护标记未批准进入模型请求/附件的次数为 0。
- 已批准需求、代码、结构、计数、诊断和spec必需的合规场景视图误拦为0。
- 按 shell/R/Python/读取/子代理/压缩/恢复/附件分别测试，不能只看 UI 卡片。
- 目录复制、换后缀、转成产物不改变保护属性；只有宿主核验并批准的精确视图获得限定用途的释放资格。
- 同时测试正反例：必要的非敏感单列场景标签能够释放；单列个人编号不能原样释放；变换后视图只保留批准性质；去标识失败、字典可逆哈希及连续列拼接不能被自动当安全。
- 未获准的原始敏感内容、逆向映射、可用于还原敏感值的变换参数，以及携带未获准内容的动态异常正文，不得进入模型载荷、上传、模型可见历史或长期知识。获准非敏感场景值及固定安全诊断不在此禁令内。
- 本地校验变换的语义保真；错误平移、损坏分隔结构、丢失缺失模式等须被发现，不能只通过隐私检查就宣称支持需求推理。

### 13.4 稳定性验收

- 扫描基础设施重试有界，不反复执行业务。
- 换批次只使对应缓存和证据失效，不能混入旧编码文件。
- 输出被占用时明确发布失败，不能仍报可交付。
- 未填写业务区不会先解压或删除输入。
- 只读输入目录可完成任务；测试前后源文件版本一致。
- 全部模型可见指引都有实际工具支持，不再出现“按说明操作却只能触发红线”的死路。

### 13.5 测试分层不能混称

1. 纯函数/合成单测：验证规则和故障分类。
2. 真实 R 集成：验证 R 程序、包、目录、空表/编码/跨机行为；Node 模拟 Rscript 不能替代。
3. WebUI → AI → 工具 → 本地执行 → 审查 → 交付：验证真实用户路径。
4. 合成假 transport 捕获：验证实际模型请求与附件内容。
5. 授权真实项目的本地比对：验证原始数据上的正式产出；模型仅获取批准诊断/结论，或按§8.6释放的必要场景视图，未经有效脱敏的敏感值不回传。

---

### 13.6 对“达到ZCode交付水准”的硬验收，不用设计承诺代替结果

用户要求的最终成果同时包含三个条件，必须联合通过：

1. **持续迭代交付能力**：冷启动只给真实结构下的spec/ALS/本地输入及必要参数；AI自主解释、写R、执行、定位错误、修正、独立审查并形成交付。不把旧业务代码或正确结果预先塞给生成者。需求变更、数据换批及新会话恢复都重复验证。
2. **需求理解可验证**：逐活动需求有明确范围/行/列、派生/匹配、正反例和验证覆盖；生成方与审查方独立解释，无未决语义冒充PASS。已有三个成功交付项目作为经锁定版本的回归锚点；新项目没有golden时也必须独立重算与边界验证。
3. **两类来源的敏感内容受保护**：安全开关开启，原始数据仅本地计算；spec必要的单列场景视图经用途、脱敏/敏感性和语义验证后才释放；真实敏感值不能通过错误、输出文件、附件、知识库或多次请求旁路进入AI。

要求R交付的任务还须在服务器等价环境，以同一业务代码版本直接执行；依赖、路径、输入/输出和工件合同均可核验。每轮记录程序版本、输入/需求/知识版本、验证覆盖、未决项、迭代次数和正式工件版本。

**只有上述联合端到端验收通过，才能说实现已达到相应项目/场景的交付水准。** 不能在尚未实现、尚未测试时保证所有未来spec都绝对正确；系统必须保证的是未确证不冒充正确、未经验证不宣称可交付、未获准敏感内容不发送。支持范围扩大时继续补实例与反例，不降低这些门槛。
