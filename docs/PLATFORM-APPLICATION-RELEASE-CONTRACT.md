## 1. 发布单元与执行位置

应用不是插件包的一比一映射。平台可注册几十到上百个插件，一项应用只引用所需的能力。Listing 业务类型严格为 Manual、Medical、PK、Report；DVP 独立定义配置，不继承 Listing 字段。

| 单元 | 保存/执行位置 | 允许内容 |
|---|---|---|
| ApplicationDescriptor | 目录数据库，纯数据 | 名称、用途、关键词、参数 schema、资料角色、结果类型与限制 |
| AppRegistration | 控制服务，纯数据 | Descriptor、ExecutionPlan、ViewContribution 的批准版本和摘要引用 |
| AppExecutor | 锁定执行 Worker | 领域上下文装配、资料解析、领域命令、业务验证和成果发现 |
| ViewContribution | 平台浏览器工作区，按需加载 | 声明式组件配置或经批准的专业前端模块 |
| ExecutionPlan | 发布时生成，运行时只读 | 能力到确切提供者的映射、配置顺序、资源与执行基线 |
| RuntimeBundle | 发布产物仓库，运行时只读 | 固定 DSH/SDK/Adapter、业务插件、公共依赖与 profile |

控制主服务不得 import 应用执行包来解析资料、调用验证器或计算领域结果。通用 schema 校验不执行应用提交的代码或自定义 JS validator；输入大小、schema 深度与引用解析也需限额。发布包不能自带脚本让控制服务加载即执行。

AppExecutor 使用 DSH 的原生插件/工具扩展，不重造 Agent 循环。业务计算位于 Worker 的限制域，可启动其受控子进程；不得把长任务同步推回控制服务。安装包、执行器和前端模块分别登记摘要，不将“名称相同”当作实现相同。

平台只运行自身维护的公共代码，处理身份、项目、目录、通用状态和结果登记。执行端返回的结果视为跨进程输入，平台再验证 schema、身份、Run、租约和资源归属。插件崩溃、阻塞或内存超限不得拖住控制服务的目录/项目请求；这需要实际资源隔离测试，单独 Node 进程本身不是安全沙箱。

## 2. 确定性 ExecutionPlan

### 发布时解析，运行时不猜

开发依赖要求可以使用版本范围；发布预检必须将其解析成确切集合。运行只接受批准的 planId + planDigest，不按 latest、安装顺序或临时网络查询选择提供者。首期不建设通用动态包求解器。

每份计划至少包含：

| 字段组 | 必要事实 |
|---|---|
| 计划身份 | contractVersion、planId、planDigest、appReleaseId、descriptorDigest |
| 引擎组合 | DSH/SDK/Adapter 的版本、产物摘要、平台/架构约束 |
| 能力绑定 | capabilityId + capabilityVersion → provider package/version/digest + executorId + protocolVersion |
| 数据合同 | inputSchemaId/version/digest、outputSchemaId/version/digest |
| 依赖闭包 | 完整包集合、传递依赖、peer 兼容证据、配置贡献的确定顺序 |
| 执行基线 | profileDigest、policyVersion、禁用入口、允许副作用类别、resourceClass |
| 前端 | viewContractVersion、批准视图摘要或通用降级视图 |

policyVersion 描述执行限制，不授予任何用户访问项目的权利；每次启动仍校验当前身份和项目授权。凭据只以 secretRef 绑定到执行授权，不在发布清单或摘要日志里保存秘密正文。

公共能力在一个 bundle 内复用；同名能力出现多个提供者必须由计划显式选定，不能由插件注册先后决定。循环依赖、必需能力缺失、schema 不兼容、未批准提供者和配置覆盖冲突均阻止发布。若允许可选能力，须声明缺失时行为和缺失标记；不得悄悄替换实现。

planDigest 对规范化清单计算，并覆盖所有受控子产物摘要。哈希只能发现变更，不能证明批准身份；还需要可信制品仓库和平台维护的发布批准记录。安装路径可变，但实际载入的字节和有效装配必须对应计划。

### 启动预检

Worker 在接收业务输入前核对计划批准状态、实际包/配置摘要、兼容版本、能力清单、隔离策略和资源可用性。若运行时发现未声明工具/注册项或缺少必需能力，拒绝激活并报告差异。预检与实际装载之间应由只读制品和部署身份约束避免被替换，不把一次 hash 检查当作持续保护。

## 3. 企业执行 profile 基线

默认 sdk profile 不是直接可用的企业生产基线。固定源码中 sdk-app 开启模型端插件管理工具，并存在原生 schedule 自动恢复路径，见[默认插件管理设置](../upstream/deepseek-harness-git/packages/bundle/sdk-app/cordis.patch.yml:23)、[提醒激活](../upstream/deepseek-harness-git/packages/sdk/server/README.md:34)。

企业执行基线必须满足：

1. 关闭模型可调用的插件安装、升级、启停、兼容豁免及配置管理入口；生命周期变更仅由发布服务操作。关闭工具不代替操作系统写权限约束。
2. 引擎、SDK、插件包、依赖锁和有效 profile/patch 由部署身份写入，执行身份只读。DSH home 的会话/缓存可写路径与安装/配置路径分权；具体路径按锁定版本验证，不假设整个 home 都能只读。
3. Agent 写工作区代码是业务能力，可以继续；不得用 shell、文件写入或包管理器修改受控的宿主安装与启动配置。允许的业务脚本、临时依赖区、网络和子进程能力由部署策略明确，不以禁用插件管理为由撤掉正常业务开发能力。
4. 关闭原生 schedule 工具及初始化后自动唤醒入口。只隐藏工具不够；旧 home 中已有提醒也不得自动执行。
5. 首期不接入原生长期 goal/parked 工作的跨 Run 续跑。其创建/自动激活路径不得绕过平台 Run；普通 Agent 工具与受管子任务仍可在当前 Run 内执行。
6. stdout 只用于 SDK 协议，诊断走受控日志；环境变量通过受控完整环境构造，不在日志泄露凭据。
7. 不允许通过普通用户问题、计划确认或“允许一次工具调用”更改上述部署限制。企业限制由服务端与执行域落实，不只靠提示词。

这些是部署要求，不是现在修改任何 profile 的指令。启停原生服务的具体装配在最小接入验证中确定。若无法在不破坏 SDK 的情况下阻止自动唤醒，首期仅可用干净、无原生调度存储且禁止创建调度的专属运行环境；已有提醒的 home 继续隔离，不得带入生产恢复。该替代必须通过启动激活测试，不能只靠文件名推断“没有提醒”。

## 4. home 与执行域

- 每个 Run 拥有独立 engineHomeId，绑定 projectId、appReleaseId、runtimeLockDigest、rootSessionId 和执行身份；不按 bundle 给所有工作共享可写 home。
- 安装制品可共享只读存储；会话、临时文件、输出目录和可写配置不得跨独立工作复用。
- 原生子会话必须来自已绑定 root 的受管后代，并记录 lineage。首期仅恢复 root；历史无关会话和定时唤醒不因存在于磁盘就获得激活权。
- 恢复同一 Run 可使用其原 home，必须先确认前进程树退出、原锁仍可用且当前身份获准；新 Run 使用新 home/root session。原 home 保留为证据，不原地清空。
- 恢复前 inventory 只在受控管理过程进行，不启动可能自动工作的引擎来“检查”。发现未知会话、提醒或配置漂移则隔离，人工/受控迁移处理；不得静默删除历史材料。

## 5. 发布、升级与撤权

应用版本绑定已验证的 ExecutionPlan。普通升级只调整新 Run 路由，在途运行保持原锁；缺少兼容旧环境时停止恢复，不能临时用新版本碰碰运气。

安全撤权与普通升级分开：人员/项目授权撤销、制品紧急封禁时，平台立即停止新的输入/回答/下载授权，持久记录取消意图，通知监督器撤销执行访问并停止进程树。无法证明停止时保持 UNKNOWN，不能把“留在旧版本”作为继续执行的理由。已读取的数据不能凭撤权从模型或内存追回；已落地资料按保留政策处理，不自动删除证据。短期凭据、在线权限检查与隔离环境的撤销时效需要明确测试。

前端按 ApplicationRelease/viewDigest 加载；升级不可让新 view 无提示改写旧工件。不可用时保留平台通用只读视图。

## 6. 工作台接入要求

AppRegistration 是员工应用目录的数据源，不是每项都需一个独立微前端。目录查询在服务端按身份/项目过滤；搜索、收藏、最近使用和深链接使用 appId，不依赖数组下标。

进入应用时加载该应用配置与已批准视图；提交时由服务端重新选择批准的 release/plan，并验证参数和资料引用。前端不能任意指定包、profile 路径、能力实现或 secretRef。工作创建后展示所绑定版本，切换应用建立新工作而非改掉旧上下文。

Listing 参数 schema 固定四个业务选项；DVP 不要求或保存无意义的 Listing type。领域表格、术语和工件逻辑归应用贡献；平台只认通用上下文、授权动作和版本化结果合同。跨应用交付需要输出引用、消费方兼容检查和权限校验，不因同属一个平台自动共享全部上下文。

## 7. 接入验收

| 编号 | 场景 | 期望 |
|---|---|---|
| A01 | 同一 release 在两个干净环境装配 | 相同 capability/provider/摘要映射 |
| A02 | 两提供者冲突、缺依赖、循环、schema 不兼容 | 发布预检失败，有定位信息，无 latest 回退 |
| A03 | 模型请求插件管理，或 shell 尝试改受控配置 | 管理入口不可用，部署写权限拒绝；正常工作区代码仍可写 |
| A04 | 运行前安装包/profile 被改动 | 预检拒绝接单，不恢复到漂移组合 |
| A05 | 原 home 有到期提醒/无关 session | 无平台租约不能启动任何额外执行 |
| A06 | 某 AppExecutor 阻塞、崩溃、超内存 | 对应运行失败/未知，控制服务查询及其他 worker 可用 |
| A07 | 普通升级、紧急封禁分别发生 | 前者排空旧锁，后者触发撤权/停止并记录实际结果 |
| A08 | 应用视图缺失或版本不同 | 历史工件可通用只读，不能静默按新 schema 写回 |

所有条目均待实现后实测。计划与 schema 的最终 wire 字段须在测试通过后另行发布稳定版本。
