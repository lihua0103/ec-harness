# 企业工作台体验评估与优化改造方案

日期：2026-11-17 · 类型：体验评估 + 改造建议 · 状态：**已被取代（历史参考）**。

入口：[需求规格](CLINICAL-WORKBENCH-REQUIREMENTS.md) · [目标方案](CLINICAL-WORKBENCH-SOLUTION.md) · [多插件架构](ENTERPRISE-MULTI-PLUGIN-ARCHITECTURE.md) · [既有独立审查](clinical-workbench-review/03-enterprise-architecture-and-ux-audit.md)。

## 0. 评估方法与证据边界

- **对象是当前运行面**：`packages/platform-workbench`（DSH 单页插件，2026-11-13 视觉重做 + 2026-11-17 体验增补），不是 `apps/enterprise-workbench` 旧独立应用，也不是 `prototypes/` 概念稿。
- **证据**：通读插件全部源码（`WorkbenchPage.tsx` 3488 行 + 9 个支撑文件）；查看**今日真实 E2E 截图** `.runtime/employee-ui-2026-11-17/shots/`（首页/详情/对话/运行记录/设置/待办）；核对 `platform-control` 后端能力与 HTTP 路由；对照需求/架构文档。
- **与 2026-11-11 审查的区别**：那份审查针对旧 `app.mjs`，其"项目是文本框、执行器未配置仍可点开始"等阻断项，在当前插件已部分修复（五步向导、工作空间登记、模型健康、复核卡、历史会话页）。本文不重复那些已修项，只评估**当前**形态。
- **未做**：真实员工可用性实验、读屏器完整回归、真实 Worker 下的体验复跑、性能压测。以下是源码 + 截图核对，不是运行验收。

## 1. 结论

1. **架构方向正确，应保留**：DSH 负责 Agent/模型/会话，平台负责项目/工作/版本/治理；模块化单体、不建第二套引擎。这与需求一致。
2. **当前工作台仍是"工程切片"，不是它自己需求所定义的任务/交付体验。** 它把"一次对话 + 几个表单 + 运行侧栏"当成了产品，而需求明确要求"不是选择插件 + 输入提示词 + 看聊天"。
3. **后端远比 UI 呈现的更强。** 控制面已实现持久审计（SHA-256 链）、发布审批/回滚、运行事件历史 + SSE、指标/doctor/备份、身份策略、完整知识服务、追加式输入基线——**UI 几乎都没接**。体验差的一半原因是"把已有的企业能力藏起来了"。
4. **体验差是结构性的，不是配色/间距问题。** 换皮解决不了；需要把**工作（Work）及其基线/运行/成果/复核/交付**变成主对象，把聊天降为辅助。
5. **不建议**：推倒重写、按插件拆微服务、先上 SSO/多租户、做通用 agent 编排器、继续"补一个按钮就称企业化"。

一句话：**它现在像一个"套了企业壳的开发者聊天工具"，而不是"以持续工作和可追溯交付为中心的专业协作平台"。**

## 3. 为什么体验不好：八个根因

**RC1 · 聊天/表单优先，而非任务/交付优先。** 需求 §1、蓝图 §3、多插件架构 §5.2 都明确"不要把所有业务强制成一个大聊天框"。当前详情是表单堆叠、控制台是纯原生聊天。三种工作模式（探索开发 / 换批复跑 / 审阅交付）被压成同一种"和 AI 聊天"。

**RC2 · 基础设施概念外泄。** 绝对路径、session ID、输入 hash、执行器名（dsh-profile）、执行域（本机）、原生 hero、代理名（DM Listing）、provider 路由（zai-coding-cn/…）都出现在业务面。需求 §8 明确"普通员工不用输入绝对路径/shell/密钥"。这些应进"专家/诊断"层。

**RC3 · 双重交互模型令人困惑。** "对话（不产生运行记录）"与"发起运行（产生受控成果）"是两条并行路径，详情里还有"工作草稿"和"发起运行"两个相似 textarea。这是把后端 Session vs Run 的区别直接漏给了员工。

**RC4 · 富产品模型缺失。** 需求的核心——基线（数据批次/方案/ALS/程序版本）、**三指针**（编辑中基线 / 最近运行结果 / 当前认可交付）、换批次重跑（SC-03）、差异/影响、复核与交付分离——在 UI 里基本没有。成果/输入栏只是薄投影。

**RC5 · 后端已有治理/可观测能力未呈现。** 见 §5 矩阵。审计、审批/回滚、运行事件历史、指标、备份、知识、身份策略都已存在，UI 没接。企业平台的"可信/可治理"感恰恰来自这些。

**RC6 · 首页是问候 + 卡片墙。** 审查 §6.1 已自我纠正过：返回用户要"续作/待办/结果"，不是每次描述新目标。当前首页未落实。

**RC7 · 企业平台基础件缺失。** 无全局搜索/命令面板、无深链接（URL 始终不变，仅 sessionStorage）、无统一通知/待办、无管理/运营台、无成本/用量、无知识管理、无模板库、无批量操作。

**RC8 · 具体缺陷（已逐一定位核实）。**
- 控制台 15s 自动刷新会把你从"实时对话"拽进"运行记录"：`WorkbenchPage.tsx:2089` 在 `selectedRunId` 为空且存在运行时强制选中第一个运行。
- 运行侧栏"默认模型"显示外壳默认模型，而非该运行冻结模型：`WorkbenchPage.tsx:2206`。
- 历史会话每行时间显示"时间未记录"：`reports.ts:121` 只接受字符串，而会话行传入数字 `updatedAt`（`WorkbenchPage.tsx:190`）。
- 新建向导步骤不可点击跳转、无取消/关闭；工作目录需手填绝对路径。
- 详情 freshness 刷新在运行 ID 不变时不重读成果/输入；bootstrap 无周期刷新。

## 4. 与需求/八问的差距矩阵

| 员工必须能回答（需求 §4） | 当前 | 差距 |
|---|---|---|
| 我在哪个项目、什么阶段 | 项目卡可选，无阶段/职责 | 缺项目详情与阶段事实 |
| 我在做哪项工作、负责人是谁 | 自动编号标题，无负责人/协作者 | 缺业务目标与责任 |
| 本次用哪版方案/ALS/数据批次 | 输入批次只读投影，常为空 | 缺基线编辑与三指针 |
| 工具在哪执行、cwd/依赖是否可用 | 绝对路径外泄，执行器计数 | 缺人话执行位置 + 专家层 |
| 用哪个模型路由、是否可用、数据发往哪 | 默认模型 + 健康只读 | 缺运行冻结模型显示、外发区域事实 |
| 排队/运行/等待谁/失败/未知 | 运行状态有 | 基本具备，但呈现偏工程 |
| 生成了哪版、检查了什么、谁复核了哪版 | 成果 + 复核卡 | 缺交付包、版本链、检查证据视图 |
| 换数据如何保留历史/复用代码/比较/再交付 | **无换批次入口** | **核心 SC-03 未闭环** |

后端其实已支持换批次的关键一步：`POST /api/works/:id/input-baselines`（追加式基线，`http.ts:480`）**已存在，UI 只读不写**。这是低成本高价值的接线点。

## 5. 后端已有、UI 未接的能力（改造的"免费弹药"）

| 能力 | 后端 | HTTP | 现状 |
|---|---|---|---|
| 审计浏览/导出（SHA-256 链） | ✅ `service.ts:1419` | ✅ `GET /api/audit/export` | UI 无 |
| 发布审批记录/创建/撤销 | ✅ `service.ts:277` | ✅ `http.ts:269` | UI 无 |
| 应用发布回滚 | ✅ `service.ts:384` | ✅ `http.ts:293` | UI 无 |
| 运行事件历史 + 可续传 SSE | ✅ | ✅ `GET /api/runs/:id/events[/stream]` | UI 用 15s 轮询、非持久 |
| 追加输入基线（换批次） | ✅ | ✅ `POST /api/works/:id/input-baselines` | UI 只读 |
| 指标 JSON/Prometheus、doctor、备份/恢复 | ✅ | 部分（metrics 有路由；doctor/备份仅 CLI） | UI 无 |
| 身份主体/项目成员/授权解析 | ✅ 库 | 无管理路由 | UI 无；**真实 SSO 未实现** |
| 知识检索/候选/验证/快照/语料 | ✅ 完整服务 | **无 HTTP 路由** | UI 无；需先补路由 |
| 构建 provenance / 执行计划 | ✅ `registry.ts:73` | 公开投影未含 | UI 无 |
| 每运行 outbox/dead-letter、执行域健康 | ✅ | 计数在 bootstrap | UI 未渲染 |

**已接、不是缺口**：业务复核、取消/重试/对账、模型健康显示、待答问题、成果下载。
**需后端先行、不能只画 UI**：知识管理（补路由）、每运行 token/成本（需先采集；当前只有时长）、真实 SSO/容器隔离（属部署阶段）。

## 6. 目标体验

**工作页 = 任务工作台，聊天是辅助页签。**

```
┌ 工作头：业务目标 · 项目·应用·批次 · 状态胶囊 ┐
│ 三指针：编辑中基线 I2 ｜ 最近运行 R2 结果 ｜ 当前认可交付 D1(B1) │
├ 主区页签：对话与活动 ｜ 文件与代码 ｜ 差异与问题 ｜ 检查与复核 ｜ 交付历史 ┤
│  （应用贡献表格/代码/规则/证据视图；平台不硬编码 Listing/DVP） │
├ 右栏（可收合）：本次基线 · 执行位置(人话) · 就绪 · 待办 ┤
└ 专家/诊断抽屉：真实 cwd · session · 日志 · 模型路由 · 执行器 ┘
```

- **首页**：续作优先（最近工作 + 待我处理 + 当前交付置顶），新建工作收为明确入口，弱化问候与大输入框。
- **三种模式**共用一套工作事实：探索开发（对话+草稿）、换批复跑（选已有程序+新批次，显示变化）、审阅交付（并排版本+证据+复核+交付包）。
- **基础设施**默认隐藏，专家可展开；业务面只出现项目/应用/批次/人话状态/责任人。
- **状态分层**：工作摘要说人话（"B2 结果已生成，等待张三复核；当前交付仍为 B1"），技术七轴只在运行详情展开。

## 7. 改造方案（分阶段，按价值/风险排序）

### P0 · 止血与可信度（低风险，纯前端为主，最快见效）
- 修 §3 RC8 三个已核实缺陷（轮询抢对话、运行模型显示、会话时间）。
- **去基础设施外泄**：路径/session/hash/执行器/原生 hero/代理名收进专家抽屉；业务面换人话。
- **首页重构**为续作/待办/结果优先。
- **深链接**：view-state 坐标同步到 URL，支持刷新/分享/前进后退。
- **向导修复**：步骤可跳转、可取消；唯一工作空间预选、目录默认继承；绝对路径登记收进专家区。
- **统一对话/运行心智**：单一入口 + 模式提示，消除两个 textarea 的困惑。
- 出口：员工面不再出现绝对路径/原始 ID；三缺陷复跑消失；首页首屏即"继续上次工作"。

### P1 · 任务/交付体验重构（核心，前端 + 少量后端接线）
- 工作详情 → **任务工作台**（§6）：目标 + 基线 + 三指针 + 分页签；聊天降为辅助页签（仍用原生工厂，不建第二套）。
- **换批次重跑闭环（SC-03）**：接已有 `POST …/input-baselines`，"更新资料再次运行"→ 新基线 I2（展示 B1→B2）→ 继承 C1 → 新 Run → 本批检查 → 新交付；D1 保留适用范围。
- **差异/影响视图**：两次运行/批次的输入/代码/结果/issue 对照（应用贡献业务键，不按行号）。
- **复核/交付分离**：复核卡扩展为交付包（封存≠交付≠接收）+ 交付历史/替代/撤回。
- **应用贡献结果视图**：按多插件架构 §5.2/§7，Listing/DVP 结果从"纯聊天"升级为结构化结果页。
- **运行追踪升级**：用已有 `GET …/events` + SSE 替换 15s 轮询，持久事件历史（重启不丢）。
- 出口：同一工作跨两批数据完成两次交付，一页可对照输入/代码/结果/证据，旧交付不被覆盖。

### P2 · 呈现后端已有治理/可观测（企业平台完整度，多为"接线 + 视图"）
- **审计查看器**（接 `audit/export`）、**运营/健康面板**（metrics + doctor + outbox/dead-letter 计数 + 执行域健康）。
- **发布治理（管理员）**：审批记录/创建/撤销 + 回滚 + provenance/执行计划。
- **知识管理**：先补 control HTTP 路由，再做检索/候选/验证/快照/影响；或先只读检索 + 引用。
- **身份/权限只读视图**：当前主体/项目成员/授权解析（真实 SSO 仍属部署阶段）。
- **统一待办 inbox**：业务澄清/工具授权/环境故障/业务复核/交接回评分类。
- 出口：管理员能查审计/健康/审批/知识；待办覆盖全部交互类型。

### P3 · 规模/国际化/无障碍/成本（按需）
- 服务端过滤/游标（works/runs/audit）替换全量加载；完整 i18n（当前部分硬编码中文）+ 术语表版本。
- 无障碍：skip link、命令面板、快捷键、读屏回归（WCAG 2.2 AA）。
- 成本/用量：先显示运行时长（已有）；token/成本待后端采集，不伪造 0。
- 全局搜索/命令面板跨 work/project/run/artifact。

## 8. 不做什么（范围纪律）

本期不做：SSO/多租户/计费/插件市场、通用 agent 编排器/低代码、第二套聊天/React、微服务、DOM 改写、容器/VM 隔离。这些是需求明确的后续演进条件，不能被一个 UI 改造冒充。数据授权仍由 IT/API/执行环境承担，插件不恢复按名称/类别拒读。

## 9. 验收（借用既有审查目标，尚未实测）

- 非开发员工无需 shell/密钥/数据库 ID/口头指点完成核心任务；≥80% 试点参与者无协助完成（样本/角色测试前冻结）。
- 测试中不得发生：项目/批次误认、旧交付误当新结果、未执行误当完成、草稿意外丢失。
- 每阶段出口事实见 §7；工程门禁（verify-all）只证明实际执行的检查，不替代业务/部署验收。

## 10. 建议的下一步

先冻结**一个纵向切片**：SC-03"同一工作跨两批数据两次交付" + P0 止血。建议从 **P0 + 任务工作台骨架**入手——风险最低、感知质量提升最大，且为 P1 闭环铺路。实施前按需求 §12 完成相关角色评审与阻断项闭合；本文不构成开发批准。
